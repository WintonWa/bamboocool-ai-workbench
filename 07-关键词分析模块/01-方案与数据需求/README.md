### 几个反复出错的口径，先说清

**判断对象是三层**：市场关键词 / 关键词 × 子ASIN / 关键词 × 子ASIN × **当前目标**。
第三层最容易漏——它靠 `dim_keyword_child_goal`（当前目标 + 推广角色 + 目标历史版本）。

**词库 1991 个词，但只监控 300 个**，产品脊椎 342 个子体里本模块只命中 30 个。
所以「覆盖率」的分母要看清是哪一个。

**`fact_keyword_evidence` 那 562 条是确定性规则算出来的，不是 LLM 判的。**
接口形状不变，以后换成 Agent 时页面不用动。

**日报里有一处数据自相矛盾（Q3）**：页面自算「新增覆盖 162 / 丢失覆盖 68 / 涉及核心词 352」，
而库里存的句子写「新增覆盖 0 条、丢失覆盖 0 条，其中涉及核心词 114 条」。根因在
`../02-数据构建/lib_l89.py` 的 `build_daily_reports()`：`gained`/`lost` 按 `to_date == 当日` 过滤，
而汇总型事件（`organic_up`/`down`）的 `to_date` 也是当日。**给客户看之前必须修。**

**三组上游数据对 Agent 放开为 Demo 例外**（王楠 2026-08-31 拍定，共 17 列）：
产品定位、库存承接（`fact_keyword_child_absorb` 整表）、词库定性。它们本是别人的答案，
Demo 阶段放开。仍禁读 18 列。
