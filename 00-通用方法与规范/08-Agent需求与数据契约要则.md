# Agent 需求与数据契约要则（跨模块，v1.1）

> 定稿：2026-08-31 · 王楠口述理念，Kiro 整理
> 适用：ads / keyword / competitor / inventory 四个模块的**每一个** Agent
> v1.1 改了什么：把原来只有原则的第 1 节拆成四张可直接对照的清单
> （输入给什么 / 输入不给什么 / 输出要什么 / 输出不要什么），并把判据加上时间限定。
>
> 本文只管一件事：**怎么写需求文档和数据契约，才不会写出让 Agent 无法判断的契约。**
> 需求预测那一个 Agent 的逐表逐列清单见 `01-方案与数据需求/12-需求预测Agent职责修订.md`。

---

## 0. 这份要则为什么存在

广告 Agent 的实测结论：**不是实现写错了，是需求文档和数据契约写错了，实现忠实地照做了。**

| 层 | 实测 |
| --- | --- |
| 数据 | `ext_diagnosis` 21 行、`ext_recommendation` 21 行，`value_origin` 全部 `constructed`，只覆盖 5 个子 ASIN |
| 契约 | 事实桥把这些行原样发给 LLM 当 `stage_contracts[*].items` |
| 提示词 | 「业务判断已经由当前 context 和冻结规则确定，你的职责是按顺序核验并提交」 |
| 门禁 | `validateAdsStage`：`stable(items) !== stable(expected.items)` —— 整个 items 逐字节比对 |
| 结果 | 真模型落库内容与事实桥输出逐字节相同（4 个阶段中 3 个完全一致，第 4 个只差 `0` vs `0.0` 的序列化痕迹） |

**一个契约只要钉了答案，实现得越严谨，Agent 越不可能判断。** 广告那侧的工程质量是好的——原子写入、契约门禁、只读事实、禁止 LLM 碰 SQL——正因为它严格执行了一份写错的契约，才把 LLM 压成了复印机。

所以要治的是上游。

## 1. 判据：**这个时间点上，业务能拿到什么**

> 能输入的，是运营在 Agent 这一次运行的**那个时刻**、打开自己的后台就能拿到的东西。
>
> **输出不能是已经有了结论、再让 Agent 去解释它。**

「这个时间点」是硬限定，三种偷换都要挡住：

| 偷换 | 例子 |
| --- | --- |
| 换成「将来能拿到」 | 「等接了 API 就有了」——现在拿不到就是拿不到 |
| 换成「我们库里有」 | 数据包里有 30780 行预测，但运营后台没有这一份 |
| 换成「算一下就有」 | 覆盖天数一个除法就出来——可它要先有预测，而预测是 Agent 的产出 |

逐字段问三句：

1. **运营打开后台能直接看到它吗？** 能 → 输入
2. **它要算出来、判断出来才有吗？** 是 → 产出
3. **它在我们的构造脚本里被写出来过吗？** 在，且属于产出侧 → **禁读**

第 3 问最容易漏。前两问靠常识就能过，第 3 问要去翻构造脚本——广告那 21 行、需求预测那 30780 行，都是第 3 问没问。

## 2. 输入：**给什么**

| 类别 | 具体 | 为什么能给 |
| --- | --- | --- |
| **已发生的事实** | 历史实销、历史流量与点击、历史广告花费与订单、历史缺货日与可售、历史成交价、历史排名与评论数 | 运营后台直接导得出 |
| **此刻的状态** | 当前可售库存、在途数量、当前售价、当前小类排名、当前广告结构与出价、当前关键词自然位 | 此刻的快照，能查 |
| **产品关系** | 父子体归属、装盒数、组合内容、尺码与颜色、FNSKU | 主数据，客观存在 |
| **产品定位** | 运营设定的产品目标、品线归属、运营负责人 | 人设定的，系统里有 |
| **人排的计划** | 活动排期与折扣幅度、已定的广告预算、已下采购单与 ETA、已定的调价计划 | **人已经排好了**，后台能查到 |
| **外部可观察** | 竞品报价与变体、竞品排名与评分、关键词搜索量、第三方跟卖 | 抓得到 |
| **上游 Agent 本次产出** | 库存 Agent 这一次跑出来的承接判断 | 真实业务里由 Agent 产，见 §4 |

### 2.1 同一个字段，来源不同判定不同

这是最容易判错的一类，判据是问：**这个数是人填的，还是算出来的。**

| 字段 | 人填的 | 算出来的 |
| --- | --- | --- |
| 未来 30 天广告花费 | 运营排定的预算 → **可输入** | 从历史外推的 → **禁读**（它是「投入会怎么变」的答案） |
| 未来活动排期 | 运营报的 deal 排期与折扣 → **可输入** | `preset_uplift` / `expected_effect_ratio` → **禁读**（那是「会抬多少」的答案） |
| 未来到货 | 采购单上的数量与 ETA → **可输入** | 推算的「预计可售转化日」→ **禁读** |

排期本身可以给，排期**预计带来多少提升**不能给。这两个常常在同一张表的相邻两列。

## 3. 输入：**不给什么**

不是「禁止」，是**这些东西在真实业务里那个时间点根本不存在**——它们是本项目为了搭页面烤出来的答案。

| 类别 | 具体字段（实测存在的） | 它已经替 Agent 答了 |
| --- | --- | --- |
| **对未来的预测** | `fact_child_forecast_daily.p10_units/p50_units/p90_units`、同表 `baseline_units`、`weekday_factor`、`selected_model`、`model_wape` | 将来卖多少、用哪个模型 |
| **从预测派生的投影** | 覆盖天数、安全线突破日、预计断货日、压力情景断货日、最晚下单日、建议补货量 | 什么时候出事、该补多少 |
| **已分解的因子** | `seasonality_factor` / `lifecycle_factor` / `advertising_effect_ratio` / `promotion_effect_ratio` / `price_effect_ratio` | 每一项影响多少 |
| **已剥离的干净基线** | `clean_baseline_units`、`estimated_demand_units`、`lost_sales_units`、`potential_demand_units` | 历史被缺货压低了多少 |
| **已成文的中文理由** | `adjustment_reason`、`change_reason`、`rationale`、`what_happened` | 为什么 |
| **已分级的结论** | `risk_status`、`priority`、`attention_level`、`lifecycle_stage`、`direction`、`target_fit` | 结论本身 |
| **已给的置信度** | `confidence_score`、`wape` / `bias`、选中了哪个模型 | 这个判断有多可信 |
| **预计效应** | `preset_uplift`、`expected_effect_ratio`、`performance_index` | 计划会带来多少 |
| **数据质量与构造元数据** | `quality_status`、`demand_quality_flag`、`value_origin`、`method_version` | 哪条数据算不算正常、哪些是造的（且是英文码值，G9 禁上屏） |

**判断这一列该不该进的通用问法**：把这一列的值念出来，是不是就把 Agent 该说的话说完了。`lifecycle_stage` 取值是 `成熟期`，中文、可直接上屏——念出来就答完了「生命周期在哪一段」。

## 4. 输出：**要什么**

| 类别 | 具体 | 约束 |
| --- | --- | --- |
| **判断** | 哪一类成立、哪一类不成立 | 取值必须在契约钉的词表内 |
| **量** | 预测数字、影响幅度、优先级、置信度 | 判断不出就给 NULL，不许凑一个数 |
| **理由** | 中文一句话，结论先行 | 引用的每个数字必须能与确定性层核对上 |
| **引用** | `evidence_ids` / `refs` | 必须能解析到证据，不许悬空 |
| **排序** | `ord` | 哪一项最要紧，必须是完整排列 |

**「判断不出就给 NULL」是要写进契约的正式选项。** 需求预测实测走过这条路：生命周期那一项真模型给了 `null`，没有硬凑——那是它在判断的证据。

## 5. 输出：**不要什么**

| 不输出 | 为什么 |
| --- | --- |
| **确定性算术** | 逐日库存余额、覆盖天数、缺口量、超量件数——算术留在工作台，阈值才能在参数面板改完立刻重算；塞进 Agent 就得重跑才生效 |
| **精确执行值（规则未确认时）** | 预算、出价、广告位调整幅度——客户没确认阈值前给具体数值是替他做决定 |
| **跨模块动作** | 广告 Agent 不出补货量，库存 Agent 不出出价——各自越界会产生两份互相矛盾的建议 |
| **综合评分** | 单一威胁分数 / 健康分——要的是分级加可解释依据，一个数字盖掉了理由 |
| **因果断言** | 只能给相关与条件判断。`causal_claim` 必须为 false |
| **英文码值** | 翻译只发生在一处；Agent 一律输出码值，除契约逐字段点名的自由文本 |
| **对自己不确定性的辩护** | 「本结论仅供参考」这类不上屏，写进 `uncertainty` 字段 |

## 6. 构造数据合法，构造结论不合法

Demo 的定位没有变：**缺什么构造什么**，客户没给全的字段照造。但构造**只许发生在输入侧**：

| | 例子 | 判定 |
| --- | --- | --- |
| 构造输入 | 历史销量、历史广告花费、活动排期、产品关系、装盒数、竞品报价 | **合法**——真实业务里存在，只是客户没给全 |
| 构造产出 | 断货日、诊断结论、优先级、调整方向、中文理由、置信度 | **不合法**——真实业务里由 Agent 产生 |

**这一条必须写下来，否则下一个人会拿「缺什么构造什么」当依据去构造结论，而且他不会觉得自己违规。** 广告那 21 行诊断自述 `constructed`，在「构造数据」这个授权下看起来完全正当。

## 7. Agent 之间可以串（2026-08-31 王楠拍定）

分界线不是「事实 vs 判断」，而是**这个判断由谁、在什么时候产生的**：

| | 判定 |
| --- | --- |
| 库存 Agent **本次运行**的产出 → 广告 Agent 的输入 | **允许**。真实业务里这个判断存在，因为有 Agent 在产它 |
| 我们为搭页面**预烤**的判断（`fact_child_inventory_decision`、`ext_diagnosis`） | **禁止** |

串的代价要在需求文档里写明：**下游依赖上游先跑。上游没跑过时下游必须降级说明，不能悄悄回落到预烤值**——那等于绕过本条。

**本轮的例外（王楠拍定，记在这里以免被当成先例）**：广告暂时把数据包的库存投影当作库存 Agent 的产出使用，不换源。理由是时间，属于 demo 该付的代价。它是例外，不是规则。

## 8. 需求文档必须有的五节，缺一节退回

| 节 | 内容 | 判据 |
| --- | --- | --- |
| 1 判断对象与触发 | 对象是子 ASIN / 关键词 / 竞品族中的哪一个；谁触发、怎么触发 | 对象错了后面全错（关键词的对象是词，不是 ASIN） |
| 2 职责表 | 两列逐项：**Agent 产出什么** / **工作台算什么** | 照 §4 与 §5 划 |
| 3 Agent 读哪些表 | 逐表逐列，照 §2 的七类对照 | 漏一张表 = 少了输入，Agent 会说判断不出 |
| 4 **不给 Agent 读的** | 逐列写明「它已经替 Agent 回答了什么」，照 §3 | **比第 3 节重要**：第 3 节漏一张表只是少信息，第 4 节漏一列就是答案泄漏，而且没有症状 |
| 5 输出与上屏 | 页面展示的就是 Agent 那一份；回落必须看得出来 | 不写这节，页面会继续读预烤表，Agent 白跑 |

## 9. 数据契约钉三样，不钉第四样

| 钉 | 为什么 |
| --- | --- |
| **形状** | 字段名与类型。两侧独立实现要能对接 |
| **词表** | 每个枚举字段的允许取值，中文与码值的归属逐字段写死 |
| **口径表** | `numbers` 里可引用的 metric key 清单，机器可读发布 |

**不钉：答案。**

只钉形状不够——两侧会各自发明词表，接得上但讲的不是同一件事；可一旦钉到答案，Agent 就变成复印机。**中间那一档才对。**

## 10. 门禁只能是约束型，不能是同一性型

| | 同一性门禁（错） | 约束门禁（对） |
| --- | --- | --- |
| 判据 | 提交的 **等于** 确定性层算的 | 提交的 **不与** 确定性层矛盾 |
| 写法 | `stable(items) !== stable(expected.items)` | 取值必须在词表内 / 不得与事实矛盾 / 符号须与结论一致 / `evidence_ids` 必须能解析 / 禁止因果断言 / 一句话字数上限 |
| 实现 | ads `validateAdsStage` | inventory `validateForecastJudgment` |
| 后果 | Agent 不可能贡献任何东西，而门禁全绿 | Agent 真判断，判错的被拦下 |

**数字仍然要逐字核。** `numbers` 必须等于确定性层的同口径值——那是交叉核对，不是钉答案：

- 钉「**你引用的数字不许编**」 —— 对
- 钉「**你的结论必须是这一个**」 —— 错

## 11. 写完自检六条，写代码之前跑

1. 产出侧的每个字段，在数据包里有没有同名或同义的列？有 → 答案泄漏
2. 契约文档里有没有出现完整的中文结论句？有 → 钉了答案
3. 门禁里有没有「等于确定性层的**结论**」这种判据？（`numbers` 的交叉核对不算）
4. **同一个对象连跑两次，契约允许两次结论不同吗？** 不允许 → 复印机
5. 换一个特征不同的对象，结论会变吗？不会 → 要么是模板，要么只有少数对象有数据
6. 把 Agent 换成任意一个 LLM，它拿到的输入够不够做这个判断？不够 → 输入侧缺事实

**第 4 条最好用，因为它一句话就能判。** 一个真在判断的 Agent，同对象重跑结果**可以**不同：需求预测实测跑三次，生命周期给 `null` / `null` / `0.0`，五项的 `ord` 换过位。广告跑出来与事实桥逐字节相同。

配套边界：**凡是依赖具体判断值的门禁，要用合成行，不要指定活对象**（LLM 重跑会变，门禁会今天绿明天红，且看起来像代码坏了）。确定性特征（有没有在途、跑过没跑过）不受此限。
