# 统一数据边界总则

版本：v1.0  
定稿日期：2026-09-02  
适用范围：Bamboocool 工作台、四个业务模块、全部当前及后续 Agent、数据构建与 Demo fixture。

## 1. 目的与优先级

本总则是下一轮数据边界重构的唯一分类依据。它不描述“代码现在怎么做”，而规定“数据应处于什么位置、谁可以读、谁可以写、缺失时怎样表现”。现状证据见同目录另外四份清单。

发生冲突时：业务页面信息设计以《Bamboocool-工作台全局信息设计原则》为最高产品原则；Agent 输入输出边界以本总则为准；具体接口形状再由模块契约约束。`value_origin` 不得覆盖本总则的语义分类。

## 2. 五维分类必须同时记录

任何表，以及任何跨工作台—Agent 边界的字段，都必须分别记录以下维度。维度之间不能互相代替。

### 2.1 `semantic_role`

| 值 | 定义 | 典型例子 |
|---|---|---|
| `entity_master` | 客观身份与关系 | 父子体、关键词—子体、竞品族关系 |
| `historical_observation` | 已经发生的事实 | 历史销量、花费、排名 |
| `current_observation` | 当前可观察状态 | 当前库存、售价、自然位 |
| `committed_plan` | 人已设定或确认的未来计划 | 活动排期、预算、采购单 ETA |
| `deterministic_measure` | 事实经确定性计算得到、但不替用户判断 | 均值、差值、环比、聚合、计数 |
| `rule_judgment` | 程序按规则已给出的业务判断 | 风险档位、异常状态、规则优先级 |
| `agent_judgment` | Agent 产生的判断与文本 | 预测、诊断、机会、建议、置信度 |
| `human_decision` | 运营对建议的拍板 | 接受、修改、拒绝、暂缓 |
| `execution_record` | 已执行动作与复盘 | 执行时间、结果、复盘结论 |
| `system_metadata` | 技术状态与追溯字段 | run_id、版本、时间、context hash |
| `fixture_expected_answer` | 仅供 Demo/测试验证的预制答案 | 黄金样本结论、预烤风险与建议 |
| `needs_decision` | 现有证据无法唯一归类 | 人填或程序算无法区分的字段 |

### 2.2 `provenance`

只允许：`customer_direct`、`external_observed`、`operator_set`、`synthetic`、`deterministic`、`agent_generated`、`human_generated`、`mixed`、`unknown`。

来源与语义是两件事。例如，模拟历史销量是 `historical_observation + synthetic`，合法进入 Demo 事实层；模拟断货日是 `fixture_expected_answer + synthetic`，只能进入 fixture。

### 2.3 `time_role`

只允许：`timeless`、`past`、`current`、`future_committed`、`future_inferred`、`run_metadata`、`mixed`、`unknown`。

未来计划与未来预测必须分开：采购单 ETA、确认预算与活动排期是 `future_committed`；预测销量、预计断货日、预计提升系数是 `future_inferred`。

### 2.4 `runtime_zone`

只允许：`observation_store`、`plan_store`、`feature_store`、`rule_result_store`、`agent_result_store`、`human_action_store`、`fixture_only`、`quarantine`、`needs_decision`。

### 2.5 `workbench_surface`

只允许：`fact_area`、`agent_area`、`human_action_area`、`internal_only`、`must_not_render`、`needs_decision`。

## 3. 不可变规则

### 3.1 模拟事实合法，模拟答案不合法

- Demo 可以构造真实业务中本来就存在的输入：实体关系、历史事实、当前观察与已承诺计划。
- 预测、断货日、风险、生命周期阶段、诊断、机会、优先级、理由、置信度与建议若为预制，只能放入 `fixture_only` 或独立 `demo_seed` run。
- `demo_seed` 必须拥有独立 run_id、明确 seed 模型/来源、与正式结果物理或逻辑隔离；默认工作台不得选中它。
- expected answer 只能用于测试约束，不得进入生产/演示的正式输入 payload，也不得成为“无结果时的旧答案”。

### 3.2 工作台无 Agent 也必须成立

- 工作台事实区始终可以展示实体、事实、计划、中立特征与明确标识的规则结果。
- 关键经营依据必须能脱离 AI 文本被理解。
- 没有 Agent 结果时，Agent 区显示“尚未分析”；不得回落预烤判断、旧 run 或规则文案冒充 Agent。
- 规则结果可以展示，但必须明确是规则结果，不能复用 Agent 区身份。

### 3.3 Agent 不得读取自己的答案

- 当前 Agent 的输出表、预烤同义字段、旧版本同类判断与 fixture expected answer全部禁读。
- 同一字段不能同时充当该 Agent 输入和输出。
- 门禁可以校验形状、枚举、证据引用、数字真实性、事实矛盾和跨步闭环；不得要求 Agent 结论等于预制结论。
- 数字交叉核对只证明“引用数字没有编”，不能锁定结论。

### 3.4 上游 Agent 结果必须以 run 接入

同时满足以下六项才能读取：需求明确声明依赖；`status='completed'`；有 `run_id`；`data_as_of` 或 context 可核对；结果完整；缺失时显式降级。任何一项缺失，都不能静默改读基础包答案。

上游 Agent 输出进入下游输入时，字段仍是 `agent_judgment`，不会因为“已经存在”变成事实。

### 3.5 prior run 只能用于明确的比较任务

- 任务必须明确要求“与上次比较”；输入中标识 `prior_run_id`。
- prior run 必须是同对象、completed、context 可比较的上一版。
- prior run 不能冒充当前观察，也不能用于强迫本轮复刻上一轮结论。
- 页面“较上次”必须能 JOIN 到真实上一版；首次运行显示“首次分析”。

### 3.6 确定性指标与规则判断分层

- 均值、差值、计数、聚合、位次变化量属于 `deterministic_measure`，通常允许给 Agent。
- 风险档位、是否异常、任务优先级、状态分类属于 `rule_judgment`。
- 当 Agent 独立判断同一问题时，对应 `rule_judgment` 禁读；只有作为明确上游规则或对照基准时才条件性允许，并须在契约中点名。

### 3.7 provenance 只用于来源对账

`direct / derived / constructed` 不决定能否输入 Agent，也不决定能否上屏。每次边界检查必须先看 `semantic_role`，再看 provenance、time_role 与 run 状态。

## 4. 接口必须分层

工作台事实接口与 Agent 输入接口不得直接共用一个摊平 payload。

| 接口 | 可以包含 | 不得包含 |
|---|---|---|
| 事实/页面 read model | 事实、计划、特征、标明来源的规则结果、独立 Agent 区块 | 把规则与 Agent 结论摊平成无来源字段 |
| Agent input contract | 逐字段 allow-list、上游 completed run 引用、证据目录 | 页面文案、fixture、自己的输出、未完成 run |
| Agent result contract | run 头、结果子表、证据引用、完整性状态 | 基础事实副本、静默 fallback |
| human action contract | 原建议引用、人的决定、修改内容、执行状态 | 把人的决定写回 Agent 结果 |

页面 context hash 只覆盖判断对象、事实版本、计划版本、规则参数和有效上游 run_id；不得覆盖当前 Agent 自己的输出，否则会形成循环依赖。

## 5. 运行状态与展示规则

| 状态 | 正式 Agent 区 | 事实区 | 规则/处理 |
|---|---|---|---|
| `not_run` | 尚未分析，不显示结论 | 正常显示 | 可提供触发入口 |
| `queued/running` | 只显示真实进度，不显示半份结论 | 正常显示 | 半成品可保留在 staging |
| `partial/writing` | 不作为正式结论渲染 | 正常显示 | 仅进度/内部诊断可见 |
| `completed` | 完整性、context、字段门禁全过才显示 | 正常显示 | 唯一正式读取态 |
| `stale` | 显示过期状态；结论默认收起且不可与新事实混排 | 正常显示新事实 | 引导重跑，不回落 fixture |
| `failed` | 显示失败原因和上次有效 run（若明确标成 prior） | 正常显示 | 不展示失败 run 子表 |
| `skipped` | 显示跳过原因；可链接被复用的 completed run | 正常显示 | 不能把 skipped 自身当 completed |

“阶段进度可见”不等于“阶段业务结论可正式上屏”。running/partial 的结果可用于恢复与调试，但必须与正式 Agent 区隔离。

## 6. 工作台读取边界

工作台可直接读取 `entity_master`、`historical_observation`、`current_observation`、`committed_plan`、`deterministic_measure`；可读取已单独标识的 `rule_judgment`；可按完整 completed run 读取 `agent_judgment`；可在独立区域读取 `human_decision` 与 `execution_record`。

工作台不得直接渲染 `fixture_expected_answer`、staging/recovery、running/failed 子表、无 run 归属的 Agent 文案或无法确认来源的混合字段。

## 7. 推荐动作词表

只允许：`keep`、`keep_but_reclassify`、`move_to_feature_store`、`move_to_rule_result_store`、`move_to_agent_result_store`、`move_to_fixture`、`quarantine_legacy`、`remove_after_migration`、`needs_decision`。

“remove”只能发生在读取方完成切换、备份/fixture 已建立且门禁覆盖之后。本审计不授权删除。

## 8. 最低验收门禁

1. 每个 Agent 有机器可读 allow-list 与 deny-list。
2. 自己输出表及同义预烤字段在输入桥零命中。
3. 上游 Agent 依赖逐项校验 run_id、completed、完整性、data_as_of/context。
4. running、writing、failed、recovery 数据无法进入正式页面读取查询。
5. 无 Agent 结果时事实区仍可用，Agent 区只显示尚未分析。
6. 同对象同日两次 run 并存；prior run 可 JOIN；首次运行 prior 为空。
7. context hash 不含当前 Agent 输出与 fixture。
8. 测试只核约束与事实一致性，不核答案同一性。
