## 4. 页面与判断对象

两个页面（方案 §4.4 与全局原则 §6）：

| 页面 | 总览负责定位 / 详情负责解释 |
| --- | --- |
| 竞品威胁总览 | 当前威胁最高、变化最大的竞品产品族 |
| 单一竞品分析 | 身份、产品族、市场表现、价格促销、关键词流量、共同时间线 |

核心关系：**价格/促销、销量/排名、流量/关键词在共同时间轴上的变化**。

对外输出（关键词与广告模块会把这些当竞争证据，方案 §5.3）：带时间的价格、促销、市场、关键词、流量变化，共同时间线，关注程度，可能影响范围。

**判断对象是竞品产品族，不是单个竞品 ASIN。** 这一点决定总览那张比较表的行是什么，先定下来再设计板块。

关键边界（方案 §6，硬要求）：**同期变化先作为共同证据，经过验证后才形成因果结论。** 竞品降价与自家销量下滑同时发生，页面要表达的是"这两件事同期发生"，不是"因为它降价所以我们跌了"。共同时间线这个组件的存在意义就是让运营自己看出关系，而不是替他下因果判断。

## 5. 数据需求要怎么表达

**产品对象脊椎固定：342 个子 ASIN / 5 个父 ASIN，统一基准日 2026-08-03。** 取自
`/Users/linsen/BAM/02-产品销售库存模块/02-数据构建/v0.3.0/bamboocool_product_sales_inventory_v0.3.0.sqlite`
的 `dim_product_child` / `dim_product_parent`。

- 竞品对象是外部产品，自然不在脊椎里——但**"哪些自家子体受这个竞品影响"这条关系的自家一侧必须落在这 342 个里**，靠 `bridge_competitor_child` 表达；
- **不要在自己的包里重建 `dim_product_child` / `dim_product_parent`。** 需要自家产品身份就 `ATTACH` 产品包读。广告模块当初自建了一套 521 个子体的维度（7 列 vs 产品包 20 列），与脊椎交集只有 188、父体只对上 2/5，跨模块 join 因此断裂，这是目前唯一在返工的地方；
- 缺什么就构造什么。这套 Demo 给内部团队和客户看**页面交互逻辑是否合理**，精度可以降低，**链路不能断**。竞品的历史价格、促销、排名、流量客户大概率没给全，构造出来即可；
- 构造数据统一用 `value_origin` 列标档位（`direct` / `derived` / `constructed`），这列只用于内部对账，**枚举值绝不上屏**；
- 共同时间线要求多条序列共享同一根时间轴，所以各序列的粒度和区间要一起规划，不能一条按日一条按月然后在图上对齐；
- 独立 SQLite、只读打开（`file:…?mode=ro`），路径集中声明，不在业务文件里写死绝对路径。

反推的方法：从"页面必须产生什么结果"倒推计算链，再倒推数据对象、事件、状态、粒度和时间，最后才映射客户已有数据。**不要从"客户现有表里有什么"出发决定页面能做什么**——那会稳定地产生一种假完成：数据自洽、检查全绿，但页面任务无法完成。详见 `01-Demo数据构建方案制定方法.md` 第 1 节。
