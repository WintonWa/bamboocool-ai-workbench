# Bamboocool Demo 数据构建方案制定方法

版本：v1.0  
更新时间：2026-08-29  
适用范围：Bamboocool 后续所有业务板块的 Demo 数据规划  
文档边界：本文只规定“下一板块的数据构建方案应该怎样制定和验收”，不替任何具体板块选择数据、不设计具体业务表，也不执行数据构建

## 1. 这套方法要解决什么问题

后续构建 Demo 数据时，不能再从“客户现有表里有什么”出发决定 Demo 能做什么，而要从产品方案承诺的用户任务出发，反向推导完整数据需求，再判断客户数据能继承多少、缺失部分如何构造。

正确顺序是：

```text
产品能力
→ 用户实际操作
→ 页面必须产生的结果
→ 结果依赖的计算链
→ 计算需要的数据对象、事件、状态、粒度和时间
→ 客户数据映射与缺口
→ 派生或构造方案
→ 可执行验收
```

不能使用以下顺序：

```text
扫描到哪些表
→ 先把这些表导出来
→ 页面能展示什么就展示什么
→ 缺少的能力以后再补
```

后一种方法会稳定地产生一种假完成：现有数据自洽、质量检查全绿，但产品任务无法完成。

## 2. “可玩 Demo”的统一定义

> 精度可以降低，结构不能缺；算法可以简化，链路不能断；数据量可以控制，业务粒度不能错；数据可以构造，但口径和来源必须明确。

“可玩”允许：

- 预测、评分、归因等算法使用简化规则；
- 数值不具备真实经营决策精度；
- 只选择有限数量的代表对象；
- 用构造数据补足客户没有提供的事件、状态和时间序列；
- 使用轻量数据库或本地文件，不建设正式数据平台。

“可玩”不允许：

- 用更高层级的数据代替产品规定的最小分析单位；
- 用周期累计或均值代替页面要求的逐日/逐事件数据；
- 只生成能填满页面的静态数字，不生成交互和联动依赖；
- 因客户数据源缺失而静默删除能力；
- 用静态结论标签代替可复算的输入和计算链；
- 只验证文件、行数和非空率，不验证用户任务能否跑通。

因此，可玩程度不是由“数据够不够多”决定，而是由“承诺的能力链是否完整”决定。

## 3. 为什么必须产出这些规划材料

下列材料不是形式化负担。每一份都对应一种已经发生过或极易发生的遗漏。

| 规划材料 | 为什么需要 | 缺少时会发生什么 |
| --- | --- | --- |
| 能力—任务—完成定义 | 把抽象产品能力改写成用户能实际完成的任务 | 需求写了“分析、预测、诊断”，构建者却不知道做到什么程度才算完成 |
| 数据依赖图 | 从最终结果一直反推到最上游输入 | 只生成中间事实，没有发现预测、风险、推荐等下游结果仍然断链 |
| 粒度、时间和状态契约 | 同一个字段名在不同层级、日期范围和状态下含义完全不同 | 用父级替子级、用月份替日期、只有当前没有历史或未来、只有正常没有取消/失败 |
| 源—目标映射 | 区分客户真正提供的数据与目标能力需要的数据 | “扫描到字段”被误判成“业务数据可用” |
| 缺口处置队列 | 把缺失项变成当前版本任务 | 缺口只写入说明文档，实际构建时被整体推迟 |
| 场景清单 | 保证 Demo 有可重复触发的业务故事 | 页面有数据，却没有一个对象能完整演示核心能力 |
| 自动断言与人工演示步骤 | 同时验证数据正确和任务可完成 | 机械检查全绿，但页面筛选、切换和联动没有可用结果 |
| 来源、规则和版本说明 | 区分客户事实、推导和构造，并保证重复生成稳定 | 演示数据被误认成客户事实，或每次生成后关键故事漂移 |

这些材料共同组成一份《数据构建执行契约》。构建 Agent 和能力验收 Agent 必须使用同一个版本，不能各自维护一套理解。

## 4. 双 Agent 的分工

### 4.1 数据构建 Agent

它回答的问题是：

> 按照已经冻结的能力契约，怎样利用指定数据源和构造规则，生成完整、稳定、可查询的数据包？

主要职责：

1. 扫描用户指定的数据源范围；
2. 验证实际数据粒度、时间范围、指标语义、覆盖率和样例；
3. 填写源—目标映射；
4. 提出派生、补造和场景构造方案；
5. 定义守恒、关联、时间和版本约束；
6. 先做纵向切片，再批量生成；
7. 提交数据、manifest、血缘、质量报告和场景证据；
8. 根据失败单修正数据。

不得自行：

- 删除能力或交互；
- 降低业务粒度；
- 缩短必需历史或未来范围；
- 把源数据缺失解释成“这个能力不做”；
- 修改验收条件以适配已经生成的数据。

### 4.2 能力验收 Agent

它回答的问题是：

> 这些数据是否真的足以让用户完成产品方案承诺的任务？

它不是构建完成后才出现的普通审查者，而是在构建前负责制定验收部分的共同规划者。

主要职责：

1. 逐项阅读产品方案、能力清单和业务决策；
2. 把每项能力拆成用户动作和可观察结果；
3. 反推目标粒度、时间、状态、事件、输入和输出；
4. 编写自动断言、人工演示步骤和完成定义；
5. 审查缺口处置能否保持能力链完整；
6. 在纵向切片阶段尽早验收；
7. 最终逐能力给出 `PASS / FAIL / BLOCKED`；
8. 对修复涉及的全部下游能力重新回归。

能力验收 Agent 拥有阻断权，但不能代替构建 Agent 修改数据，也不能脱离产品依据自行扩大范围。

### 4.3 为什么要分成两个角色

如果同一个 Agent 同时决定范围、处理缺口、生成数据并判断自己是否完成，很容易把实现便利变成需求降级。

两个角色分开后：

- 构建 Agent 对“怎么实现”负责；
- 能力验收 Agent 对“是否完成用户任务”负责；
- 同一份契约让两者可以直接定位分歧；
- 验收结论不依赖构建者口头解释；
- 失败可以落到具体能力和具体数据缺口，而不是笼统地说“数据不够”。

## 5. 数据构建方案的制定流程

### 阶段一：冻结业务范围

先回答：这个板块的 Demo 到底允许用户完成哪些任务？

输入：

- 正式产品方案；
- 已确认的页面结构和交互；
- 能力清单；
- 客户访谈中的业务事实；
- 用户本轮明确的范围决策。

输出：

- 能力清单；
- P0/P1/P2 优先级；
- 明确不进入当前 Demo 的能力；
- 每项范围决定的证据位置。

为什么先做：数据源不能决定产品范围。若范围不先冻结，构建者会自然地优先实现“现成数据容易支持的东西”。

门禁：每项进入 Demo 的能力都有稳定编号和产品依据；范围删减均由用户确认。

### 阶段二：把能力拆成可完成的用户任务

每项能力至少写清：

```text
用户从哪里进入
→ 选择或输入什么
→ 系统返回什么
→ 用户再改变什么
→ 哪些结果必须随之变化
→ 用户最后能作出什么判断
```

禁止只写“支持趋势分析”“支持风险识别”“支持智能推荐”。这些是能力名称，不是完成定义。

输出：能力—任务矩阵，包括：

- `capability_id`；
- 页面和入口；
- 用户动作；
- 可观察输出；
- 联动结果；
- 正常路径和关键异常路径；
- 人工演示步骤；
- 最终完成定义。

为什么要拆：只有把能力写成动作序列，才能知道数据不仅要“显示”，还要支持筛选、切换、下钻、修改、版本变化和异常状态。

门禁：每个 P0/P1 能力都有从入口到结果的完整演示步骤。

### 阶段三：反向建立数据依赖闭包

从每个可观察结果开始逐层追问：

1. 这个结果是原始事实、规则计算还是情景结果？
2. 它需要哪些直接输入？
3. 每个输入的最小业务粒度是什么？
4. 需要历史、当前还是未来数据？持续多长？
5. 哪些事件会改变它？
6. 哪些状态和版本必须保留？
7. 页面汇总由哪些最低单元计算？
8. 上游变化后，哪些下游结果必须同步更新？

数据需求至少从六个维度描述：

| 维度 | 要写清什么 | 为什么 |
| --- | --- | --- |
| 对象 | 人、商品、活动、广告、关键词、任务等业务实体 | 决定主键和关联关系 |
| 粒度 | 一行代表什么业务事实 | 防止高层级数据冒充明细 |
| 时间 | 日期、时刻、区间、历史长度、未来长度 | 防止只有快照却要求趋势和预测 |
| 事件 | 新增、调整、暂停、取消、完成等变化 | 支撑联动、版本与因果故事 |
| 状态 | 正常、异常、缺失、失败、过期、低置信等 | 防止 Demo 只有理想成功状态 |
| 结果 | 指标、判断、排序、解释、建议和证据 | 确保页面读取的是可执行结果而非占位文案 |

输出：

- 能力依赖图；
- 目标数据对象清单；
- 每个对象的粒度、时间和状态契约；
- 指标定义与输入输出；
- 上游到下游的联动关系。

为什么要做依赖闭包：页面最上层的风险、建议、洞察通常依赖多级计算。只列最终字段或只列原始表都会漏掉中间链路。

门禁：从每个 P0/P1 页面结果都能沿依赖图回到最上游输入，且没有悬空节点。

### 阶段四：审计指定数据源并做映射

只有完成前三个阶段后，才开始检查数据源。

数据源范围由用户指定。指定范围内不存在的数据，直接写为“源缺失”；不需要自行扩大到其他文件夹寻找。

不能只看文件名和表头。每个候选字段必须检查真实行，以确认：

- 一行的业务粒度；
- ID 是单值、列表还是聚合对象；
- 日期是一日、月份、快照日还是报表区间；
- 指标是总量、归因量、累计值、均值还是滚动窗口；
- 目标主键下是否唯一；
- 非空率、对象覆盖率和日期范围；
- 多来源之间是否冲突。

每个目标输入标记为：

| 状态 | 定义 |
| --- | --- |
| `direct` | 客户源数据的粒度、口径和范围完全匹配，可直接继承 |
| `derived` | 可由现有字段按明确规则计算 |
| `supplemented` | 源缺失、粒度不足或时间不足，需要受真实锚约束构造 |
| `scenario_added` | 为未来事件、异常状态或演示故事专门构造 |
| `blocked` | 无法合理构造，且缺失会使能力结论失真，需要用户决策 |

输出：源—目标映射矩阵，至少记录源文件、Sheet、字段、源粒度、语义、日期、覆盖率、冲突、转换规则、目标对象和来源状态。

为什么在需求之后做：数据源审计负责回答“哪些可以继承”，不能负责决定“哪些能力值得做”。

门禁：每一个必需输入都有来源状态；不存在“没有检查”“以后再看”的空白项。

### 阶段五：把缺口设计成构建任务

每个 `derived`、`supplemented`、`scenario_added` 或 `blocked` 项都必须进入缺口处置队列，而不是只写进已知限制。

处置项必须包含：

- 影响的能力编号；
- 缺失对象或字段；
- 目标粒度和时间范围；
- 构建方法；
- 可使用的客户真实锚；
- 守恒或一致性约束；
- 允许的简化和误差；
- 来源标签；
- 自动测试；
- 负责人和状态。

为什么需要真实锚和守恒：构造数据不要求准确，但要与已知客户事实保持不矛盾。例如拆分明细后应能汇总回真实总量，构造事件后不能破坏其他既有汇总。

为什么需要确定性：必须使用固定规则和固定随机种子，确保不同版本重复生成时，明星场景和关键结果不会漂移。

门禁：影响 P0/P1 的缺口必须在当前构建计划中处理；若标记 `blocked`，必须在开工前交给用户决定。

### 阶段六：设计演示场景和数据规模

先设计“要演示什么故事”，再决定需要多少对象和记录。

每项 P0/P1 能力至少包含：

- 一个正常成功场景；
- 一个能体现能力价值的关键问题场景；
- 产品方案要求的变更或联动场景；
- 一个缺失、失败、取消、过期或低置信场景（适用时）；
- 明确的对象、输入事件、操作步骤、预期输出和自动断言。

数据规模由以下因素共同决定：

- 能否覆盖全部必需场景；
- 列表、筛选、聚合是否有足够密度；
- 是否仍能人工检查明星对象；
- 前端本地加载和查询是否流畅；
- 不截断真实对象关系；
- 不为了追求“大数据量”生成无业务差异的重复记录。

为什么场景先于规模：可玩性来自状态和关系差异，不来自简单增加行数。100 万行同质数据仍然可能像玩具；少量但覆盖完整能力链的数据反而更可玩。

门禁：P0/P1 场景覆盖率在计划层达到 100%，每个场景都能映射到具体数据构建任务。

### 阶段七：选择存储和交付形态

JSON、SQLite 或其他形式应由查询方式和交付用途决定，而不是先选格式再迁就数据模型。

判断原则：

- 需要多表关联、聚合、筛选和自动验收时，优先使用 SQLite 作为标准数据层；
- 前端需要直接加载的固定摘要和详情，可以从标准层导出 JSON；
- 同一份逻辑数据不要分别手工维护 SQL 和 JSON，应由同一构建流程生成；
- 不论使用何种格式，都必须保留 schema、版本、来源、质量和生成说明。

为什么格式放到后面决定：表和文件只是承载方式。过早争论 JSON 还是 SQL，会掩盖真正需要先确定的业务粒度、关系、事件和查询。

输出：

- 标准数据层形式；
- 页面导出形式；
- 数据包目录；
- manifest 内容；
- 生成与更新方式。

### 阶段八：先做纵向切片，再批量生成

先选 1–2 个代表对象，把一项或一组核心能力从上游事实、构造数据、派生计算一直做到页面查询结果。

能力验收 Agent 此时执行第一次完整演示，而不是等所有对象生成完才检查。

为什么需要纵向切片：如果数据粒度、版本关系或计算链设计错误，批量生成只会放大返工。一个完整对象比一百个不完整对象更能验证方案。

门禁：核心纵向切片通过能力、数据和场景验收后，才允许批量生成。

### 阶段九：把验收写进方案，而不是事后补

验收必须分为五层：

1. 契约验收：每项能力是否有完整数据定义和完成条件；
2. 来源与构造验收：来源状态、构造规则、真实锚和标签是否齐全；
3. 数据验收：主键、外键、范围、连续性、守恒和版本是否正确；
4. 能力验收：页面动作是否能返回并联动正确结果；
5. 场景验收：核心故事能否按固定步骤重复触发。

为什么分层：数据正确不等于用途正确。只有五层一起通过，才能避免“已有表检查全绿，但页面能力不可运行”。

门禁：P0/P1 必须逐项 `PASS`，不能只给整个数据包一个笼统的“通过”。

## 6. 两个 Agent 的标准协作顺序

1. 两个 Agent 读取同一套产品方案和决策资料；
2. 能力验收 Agent 起草能力、任务、粒度、状态、场景和完成定义；
3. 数据构建 Agent 只对可实现性提出问题，不得自行删减能力；
4. 双方冻结《数据构建执行契约》版本；
5. 数据构建 Agent 审计指定数据源并填写源—目标映射；
6. 数据构建 Agent 提交缺口处置和构造计划；
7. 能力验收 Agent 判断处置后能力链是否闭合；
8. 数据构建 Agent 完成纵向切片；
9. 能力验收 Agent 按人工步骤和自动断言验收；
10. 纵向切片通过后，数据构建 Agent 批量生成；
11. 能力验收 Agent 执行五层最终验收；
12. 失败项按能力编号退回，修复后回归全部受影响下游能力；
13. P0/P1 全部通过后才能交给前端。

双方可以在同一文档协作，但字段所有权分开：

| 内容 | 主要所有者 |
| --- | --- |
| 产品依据、用户动作、预期结果、优先级、完成定义 | 能力验收 Agent |
| 目标粒度、时间、状态、必需数据 | 能力验收 Agent 起草，双方确认 |
| 来源映射、构造方法、真实锚、守恒规则 | 数据构建 Agent 起草，双方确认 |
| 自动断言、演示步骤、最终状态 | 能力验收 Agent |
| 构建状态、产物位置、构建证据 | 数据构建 Agent |

任何人若要修改能力范围、业务粒度或完成定义，都必须记录变更并取得用户确认。

## 7. 一份合格的数据构建方案必须包含什么

### 7.1 方案正文

1. 当前板块范围与不做项；
2. “可玩”的具体完成标准；
3. 能力—用户任务清单；
4. 数据依赖图；
5. 目标对象及粒度、时间、事件、状态、版本定义；
6. 指定数据源范围；
7. 源—目标映射；
8. 缺口分类和构造方法；
9. 场景和明星对象计划；
10. 数据规模与选样逻辑；
11. 存储、目录和版本策略；
12. 纵向切片计划；
13. 五层质量门禁；
14. 双 Agent 分工和交接方式；
15. 发布标准与需要用户决策的阻塞项。

## 8. 方案制定完成的门槛

注意：这里判断的是“数据构建方案是否可以开工”，不是“数据包是否已经构建完成”。

只有同时满足以下条件，方案才可交给数据构建 Agent：

- P0/P1 能力清单完整且有产品依据；
- 每项能力都有用户动作、可观察结果和完成定义；
- 每项能力的对象、粒度、时间、事件和状态已经明确；
- 所有最终结果都有闭合的数据依赖图；
- 每个必需输入都有来源状态或明确的待审计项；
- 每个已知缺口都有构造或阻塞处置；
- P0/P1 场景覆盖率为 100%；
- 纵向切片对象和验收步骤已经选定；
- 五层门禁已经写入方案；
- 两个 Agent 的字段所有权、交接节点和失败单格式已经确定；
- 任何能力降级或业务粒度变化都已有用户确认。

如果以上任一项缺失，继续扫描或生成数据只会把未定义的问题推迟到更昂贵的阶段。

## 9. 数据包最终发布的门槛

数据构建完成后，只有同时满足以下条件才能称为“可玩 Demo 数据包”：

1. P0/P1 能力数据覆盖率 100%；
2. P0/P1 能力验收通过率 100%；
3. 必需场景覆盖率 100%；
4. Critical 缺口为 0；
5. 五层门禁全部通过；
6. 关键结果可以从上游明细按 Demo 规则复算；
7. 客户事实、派生、补造和场景数据清楚区分；
8. 固定规则和种子下重复生成，关键演示结果稳定；
9. 前端无需临时硬编码关键业务结果；
10. 能力验收 Agent 能仅根据契约、数据包和证据独立复核。

## 10. 后续必须避免的做法

- 先扫描数据源，再倒推产品能做什么；
- 把数据索引当作业务语义审计；
- 用表头判断粒度和指标含义；
- 把缺口矩阵当说明材料，不转成构建任务；
- 把阶段性来源事实层交给前端当完整数据包；
- 把“算法可以简化”理解为“所需输入可以省略”；
- 把“数据量不必太大”理解为“可以降低业务粒度”；
- 用父级、月度或窗口数据替代产品要求的子级、逐日或逐事件数据；
- 只做正常状态，不做取消、失败、过期和版本变化；
- 只检查已有表，不检查必需表是否存在；
- 修复一个字段后只跑局部测试，不回归所有下游能力；
- 让构建者自己决定需求降级并自己宣布验收通过。

## 11. 一句话执行原则

以后任何板块开始构建数据前，都必须先回答：

> 用户要完成哪些任务；每项任务需要哪些对象、粒度、时间、事件、状态和结果；客户数据能继承什么；缺失部分怎样构造；用什么场景和断言证明这项任务真的能完成。

这五个问题没有形成共同契约之前，不开始批量构建数据。
