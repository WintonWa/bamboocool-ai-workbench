# 需求预测 Agent：分段运行需求

> 提出方：工作台（消费方）
> 起因：实测一次运行 **107 秒**，期间界面无任何可见变化，运营读作卡死
> 立场沿用 `12-需求预测Agent职责修订.md`：**本文只说页面需要什么，不规定 Agent 怎么算、怎么切**
> 日期：2026-08-31

---

## 0. 实测事实（可复现）

```
curl -m 200 -w "%{time_total}" \
  "http://127.0.0.1:18820/api/inventory/run-demand-forecast?object=B0B3LM36WB"
```

| 项 | 实测值 |
| --- | --- |
| 墙钟时长 | **106.95 秒**（11:01:48 → 11:03:35） |
| 九个步骤 `duration_ms` 合计 | **≈ 5.7 毫秒** |
| 一次调用的输出量 | 90 天 × 3 分位 = **270 个数字** + 5 项判断 + 7 个步骤 |
| 落库方式 | `writeDemandForecastRun` 单个 `BEGIN IMMEDIATE` 事务，结束时一次性写入 |
| 三条 run 的时间戳 | `created_at` 与 `completed_at` **完全相同** |
| 外壳单次调用超时 | `AGENT_TIMEOUT_S = 180` 秒，余量 73 秒 |

**107 秒里，一步都没被记下来。** 七个步骤全是读表与校验（各 0.0ms），真正花时间的那件事不属于任何一步。

---

## 1. 为什么不能在呈现层解决

外壳可以把九步按固定节奏逐条揭示（现有 `REVEAL_MS = 220`），9 × 0.8 秒 ≈ 7 秒。**但后面还剩 100 秒空白。**
加计时器只是把「卡住」换成「看着它卡 107 秒」。

而且揭示期间不能显示步骤的结果行：「五类判断通过契约校验」是结论，响应没回来就显示它等于编。
只能显示步骤名，那就成了一个 7 秒的空转，然后 100 秒静止。

**所以节奏必须来自真实运行，不能来自播放速度。**

## 2. 页面需要什么

### R1 运行中就能读到进度 —— 阻塞项

现在库里在结束前什么都没有，页面无从轮询。需要在跑的过程中可以知道：**哪一步在跑、哪些已完成**。

两种形状页面都能接，**由 Agent 侧选**：

| 形状 | 页面怎么读 |
| --- | --- |
| 分步落库 | run 行开跑即建（带一个「在跑」状态与开始时刻），每步完成即写一行 step，页面轮询 |
| 流式响应 | SSE 或分块响应逐步推送，页面消费流（`server.ts` 已有 `streamHeaders`，看是否可复用） |

### R2 步骤数与单步时长

目标：**运营点一下之后，每 1~3 秒有一次可见变化，且每次变化对应一件真发生的事。**

| 约束 | 值 | 理由 |
| --- | --- | --- |
| 单步时长上限 | **≤ 25 秒** | 超过这个长度人开始怀疑坏了 |
| 总步数 | **≥ 6** | 少于这个数就没有「步骤感」 |

前四步（读历史销量与缺货、读影响项、读未来计划、确认上架与承接）本来就快，天然满足。
需要切的是判断与产出那一整块 107 秒。

参考粒度（**不是规定**，Agent 侧定）：

- 五类判断一段 + 逐日按月三段 = 4 段，单段约 27 秒，总步数 8
- 五类判断一段 + 逐日按半月六段 = 7 段，单段约 15 秒，总步数 11

### R3 分段只按时间窗切，不按抽象层切

每一段仍要吐出那一段的**真实逐日数字**。

**不接受**：改成「LLM 给形状参数、代码展开成 90 天」。那样 LLM 不再产出预测，只产出参数，等于把产出侧退回代码——`12` 号文第 3 节那张职责表就白恢复了。

### R4 长跑要能和失败区分开

现在 `status` 只有 `completed`，且 `created_at == completed_at`。页面因此无法回答「它还在跑，还是已经挂了」。

需要：run 行在**开跑时**就存在，带「在跑」状态与开始时刻；结束时改成完成或失败。

这条同时修掉一个当前的无症状错误：外壳 180 秒超时会先返回「Agent 超过 180 秒没有回应」，而 Agent 仍在跑并最终写库 —— **面板报失败，页面却出现一条更新的 run**，两边说的不是一件事，且界面上看不出来。

### R5 模型耗时要归到步骤

每步的 `duration_ms` 要含它自己真实花掉的时间。现在合计 5.7 毫秒，面板于是在等了 107 秒之后报「2 ms」。

外壳的注释是对的 ——「显示的是各步真实耗时之和，不是墙钟时间；把揭示节奏当耗时报出去就是拿节奏冒充数字」。问题在另一头：**真实耗时没被记。**

### R6 `baseline_units` 与「数字对不对得上」的检查 —— **先不做**（2026-08-31 定）

Agent 侧问过按整段查还是按每天查（run 级 `impact_pct` 对逐日 `baseline_units`）。
**这一条先不判断：有数、有结果就可以。** Demo 要证明的是判断真的在发生、过程看得见，
数字准不准是后面的事。所以：

- `baseline_units` 可以继续为空，不要求 Agent 补
- 不定容差，不做「因子乘回基线重建 `p50`」这条检查
- 逐日因子分解（季节/生命周期/广告/活动/价格系数）也不要求 Agent 产出

**但有一个必须修的，它和准不准无关。** 空基线曾经被 `compute.py` 用 `or 0`
套成 0，于是日详情写出「基线 0.0 件」，紧挨着「17 件」：

| 对象 | 来源 | 第一天预测 | 基线 |
| --- | --- | --- | --- |
| `B0B3LM36WB` | Agent | 17.0 件 | **0.0** ← 错数 |
| `B0CBPXNC1M` | 数据包快照 | 5.0 件 | 4.34 |

**那是错数，不是缺数。** 已改成留 `None`，让 `daychart.js` 的
`baseline != null` 守卫把整行藏掉。空值和 0 必须显示成两件事。

顺带记一条，将来真要做这类检查时用得上 —— **别拿高量对象当检查对象**：

| 日均 `p50` | 子体数 | 舍入半件的相对误差 |
| --- | --- | --- |
| < 2 件 | **145** | 大于 ±25% |
| 2 ~ 5 件 | **95** | ±12.5% ~ ±16.7% |
| 5 ~ 10 件 | 58 | ±5% ~ ±10% |

342 个里 **240 个（70%）日均低于 5 件**，而 `B0B3LM36WB` 落在 13~33 件。
在它身上试一条 ±5% 的误差线永远试不出问题，换到那 240 个上会天天误报。
真要定容差时写成「差 5%、或者差半件，按宽的算」，并挑一个日均不到 5 件的对象验。

### R7 置信度不需要给两份

现在载荷里 `demand.confidence_label` 与 `forecast_judgment.confidence` 都是 `中`，
`confidence_reason` 逐字相同。页面上因此出现「预测置信度 中」和「判断置信度 中」两处同值。

**这是页面侧要改的（删掉一处）**，写在这里只为说明：Agent 侧一份就够，不必分两个字段。

## 4. 代价

拆段会让**总时长上升** —— 每段都要重发上下文。107 秒可能变成 120~140 秒。

这是用总时长换节奏。判断值不值得由 Agent 侧衡量并回话：如果拆 4 段后总时长涨过 150 秒，可能要连带考虑更细的粒度（每段更小、上下文更短）或者换更快的模型。

**演示只需现场跑几个对象，不是全量 342 个**，所以总时长不是设计约束，观感才是。

---

## 5. 验收

拆段落地后，页面这边按这五条验：

1. 运行中每 1~3 秒有一次可见变化，且变化对应真完成的一步
2. 任一单步不超过 25 秒
3. 强行中断 Agent，run 行留在「在跑」或转「失败」，页面不显示半截结果
4. 每步 `duration_ms` 之和与墙钟时长同一量级（不再是 5.7ms 对 107 秒）

第 5 条原为「`baseline_units` 全部有值、因子乘回基线能重建 `p50`」，
按 R6 的决定**撤下**：这一版不判断数字对不对得上。
