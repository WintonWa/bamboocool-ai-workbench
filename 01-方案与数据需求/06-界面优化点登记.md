## 0. 这一页的使用者假设

用这个工作台的是**对自己产品非常熟悉的运营**。他不需要页面告诉他
这个 ASIN 是什么品类、什么尺码、谁负责——他早就知道。

由此得出一条贯穿性原则：

> 身份类字段不占第一屏的黄金位置，只保留定位所必需的最小集；
> 其余身份字段收进按需展开的入口。判断结论和风险占主位。

这条原则是下面 O1/O3 的共同依据，也应该用来审查后续新增的任何板块：
**新字段进第一屏之前，先问运营是不是本来就知道。**

## O1 产品身份信息收进按钮（本版不做）

**现状**：页面标题下面一整行平铺七个字段——
父体、款号、组合、尺码、SKU、店铺、负责人、盘点基准日。
在 1280 宽的窗口下这行会折成两行，把结论卡片往下推。

**要改成什么**：

- 标题行只留三样：**子 ASIN**、**括号内的中文昵称**、**父 ASIN**
- 其余字段收进一个按钮（悬停或点击展开一个小面板）
- 面板里可以顺带做「修改产品信息」的入口——运营发现昵称/负责人
  写错了能就地改

**为什么**：熟悉产品的运营看一眼子 ASIN 就知道是什么货，
中文昵称是为了不用背 ASIN，父 ASIN 是为了知道自己在哪一族里。
剩下五个字段是**查证时才需要**的，属于按需信息。

**本版不做**：用户明确要求这版先不做。
**触发条件**：等第一屏的信息层级定稿后一起做，因为它和「结论占主位」
是同一个动作的两面。「修改产品信息」还需要先定写回路径——
当前数据层是**只读**打开 SQLite，没有写入通道，这是真约束不是借口。

量级不同，单独分节。

## R1 需求预测：从页面公式改为读预测 Agent 的结果

**决策日** 2026-08-30 · **技术契约** 见 `07-预测Agent接口契约.md`

### 变更内容

需求预测**不在页面上算了**。原来页面自己跑一条公式链：

```
六个滚动窗口日均 → 按权重加权成基线日均 → 乘趋势系数（原始→限幅→折减）
→ 得预测日均 → 乘天数得未来累计
```

这条链整段废除。改由一个**预测 Agent** 离线跑，把结果写进独立的 SQLite，
工作台读表。

### 为什么改

原来那条公式链的问题在讨论中暴露得很具体（以 B0GKFMB38P 为例）：

- 14 天和 30 天两个窗口都被 7 月的销量尖峰灌满，而它们合占 0.50 的基线权重，
  等于**一半的基线压在含活动的窗口上**
- 趋势系数原始值 0.216（近 7 天比 30 天均值低 78%）先被下限 0.5 截住、
  再被强度 0.5 折减成 0.75，一个「砍 78%」的信号最后只表达成「降 25%」
- 结果预测 6.4 件/天，而该对象近 7 天的真实速度是 3.3 件/天，**高了 1.8 倍**
- 这个偏差一路传到覆盖天数、断货日、缺口量，最终污染风险结论

公式没法自己知道「那个尖峰是活动造成的、不会重复」。
**判断历史哪一段该采信、活动影响多大、生命周期在哪一段，这是逐例判断，
不是加权平均能做的事。**

### 切分：Agent 出判断，工作台出算术（B 方案）

| 谁做 | 内容 |
| --- | --- |
| **Agent** | 未来 90 天逐日销量预测 + 预测区间 + 最关键的调整项及依据 |
| **工作台** | 逐日库存余额、覆盖天数、安全线突破日、预计断货日、缺口量、超量件数、最晚补货日、建议补货量、承接能力、五类风险 |

考虑过让 Agent 一路算到结论（警戒日/断货日/补货量都由它出，页面纯呈现），
没采用，两条理由：

1. **保住可摆弄。** 「改参数立刻重算」是这个 Demo 的核心要求。
   投影是确定性算术，留在页面就能让安全库存天数、入库延迟、
   各类阈值继续在参数面板上调并立刻生效；搬进 Agent 就等于让一次离线运行
   冻结一堆本该随手能试的假设。
2. **预测区间才用得上。** Agent 给 `lower / forecast / upper` 三条需求线，
   页面各跑一遍投影，断货日就是一个**区间**（悲观最早哪天断、基准哪天断）。
   投影在 Agent 里离线跑只能给一个数，区间信息在那一步就被压掉了。

### 运行模型：按对象各自的新鲜度

Agent 是常规性任务，不是每个对象每天都跑：

- 全盘每周固定跑一次
- 重点对象、或运营自己筛出来的，可以当天再跑一次直接更新
- 尾部对象一周一次

每次运行记录**运行日**和从那天起的 90 天预估。于是页面上出现两个时间锚点：
**数据基准日**（库存与历史截止日）和**预测运行日**（每个对象可以不同）。

**汇总口径**：按每个对象最新一次运行汇总，不做批次对齐。

**新鲜度不作为告警。** 依据是业务判断：运营不去分析的对象，
本身就说明它不重要或量小。所以页面只客观显示「预估更新于 X 日 · 周跑」，
不涂红、不排进异常。**旧预估是一个关于重要性的信号，不是错误状态。**

唯一要处理的组合：尾部对象预估过旧、而它现在触了库存不足——
这时旧预估会低报严重度，页面给一个可点的「建议重跑」动作入口。（未定）

### 页面的增删

**删**：`build_demand` 整条公式链；参数面板 10 个需求预测参数
（7/14/30/60/90 天窗口权重、趋势强度、预测天数、活动系数、活动天数、活动起始偏移）。

**留**：投影、库龄、仓储费、五类风险、承接能力全部保留，只把需求输入换源；
参数面板保留阈值类与承接类（安全库存天数、目标覆盖、消化上限、入库延迟、
可用率下限、181+ 占比、费销比、费毛利比、费率）。

**加**：`lib/forecast.py` 挂载预测库、取最新运行；投影跑三遍出断货日区间。

## R2 「销量与需求」板块改为逐日柱状图

**决策日** 2026-08-30 · **参考来源** 见本节末「参考实地读取记录」

原来是六行滚动窗口表 + 右侧预测指标列表。改成**以日为单位的柱状图**，
横轴一根轴贯穿历史与未来。本质是把运营原来手工维护的**产品跟进表**自动化并放进图里
——跟进表是按日记录产品数据的人工台账（销量 / 利润 / 销售额 / 广告花费），
所以字段口径要对着跟进表来，不要另起一套。

### R2.1 按数据性质分四种画法（核心）

这是参考工具最值得抄的一条。不是配色，是**同一张图里不同性质的数据用不同画法**：

| 数据性质 | 画法 | 我们这张图对应什么 |
| --- | --- | --- |
| **量**（每天一个数） | 柱，可堆叠 | 逐日销量（历史实际 + 未来预测） |
| **连续指标** | 折线 | 价格、转化率、流量（按需开启） |
| **有数值的状态** | 横向段，落在自己的值轴上，值变了出台阶 | 价格（促销期降价形成台阶） |
| **无数值的状态** | 横向段，钉在顶部固定高度的泳道 | BD 期、Coupon 期、广告加投期 |
| **点事件** | 散点，符号区分（● 圆点 / ★ 星） | 补货到仓、改标题、改主图 |

**关键**：点事件与状态区间必须分开处理，且各占自己的 y 高度，
所以同一天多个事件（BD 叠 Coupon）天然错开，不需要合并也不会打架。

**这里推翻了本文档早期的一个设想**：原先写的是「在柱子上叠标记」。
那是错的——BD 和 Coupon 有起止日，是**区间**不是点，必须画成横条；
补货到仓、改标题才是点事件。混为一谈会让"这个活动持续了几天"这个信息消失。

**缺货日与异常日不走事件泳道**，因为它们说的不是"这天发生了什么"，
而是"**这天的柱子本身不可信**"。所以要改柱子自己的样式（灰掉 / 描边 / 斜纹），
不能另开一条泳道。否则运营会把断货造成的低销量误读成需求下降。

### R2.2b 事件泳道的实现机制（实测，直接照做）

参考工具主图有 **7 根 y 轴，全部 `show: false`**，各管一类：

| 轴 | 名字 | 配置 | 管什么 |
| --- | --- | --- | --- |
| 0 | `trafficScore` | value | 柱（量） |
| **1** | **`bestSellerDiscountDiff`** | **value，`min:0 max:17`** | **事件泳道** |
| 2 | `price` | value | 价格台阶 |
| 3 | `stars` | value | 评分 |
| 4 | `ratings` | value | 评论数 |
| 5 | `rootCategory` | value，**`inverse: true`** | 大类排名 |
| 6 | `category` | value，**`inverse: true`** | 小类排名 |

**泳道不是另一张图，是同一个 grid 里的一根隐藏轴。** 轴 1 固定 `min:0 max:17`，
所有事件标记（Best Seller 徽章条、折扣状态条、各类 diff 点事件）都挂在这根轴上，
按整数 y 值分层 —— 17 个层位。这就是"多事件同天不打架"的全部机制：
**给每类事件分配一个固定的整数 y，轴范围固定，于是层位永不漂移。**

`grid: {top: "15%", bottom: 60, left/right: "2%"}` —— 顶部留 15% 高度给泳道，
底部留 60px 给 dataZoom 和轴标签。

排名轴用 `inverse: true`，因为排名 1 比 100 好，轴必须反转。
我们的销量没有这个需求，但如果以后加排名类指标要记得。

**另一个直接可用的做法：series 的 data 用对象而不是裸数字。**

```
data: [{ value: 6418, ratio: 0.9919, asinsTraffic: [...] }, ...]
```

tooltip 里那个 `(99.75%)` 就是直接读 `ratio`，不是现算的。
我们可以照做——柱子的 data 挂上 `{value, 利润, 广告花费, 价格, 是否缺货, 是否异常, 当天事件}`，
tooltip formatter 直接读，不用回查另一份数据结构。

### R2.3 Tooltip 规范（整套照搬参考工具）

参考工具的实际形态：

```
2026-07-12 星期日（美西时间）
综合流量得分:              6,759
● 自然流量得分      6,728 (99.54%)
● 广告流量得分         31 (0.46%)
● Best Seller       in Candle Lamps
● 大类BSR[Home & Kitchen]      51
● Deal($)                    9.99
  划线价格                  19.99   ← 删除线渲染
● Promotion         Buy 2, Save 5%
```

五条必须照做：

1. **表头带星期。** `2026-07-12 星期日`。Agent 要考虑星期规律，看图的人也得能一眼
   看出周末，只给日期读不出周节奏。
2. **表头带时区声明。** `（美西时间）`。亚马逊数据是美西口径，不声明会和国内运营的
   日期认知错一天。
3. **只显示当天有值的行，不是固定行数。** 实测对比：07-09 那天 tooltip 没有
   Best Seller 这行，07-12 有。固定列出全部序列会让大部分行是空的。
4. **合计在最前，成分带绝对值 + 占比。**
5. **数据语义直接变成视觉编码。** 划线价用删除线渲染。我们对应的是：
   缺货日的销量数字要标出"非真实需求"。

我们的 tooltip 内容（历史侧）= 产品跟进表那一行：
销量 / 销售额 / 利润 / 广告花费 / 价格 / 流量 / 转化率，加当天的事件。

### R2.4 悬停与点击是两件事

参考工具图底部有一行提示文字：**`点击柱子诊断流量`**。

所以是两级交互：**悬停出当天事实，点击进当天的诊断。**

映射到我们：

| 动作 | 出什么 |
| --- | --- |
| 悬停某天 | 该天的全部指标（跟进表一行）+ 当天事件 |
| 点击某天（历史侧） | 这天为什么是这个数——事件归因、是否缺货扭曲、是否异常 |
| 点击某天（未来侧） | Agent 的调整项及依据（`fact_forecast_factor`） |

这跟原先「点某天出那天全部指标」略有不同：把**看数**和**分析**分成两个动作，
悬停不打断浏览，点击才进入解释。

### R2.6 技术选型（**已定：ECharts**）

当前 demo 的图全是手写 inline SVG（库龄柱、余额曲线、父体日线），
服务端零依赖（stdlib `http.server` + 只读 SQLite）。

新柱状图要做到：270 天日期轴（180 历史 + 90 预测，将来两年）、dataZoom 拖拽缩放、

**方案 A：引入 ECharts**（参考工具用的就是 ECharts + Element Plus）

- **不破坏"零依赖"约束** —— 那条约束说的是服务端；前端引一个静态 JS
  不需要 npm、不需要构建、不联网
- 收益：dataZoom / tooltip 命中检测 / legend 联动 三样都是现成的

**方案 B：继续手写 SVG**

- 代价：dataZoom 拖拽、tooltip 轴向命中检测、legend 联动重绘，
  三样各是独立工程量，且大概率达不到参考工具的手感
- 收益：保持前端零依赖

**已选 A（2026-08-30）。** `web/assets/echarts.min.js`，ECharts 5.5.1，
1,030,855 字节，Apache-2.0，从 jsDelivr 一次性下载后本地静态提供。
不需要 npm、不需要构建、运行时不联网。服务端仍是 stdlib `http.server` + 只读 sqlite3。

#### 坑 1：一个早返回把不相关的风险一起掐了

`build_risks` 开头是 `if not inventory.available or not projection.available: return risks`。
在页面自己算预测的年代 `projection` 永远可用，这行守卫从没起过作用。
改成读 Agent 之后，没有预测的对象 `projection` 不可用，于是**五类风险全部不判**——
包括库龄和仓储费，而这两类只看批次库龄和体积，跟需求毫无关系。

实测：库龄 46 → 0，仓储费 21 → 0。

改成按真实依赖拆分守卫后恢复：可用性 73、库龄 46、仓储费 21 与重构前**一个不差**，
只有库存不足与超量备货降到 2 / 2（因为只有 8 个对象有预测）。

**教训**：把一个曾经恒真的前置条件变成可假时，要把依赖它的东西一个个数过去，
不能假设原来的守卫写得刚好。

#### 坑 2：缺货那 25 天在图上是一片空白

缺货日销量通常是 0，**高度为 0 的柱子画不出任何东西**。
于是精心设计的「浅色 + 斜纹」柱样式无处可施，那一段成了空白，
读起来像「没有数据」——比读成需求下降更糟。

改成把连续缺货段单独画成**贯穿绘图区的背景色带**（`build_chart` 的 `stockout_bands`）。
柱子的斜纹样式保留，用于缺货期间仍有零星出单的日子。

这条不违反 R2.1「缺货不进事件泳道」：背景带不是泳道，
它表达的正是「这一段的柱子不可信」这个作用域。

---

#### 坑 3：事件泳道横穿柱子

第一版用**一根共享 y 轴**放泳道，靠拉大量程给泳道腾地方。
结果泳道值 5（BD）在量程 `-0.6~11.5` 下落在 46% 高度，红色横条正好压在 30 件的柱子上。

改成**上下两个 grid**：上面一条窄带专放泳道，下面是主图。
物理分开，不需要靠算量程维持互不干扰。
参考工具用一根轴能成立，是因为它的柱轴留了头部空间、柱子只用到下半部；
我们的柱轴是自动量程，柱子会顶到顶，所以必须分 grid。

泳道带高度按**所有可能的泳道数**给（7 × 9px），不按当前对象用到的条数给：
同一类事件在不同子体上必须落在同一高度。
但一个事件都没有时整条收起——342 个子体里 334 个没有事件，那是常见情况。

#### 坑 4：图例色块和图上的标记不是一个颜色

颜色写在 data 项的 `itemStyle` 和 `custom` 的 `renderItem` 里，
而**图例读的是 series 级颜色**，于是图例给了默认调色板的蓝、绿、黄，
和图上的深灰、灰、红完全对不上。

每条序列补显式 `color` 后一致。

三套测试当时全绿。四个都是**看屏幕**发现的：

所以这次把它们变成了门禁，且门禁必须打在**真的有那个特征的对象上**：
第一版门禁跑在一个既无事件也无缺货的子体上，
报「泳道 0 条 / 缺货柱 0 根」还照样打勾——**没有检查对象的门禁比没有门禁更糟**。

### R2.10 迁移到 v0.3.0 数据包（2026-08-30）

用户重建了 v0.3.0：489MB、44 张表、历史 730 天、**342 个子体全部有预测**，
并补上了 v0.2.2 时缺的未来计划（促销 / 价格 / 广告 / 货件）。
上一轮那条「预测覆盖只有 8 个对象」的待决因此直接消失。

#### 决策：口径统一按逐日源（A 方案）

客户自己的两个来源互相矛盾 —— 他的子体级 `fact_sales_window` 加不回他自己的
父体逐日（父体近 30 天比子体窗口合计低 1–4%，`B0GQXK2Q58` 低 19%）。
数据包把分配锚在父体上（父体级差异精确为 0），子体级因此中位偏差 **20.3%**、
p90 75%，只有 14% 的子体在 5% 以内。

**页面统一读逐日**：侧栏那列 30 天销量、经营框、图上的柱子同源，
柱子加起来永远等于表头那个数。代价是子体级那个数从「客户真值」变成
「父体真值的分配值」，父体级仍精确对齐客户真值。

#### 决策：v0.3.0 当作「最新一次跑的结果」的静态快照

不做多次运行取最新、不做新鲜度、不做回填/重跑通路。数据包只有一行全局运行记录
（`run_mode: golden_only`），每个对象的运行日相同，「预估更新于 X 天前」对 342 个
对象是同一个常量，放上去只是噪音。那一格换成 **选用模型 + 56 天回测偏差**，
那才是逐子体不同、且运营本来不知道的信息。

契约（`07-预测Agent接口契约.md`）里的 `created_at` 分先后与按对象各自节奏运行
**保持不变**，等真实 Agent 跑起来再恢复那套机制。

#### 决策：不使用 `bridge_demo_child_route`

数据包提供了一张路由表，把 337/342 个子体改指到 5 个黄金对象。核实后不用：
每个子体**确实有自己的预测**（90 天序列去重 266/342，历史 329/342），
被路由到同一黄金对象的两个子体自身预测是 2,325 和 3,324，而路由目标是 4,933。
那张表是纯展示层覆盖，用了就是把 4,933 挂在一个自身只有 2,325 的子体名下 ——
而运营对自己产品很熟。

**代价要知道**：黄金五个是最好的一档。全盘 `confidence_score` 中位 0.617
（黄金五个 0.86–0.91），回测 WAPE 中位 **38.3%**、p90 63%、最大 167%
（黄金五个 8.6–13.9%），61% 的对象选用 `lifecycle_damped` 兜底模型。
所以置信度分布是 高 7% / 中 34% / 低 58%，演示时点到尾部对象会诚实显示「置信度低」。

---

#### 派生缓存：为什么多一层

源包逐日表主键是 `(date, child_asin)` —— date 在前。板块按子体读，用不上前缀，
SQLite 退化成跳扫 249,660 行：**65–128 ms / 表 / 子体**，六张表一个板块 ~700ms，
全量评估 342 个要四分钟。带了 `(child_asin, date)` 索引的两张表同样查询是
**0.3–0.9 ms**，差约 130 倍 —— 所以问题在索引不在数据。

源包是版本化产物，不改。改在 demo 侧建一张窄宽表
`derived/chart_cache.sqlite`（36MB，2.5s 构建，删目录即干净），
只装图表真正渲染的列，按 `(child_asin, date)` 建。查询回到 0.8ms，
全盘评估 3.4s（10ms/子体）。

**给数据方的建议**：若下一版给逐日表加 `(child_asin, date)` 索引，
这层缓存就可以整个删掉，页面直接读源包。

事件区间**不能按 `promotion_id` 聚合**，两边的 id 粒度都对不上区间语义：
未来 Coupon 是一天一个 id（`PLAN-CP-23/24/25` 连着三天）→ 按 id 会切成三段一天；
历史 Coupon 是 6 个 id 摊在 5,343 行上跨多个子体和多个不相邻时段 →
按 id 会把不相邻的两段并成一条超长区间。
正确规则是**同一子体 + 同一类型 + 日期相邻才合并**，断开就切段。

#### 坑 5：对照基线第一次跑就抓到一个缺失的输入

保留数据包的 `fact_child_inventory_decision` 作对照基线（不作页面输出，
页面仍自己算以保住参数可调）。第一次比对：断货日只有 **60%** 一致，
而且 116 个差异**全是同一个方向** —— 页面说会断货，数据包说不断。
一致的方向指向缺输入，不是噪音。

根因：页面只把「待调仓 + 入库中」算作到货，把在途排除了 ——
因为 v0.2.2 时代出货 ETA 只到款号级，分不到子体。
v0.3.0 给了 `plan_child_supply_event`：684 笔、覆盖全部 342 个子体、139,446 件、
带子体级 ETA。那个限制没了。

约定是**读出来的不是猜的**：342 笔 confirmed 到货全部落在 `eta_earliest`，
落在 `eta_latest` 的 0 笔；`base` 情景合计 100,751 = 恰好两个 confirmed 分档之和，
`improvement` 139,446 = confirmed + planned。所以到货日取 `eta_earliest`，
只计 `event_status=confirmed`。

接上之后一致率 **60% → 80%**，差异较大 116 → 36，方向变成双向。

保留一处口径差不追平：页面还会在 `internal_release_lag_days` 之后释放
待调仓/入库中，数据包完全不算这部分。那批货是真的在 FBA 网络里、真的会转可售，
为了让数字对上而删掉它会让页面更不准，不是更准。

#### 坑 6：接上到货之后，「库存不足」的判据失效了

原判据是 `覆盖天数 < 安全天数`，而覆盖天数 =（可售 + 窗口内已确认到货）÷ 预估日均。
**分子里的到货没有时间概念** —— 一批 2026-09-12 才到的货被当成今天就在手上。
v0.2.2 时「已确认到货」只是那点待调仓/入库中，影响不大；接入子体级货件后
覆盖天数中位数变成 118 天、最小 23.5 天，几乎没有对象低于 14/60 天的安全线，
这条判据命中只剩 **5 个**，等于这类风险实质消失。

改成**按逐日投影判**（会断货 或 会破安全线）—— 投影尊重时间。
命中 **171 个**，与数据包自己判定需要补货的 168 个基本一致。
覆盖天数保留为展示指标，不再作为判据。严重度改按「多快出事」。

#### 坑 7：泳道颜色全灰

颜色表的键写成小写 `bd`/`coupon`，而 v0.3.0 的 `event_type` 是
`BD`/`LD`/`Coupon`/`PriceDiscount`（大写），于是全部落到 fallback 灰 ——
BD 和 Coupon 在图上一个颜色。**彩色在这张图上唯一的职责就是区分事件类型，
一灰就等于没做。** 已加门禁：同一对象的各泳道颜色必须两两不同。

#### 顺带发现的数据问题（不挡页面，但会被看见）

`fact_child_inventory_daily.closing_fba_sellable` 两端正常、中间失真。
`B0B3LWGP36`：2024-08-04 是 5,794，2025-02-04 涨到 **529,628**，基准日回到 5,897。
全表最大 534,328，而全部子体真实可售合计只有 145,100。
数据包的 `historical_inventory_balance` 门禁只验
`期初 + 到货 − 销量 = 期末` 的算术自洽，验不出量级荒谬。
页面只用该表的 `stockout_flag`，不受影响；但同表的 `coverage_days` 也是从它派生的。

#### 还缺的一项

**逐日毛利没有。** 所有逐日表都不含 profit/margin/cost，所以 tooltip 里没有毛利行。
月级有（`fact_child_sales_monthly.order_gross_profit / order_gross_margin`），
所以经营框和费毛利比不受影响。要上逐日需要数据方在
`fact_child_sales_daily` 增列，或给出可用于逐日的单位成本
（`fact_unit_economics.unit_cost` 有 162 个子体是 unknown，现算不出来）。

**改了什么** 「批次消耗方式 = FIFO」原来是参数面板的第 11 项，标着 `locked: true`。
迁移后参数面板只剩 10 项，这一项不再出现在面板里，改为由
`/api/inventory/meta` 的 `depletion` 字段带出，在库龄板块处就地说明。

**为什么** 它 `locked=True`、恒为 FIFO，切换需要重建数据层（敏感性已知：181+ 相差 2.65 倍）。
把一个调不动的东西放进"可调参数"面板，操作者会以为能调 —— 那是误导。
它是事实，不是控制项，所以应该出现在它影响的那个板块旁边，而不是在参数面板里。

**副作用** 无。这一项本来就不可调，面板上少一项，操作者少一次无效尝试。

**验证** 参数面板 10 项，`meta.depletion.method = FIFO`、`locked = true`、
带一句中文说明。外壳门禁 G6（参数带前缀且越界被夹紧）通过。

## R3.4 字体统一到设计图（去掉等宽）

**时间** 2026-08-31 · 用户：「我需要所有的字体都是我截图那种的」

**问题** 用户对比设计图与工作台，指出字体不一样。查出来是**数字用了等宽字体**：
`.big` 等 14 处声明走 `var(--mono)`（本机 = SF Mono）。等宽字体为了让 `1`
填满字身会画底衬线，所以 `1` 和 `6` 几乎同宽；设计图里 `1` 只有 `6` 的一半多。

**这不是迁移引入的** —— 18810 版的 `app.css` 原本就这样。上一轮「逐像素复现设计图」
只比了**字号**（字形高度），从没比过**字族**，所以这个差异一直没被发现。

**怎么定的字族** 字形宽度比值指纹（比值与缩放无关，绝对 px 会受缩放影响）：
SF Pro Text 偏差 0.0220 / Helvetica 0.0390 / Geneva 0.0523 /
Helvetica Neue 0.0733 / SF Mono 0.1115。**设计图就是 SF Pro。**

**改了什么**
- `inventory.css` 生效规则里 `var(--mono)` 14 处 → 0 处，全部走 `var(--sans)`
- 需要列对齐处补 `font-variant-numeric: tabular-nums`（共 14 处）
- 外壳 `tokens.css` 的 `--sans` 把 `-apple-system` 提到最前。本机没装
  IBM Plex Sans 与 Inter，原来靠连 miss 两次才落到 SF Pro，匹配是偶然的；
  **本机渲染结果与改前一致**，对其他四个模块零视觉影响。
  这反转了同日的口径一，退回只需换回那一行
- `daychart.js` 的 `FONT` 同步（canvas 拿不到 CSS 变量，两处必须一起改）

**代价** ASIN 这类字母数字混排失去逐位竖向对齐。用户明确要求统一字形，已接受。

**验证** 整页（侧栏 + 主体）逐节点读 `getComputedStyle`：**只出现一个字族**，
零等宽残留，侧栏 342 行零截断，零溢出。新增 3 条门禁：CSS 不用等宽 /
列对齐声明 ≥10 处 / 图表字体栈与 `--sans` 首项一致。

## R3.5 修「销量与需求」交互全失效（迁移引入）

**时间** 2026-08-31 · 用户手点发现：拖不了时间条、悬停看不到当天信息、点击看不了状态

**根因** `ReferenceError: n0/n1/n2 is not defined`。18810 版里 `daychart.js` 是**普通脚本**，
与 `app.js` 同处全局作用域，直接用它定义的数字格式化函数。迁移时改成 ES module，
作用域隔离，那三个函数搬进了 `util.js` 却**没给 `daychart.js` 补 import**。

三处交互挂在同一个原因上：`dayTooltip()` 用 `n1/n2`（悬停），`dayDetail()` 用 `n0/n1`（点击）。
时间条本身没坏，但每次移动都要重画 tooltip，一碰就抛错，表现为整块「动不了」。

**为什么加载时不报错** ES module 里未定义标识符不是静态错误，只在**执行到那一行**才抛。
文件能正常 import、导出名正确、`setOption` 也跑通 —— 只有鼠标真碰上去才炸。

**门禁为什么全绿** `test_render.mjs` 的 ECharts 桩把回调空吞了：
`on: () => {}`、`getZr: () => ({ on: () => {} })`，`setOption` 只把配置存下来。
门禁验的是**配置的形状**（泳道几条 / 颜色互不相同 / 轴从 0 起 / 序列等长），
`tooltip.formatter` 和 click 处理函数**一次都没被调用过**。

**修法（两件）**

1. `daychart.js` 顶部补 `import { n0, n1, n2 } from './util.js';`
2. 桩改成记录回调，门禁真调一次：
   - `on` / `getZr().on` 把处理函数存进表
   - 补 `containPixel: () => true` 与 `convertFromPixel`，否则 zrender 层按 x 反查列
     会在第一个判断就 return，等于没测到
   - 新增 3 条：tooltip 格式化真调不抛错且产出 >40 字符 / 点击真写出当天详情 /
     时间条 slider+inside 都在

**反证** 临时移除那行 import，两条新门禁立刻变红并指名 `n0 is not defined`，加回即绿。
门禁数 57 → 60。

**教训** 「能 import + 导出名对 + 配置结构对」三条全绿，不等于交互活着。
桩把回调吞掉的门禁，验的是配置不是行为。

## R3.6 主图改正方形并与右侧信息齐平

**时间** 2026-08-31 · 用户：「主图可以是一个正方形，最好能把右侧的信息从高度上覆盖掉，
它们是齐平的。然后下面那个板块可以往上移，中间空隙有点大」

**改了什么** 主图 92×115 竖长方 → 正方形，边长 = 右侧信息块高度（实测 166×166，
内容短的对象自动 129×129）；组合内容底到下个板块由 31px 收到 10px。

**「空隙」不在板块之间** —— 身份块底到板块顶本来就是 0px。那 31px 是右列最后一块
`.specwide` 作为 `<dl>` 吃到的浏览器默认 `margin: 1em 0`（13px），
加 `.idblock` 的 `padding-bottom: 18px`。

**正方形无法纯 CSS 实现**，边长由 JS 量右列高度得出（`page-detail.js` 的 `sizeIdSquare`）：
- `align-items:stretch` + `aspect-ratio:1` 实测宽度恒为 **0** ——
  flex 主轴宽度要在交叉轴高度确定之前算完，`stretch` 给的高度来得太晚
- 去掉固定尺寸后图片天然尺寸 774×972 反向撑出容器，整块变成 **774×774**，
  所以 `.idimg` 必须绝对定位、不参与布局
- 容器用 `flex-start` 而非 `stretch`，否则「JS 按右列设方图 → 方图撑行高 →
  右列被拉高」会自激
- `ResizeObserver` 盯 `.idmain`，标题换行或组合内容排数变化时自动跟上

**验证** 三个不同内容高度的对象逐个量：正方、齐平差 0、空隙 10px。
