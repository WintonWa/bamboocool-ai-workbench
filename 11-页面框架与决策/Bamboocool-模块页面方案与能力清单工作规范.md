# Bamboocool 模块页面方案与能力清单工作规范

更新时间：2026-08-13

适用范围：产品库存、关键词、竞品、广告、数据中心及后续新增业务模块

参考成果：

- `bamboocool 产品方案/Bamboocool-产品库存模块三页架构方案.md`
- `bamboocool 产品方案/Bamboocool-产品库存模块必备逻辑与能力清单.md`

## 1. 规范目的

本规范用于指导不同工作窗口按照统一方法完成 Bamboocool 各业务模块的方案设计，并稳定产出两类结论文档：

1. **模块页面架构方案**：说明模块由哪些页面组成、每个页面包含哪些板块、每个看板展示什么业务关系，以及页面之间如何流转；
2. **模块必备逻辑与能力清单**：说明为了生成页面结果，系统需要对原始数据和过程数据完成哪些归并、计算、预测与评价。

两类文档分别回答两个问题：

```text
页面架构方案：运营最终看见什么，如何完成查看与下钻？
能力清单：这些页面结果需要通过哪些业务处理逻辑生成？
```

## 2. 两类文档的推导关系

两类文档来自同一套业务事实，但使用不同的推导方向。

### 2.1 页面架构的推导方向

```mermaid
flowchart LR
    A[业务事实与运营任务] --> B[确定最小业务对象]
    B --> C[确定系统需要形成的业务结果]
    C --> D[按照运营查看任务划分页面]
    D --> E[按照业务关系划分看板]
    E --> F[形成页面架构方案]
```

核心问题是：

> 运营围绕什么对象工作，需要先看什么、再看什么，最终进入哪里完成判断？

### 2.2 能力清单的推导方向

```mermaid
flowchart LR
    A[页面看板需要的业务结果] --> B[识别结果的计算来源]
    B --> C[还原中间处理逻辑]
    C --> D[识别原始数据与过程数据]
    D --> E[合并为完整业务能力]
    E --> F[形成能力清单]
```

核心问题是：

> 这个看板显示的结果，是通过什么规则处理哪些数据得到的？

### 2.3 两类文档的完整关系

```text
业务事实
   ↓
业务对象与运营任务
   ↓
页面架构方案
   ↓ 反向追问每个看板需要什么结果
逻辑与能力清单
   ↓ 继续拆解数据依赖
数据表、字段、来源和计算关系
```

## 3. 资料读取与事实优先级

### 3.1 开始前必须读取

每个工作窗口开始设计前，至少需要读取：

1. 项目根目录 `AGENTS.md`；
2. `01-当前页面框架与决策/00-完整项目上下文.md`；
3. 与当前模块相关的页面决策、架构记录和访谈梳理；
4. `04-原始访谈与会议/` 中与当前模块相关的原始会议记录；
5. `05-客户提供资料/` 和 `数据源/` 中与当前模块相关的文件；
6. V4.1.2 Demo 中对应页面、数据结构和交互；
7. 已经完成的其他模块方案，理解跨模块输入输出关系。

任务涉及页面结构、看板或 UI 时，同时读取 Organic Soft-Tech 设计规范及前端子项目 `AGENTS.md`。

### 3.2 事实优先级

发生冲突时按照以下优先级判断：

1. 用户当前明确确认的业务决策；
2. 客户原始会议记录和客户提供的业务规则；
3. 当前已确认的项目决策文档；
4. 客户提供的真实表格、字段和现有计算；
5. V4.1.2 Demo 已形成的成熟页面逻辑；
6. V5 及历史版本中的探索性方案；
7. 通用产品经验和设计推断。

### 3.3 资料使用原则

- 会议记录用于确认客户真正关心的问题和业务规则；
- 客户表格用于确认当前数据、现有计算和业务对象；
- Demo 用于理解已经表达过的页面逻辑和交互方式；
- Demo 中的模拟数据、占位文案和推导规则不作为客户事实；
- V4.1.2 是当前成熟输出基线，V5 用于参考尚未完成的探索方向；
- 页面设计规范负责视觉和组件约束，不覆盖业务事实。

## 4. 开始设计前需要先确定的四件事

### 4.1 最小业务对象

先确定系统最终围绕什么对象计算和保存结果。

示例：

- 产品库存模块：子 ASIN；
- 关键词模块：关键词与产品的绑定关系，或关键词本身；
- 竞品模块：竞品父体、竞品子 ASIN 或竞品产品族；
- 广告模块：广告对象与所推广产品的组合关系。

页面可以在更高层级汇总，但底层判断必须落到明确、稳定的最小业务对象。

### 4.2 运营任务

明确运营进入该模块时要完成哪些不同任务。例如：

- 发现异常；
- 查看全部对象；
- 分析单一对象；
- 理解某类变化；
- 将结果交给下游页面继续判断。

一个页面应当服务于一个清晰的主要任务。任务差异较大时，拆成不同页面或不同层级。

### 4.3 标准业务结果

明确系统为每个最小业务对象最终生成什么结果。

标准结果通常包括：

- 对象当前状态；
- 核心计算结果；
- 异常或机会点；
- 严重程度或优先级；
- 形成结果的主要依据；
- 可供其他模块调用的结构化结果。

### 4.4 上下游关系

明确当前模块：

- 使用哪些上游事实或业务结果；
- 向哪些下游页面输出结果；
- 哪些结果由当前模块负责计算；
- 哪些结果只在当前模块中引用。

## 5. 页面架构的思考规范

### 5.1 同时建立两条顺序

#### 系统生成顺序

从最小业务对象开始生成计算结果，再向上汇总到总览页面。

```text
原始数据 → 对象数据整合 → 业务计算 → 标准对象结果 → 汇总页面
```

#### 运营查看顺序

从运营最常进入的页面开始，逐步查看问题、范围和详情。

```text
总览入口 → 分类或范围 → 单一对象详情
```

系统生成顺序和运营查看顺序可以不同，文档中需要分别说明。

### 5.2 页面划分标准

当两个区域满足以下任一情况时，考虑拆成不同页面：

- 服务不同运营任务；
- 使用不同的信息组织方式；
- 面向不同业务对象层级；
- 一个负责汇总发现，一个负责完整分析；
- 同页呈现会造成明显的信息密度或理解负担。

页面数量由业务任务决定，不机械复制产品库存模块的三页结构。

### 5.3 看板划分标准

每个看板应当展示一组完整的业务关系，而不是简单装载一批指标。

一个合格的看板说明需要回答：

1. 它分析什么对象或问题；
2. 它把哪些业务因素放在一起；
3. 它帮助运营理解什么结果；
4. 它与前后看板如何衔接。

例如：

> 库存承接看板把预计需求、当前可售库存和确认可用的后续库存放在同一逻辑中，帮助运营理解库存能够支撑多长时间，以及当前存在缺口还是余量。

这比“展示库存、销量、覆盖天数”更接近方案所需的表达。

### 5.4 不同问题允许使用不同模板

同一页面中的不同业务问题可以采用不同的信息组织模板。

例如库存不足、库龄和仓储费关注的关系不同，因此分别建立标准化风险模板，而不是强行使用同一套产品字段。

标准化的对象是“同类问题的表达结构”，不是整个页面所有内容的字段一致性。

## 6. 功能/能力的定义规范

### 6.1 什么属于功能/能力

功能/能力必须包含一个明确的数据转换过程：

```text
原始数据或过程数据
        ↓
按照业务规则进行归并、计算、预测或评价
        ↓
生成可以被页面或下游模块直接使用的结果
```

典型能力包括：

- 未来销量预测；
- 某个日期的可用库存计算；
- 仓储费用计算；
- 关键词价值评价；
- 竞品变化识别；
- 风险类型和严重程度计算；
- 不同对象层级的正确汇总。

### 6.2 什么属于能力内部步骤

数据清洗、时间对齐、去重、异常校验、参数匹配等内容，如果共同服务于一个完整结果，应当合并在对应能力内部。

只有当某个处理过程：

- 被多个后续能力共同调用；
- 有独立、稳定的业务输出；
- 可以单独解释其业务价值；

才适合作为一项独立能力。

### 6.3 什么属于页面呈现或交互

以下内容属于页面设计，不列为业务计算能力：

- 展示原始数据；
- 搜索、筛选和排序；
- 页面跳转和返回；
- 表格列、卡片字段和按钮；
- 展开、折叠、切换视图；
- 图表类型和视觉样式。

这些内容可以出现在页面架构方案中，但不进入能力清单。

### 6.4 能力合并标准

能力清单应当保持紧凑。通常一个模块形成约 6–12 项核心能力，具体数量由业务复杂度决定。

适合合并的情况：

- 多个步骤连续完成同一类业务结果；
- 输入高度重合，输出共同服务同一判断；
- 拆开后每项只能解释为技术处理步骤；
- 单独列出无法对应明确的页面或下游消费者。

适合分开的情况：

- 使用的业务规则明显不同；
- 输出结果可以被不同页面独立调用；
- 其中一项变化时不会必然改变另一项；
- 两项分别回答不同的业务问题。

## 7. 抽象程度规范

### 7.1 页面方案的合适颗粒度

页面方案需要细到“板块/看板级”，说明页面包含哪些部分以及各部分展示什么业务关系。

#### 过于抽象

> 页面包含风险汇总、数据聚合和异常提醒。

问题：无法判断看板具体分析什么，也无法指导后续功能设计。

#### 合适颗粒度

> 风险概览展示当前范围内各类风险的规模、严重程度和集中情况，既帮助运营理解整体风险版图，也作为进入分类风险看板的入口。

#### 过于落地

> 风险列表包含 ASIN、SKU、30天销量、FBA可售、AWD、覆盖天数、风险日期等九个字段，并使用红色标签展示等级。

问题：在方案阶段提前固化表头、字段和组件，限制后续页面设计。

### 7.2 能力清单的合适颗粒度

能力清单需要细到“一项完整业务转换”，说明处理目标、核心规则和标准输出。

#### 过于抽象

> 系统需要数据分析能力、AI判断能力和智能洞察能力。

问题：没有明确输入、处理逻辑和结果。

#### 合适颗粒度

> 未来销量预测将历史销量、近期趋势、季节性和已知活动按照预测规则组合，输出未来每日销量及累计需求，并根据实际销量持续校准。

#### 过度拆分

> 分别建立销量去重、时间对齐、异常值过滤、趋势计算、活动匹配、参数保存六项能力。

问题：把一个完整预测能力拆成技术步骤，导致能力清单冗长且失去业务含义。

### 7.3 判断抽象程度的三个问题

写完一个板块或能力后检查：

1. 产品经理能否据此继续拆下一层方案？
2. 开发能否理解系统最终需要生成什么业务结果？
3. 文案是否已经提前决定了具体字段、表头或组件？

前两个答案应为“能”，第三个答案应为“没有”。

```text

```

```markdown

更新时间：YYYY-MM-DD

```

### 9.3 每项能力必须说明

#### 能力目标

说明该能力解决什么业务计算问题。

#### 核心处理逻辑

说明系统将哪些类型的数据按照什么业务规则组合、计算、预测或评价。保持业务规则层面的表达，不提前进入数据库和技术实现。

#### 标准输出

说明该能力最终生成哪些可以被页面或其他模块直接使用的结果。

能力清单必须包含一张 Mermaid 能力链，明确：

- 各能力之间的先后依赖；
- 哪些能力共同形成标准对象结果；
- 标准结果如何进入页面或下游模块。

## 10. 两类文档的内容边界

### 10.1 页面架构方案负责

- 页面划分；
- 页面任务；
- 板块和看板；
- 每个看板展示的业务关系；
- 页面流转；
- 页面输出。

### 10.2 能力清单负责

- 数据归并；
- 业务计算；
- 趋势与预测；
- 状态和风险评价；
- 正确汇总；
- 标准结果生成；
- 结果保存与追溯。

### 10.3 后续数据设计负责

- 需要哪些数据表；
- 每张表有哪些字段；
- 字段来自哪里；
- 数据更新频率；
- 表与表之间如何关联；
- 具体计算公式和参数配置。

三个阶段保持连续，但不在同一份文档中混写。

## 11. 写作规范

### 11.1 使用正向方案表述

正文直接说明系统是什么、页面做什么、能力如何运行。

修改过程中的纠错内容转化为最终规则，不在正文保留讨论痕迹。例如直接写“风险看板按照风险类型建立对应模板”，而不是写“无需把所有风险放进同一张表”。

### 11.2 使用业务语言

优先使用运营能够理解的业务关系：

- “当前可售库存与销售消耗的关系”；
- “关键词需求、产品相关性和竞争程度”；
- “竞品价格、活动和位置变化”；
- “广告消耗与经营目标之间的偏差”。

避免用“指标聚合、智能洞察、异常汇总、跨页联动”等抽象产品术语替代真实业务内容。

### 11.3 控制细节层级

- 页面文档写到看板级；
- 能力文档写到完整业务转换级；
- 数据文档写到表和字段级；
- 原型或交互稿再确定表头、控件和视觉组件。

### 11.4 保留必要的流程结构

业务结果存在明显先后依赖时，使用 Mermaid 或简洁流程表达。流程图应当帮助读者理解“数据如何形成结果”或“运营如何完成任务”，不用于装饰。

### 11.5 避免方案自嗨

每个页面板块和每项能力都需要能够追溯到至少一个来源：

- 客户明确提出的问题；
- 客户当前已有的工作流程；
- 客户提供的数据和计算；
- 已确认的项目决策；
- 下游模块明确需要的输入。

## 12. 工作步骤

### 第一步：阅读和提取事实

从会议记录、客户资料、现有表格和 Demo 中提取：

- 用户是谁；
- 日常任务是什么；
- 当前如何完成；
- 核心业务对象是什么；
- 已经有哪些数据和计算；
- 当前最重要的问题是什么；
- 哪些结果需要交给其他模块。

### 第二步：建立业务对象和结果链

明确：

```text
原始数据 → 最小业务对象 → 中间业务结果 → 标准对象结果
```

### 第三步：形成页面架构草案

按照运营任务划分页面，并为每个页面确定：

- 页面目标；
- 页面板块；
- 看板展示关系；
- 下钻路径；
- 页面输出。

### 第四步：与用户确认页面架构

先确认页面边界和板块逻辑，再落成页面架构文档。

### 第五步：反推必备能力

针对每个看板追问：

1. 看板需要什么计算结果？
2. 结果由哪些原始数据或过程数据产生？
3. 中间需要经过什么规则处理？
4. 这个处理过程应当独立成能力，还是合并到更完整的能力中？

### 第六步：合并能力并建立依赖链

将属于同一完整业务结果的步骤合并，使每项能力都有清晰目标、处理逻辑和标准输出。

### 第七步：与用户确认能力清单

先确认能力数量、边界和颗粒度，再落成能力清单文档。

### 第八步：交叉校验两类文档

确保：

- 每个核心看板都有对应能力支持；
- 每项能力至少被一个页面或下游模块使用；
- 页面文档没有提前进入表和字段；
- 能力文档没有混入筛选、表头和组件；
- 两类文档使用相同的业务对象和结果口径。

## 15. 规范结论

各模块设计统一遵循以下主线：

```text
先理解业务，不从页面组件出发
        ↓
先确定业务对象与标准结果
        ↓
按运营任务形成页面架构
        ↓
从看板结果反推计算能力
        ↓
合并为少量完整业务能力
        ↓
再进入数据表、字段和实现设计
```

页面架构方案负责建立运营的查看逻辑，能力清单负责建立系统的计算逻辑。两者共同构成后续数据设计和页面落地的业务底板。
