# Bamboocool 亚马逊广告运营 AI 工作台｜完整项目上下文

更新时间：2026-08-03  
当前阶段：先把各页面的业务框架、判断逻辑和屏幕信息设计讨论清楚，再进入 UI、字段、阈值、接口和开发细节。

## 1. 当前项目范围

第一版必须遵守以下边界：

- 只面向一个确定品线 / 类目；
- 只面向一个确定运营，只有运营视角；
- 不做多品线、多运营、团队汇总、管理者视角和角色切换；
- 不先做通用 SaaS 平台，也不为远期跨品类迁移提前增加复杂抽象；
- AI 第一版只给判断和建议，不直接修改广告；
- 广告动作由运营人工执行；
- 第一版复盘只覆盖广告动作，先看 3 天，必要时补充 7 天；
- 关键词和竞品是证据层，不独立形成广告调整闭环。

旧材料中出现的多角色日报、跨品类模板、自动执行、一键改广告等内容，均不属于当前版本。

## 2. 核心业务闭环

当前已经确认的主链路是：

> 产品与库存判断 → 关键词和竞品分析佐证 → 广告决策 → 人工执行 → 3 / 7 天广告动作回溯

页面之间的关系：

- 产品与库存页先判断具体产品当前处境和承接能力；
- 关键词页说明市场需求、产品覆盖和位置等证据；
- 竞品页进一步验证竞争压力及其证据；
- 广告决策页综合产品、库存、关键词和竞品证据形成建议；
- 运营人工执行，并记录实际动作；
- 回溯页比较执行前后变化，继续形成下一步建议。

## 3. 当前讨论方式

用户说“讨论”时，先在聊天中把框架打磨清楚，不直接修改 Excel、PRD 或飞书。只有用户明确要求落文档时才写入。

每项功能优先拆清：

1. 使用场景；
2. 判断对象；
3. 输入数据；
4. 业务规则；
5. AI 输出；
6. 人工动作；
7. 复盘方式；
8. 异常边界；
9. 客户需提供的材料；
10. 当前状态：已确认、讨论方向、待确认或当前不做。

当前只讨论框架，不提前编造字段、算法、阈值和第三方插件能力。

### 3.1 从业务设计到前端实现的固定流程

项目不能从业务框架直接跳到前端组件。各页面进入正式 UI 和开发前，必须依次完成：

> 业务决策设计 → 全局信息设计原则 → 页面屏幕决策设计 → UI 与前端实现 → 真实任务验收

其中：

- 业务决策设计回答“运营需要判断什么、依据什么、边界是什么”；
- 全局信息设计原则规定所有页面共同遵守的工作台语法、组件选择、AI 角色和视觉约束；
- 页面屏幕决策设计回答“信息按什么顺序传达、哪些数据需要比较或建立关系、使用什么图表和交互”；
- UI 与前端实现只能在上述内容明确后落地，不能自行补充未确认的业务阈值、算法、字段或因果关系；
- Demo 和 AI 生成图片可以用于探索，但不能反向覆盖已经确认的业务和信息设计。

所有页面和前端 Agent 必须遵守：

- `Bamboocool-工作台全局信息设计原则.md`；
- 对应页面的“架构与决策记录”；
- 对应页面的“屏幕决策设计”。

## 4. 总览页最新结论

总览页分为四部分：

1. 运营信息展示；
2. 重要异常；
3. 执行建议；
4. 核心数据复制 / 简要周报。

### 4.1 运营信息展示

这一部分承接访谈中“怎么判断当前卖得好不好、平时关注什么”的逻辑，先给运营看结论和趋势，不做全量数据报表。

已经明确的经营判断方向：

- 销售额 / GMV 相对去年同期的增长；
- 利润率；
- 市场份额及其变化；
- 库存、资金占用、仓储和下单作为辅助信息。

需要注意：头部大类目的市场份额主要按月判断，不能把“总览每天打开”理解为所有指标都按日判断。页面需要明确每个结果的统计周期和比较周期。

### 4.2 异常与执行建议

总览页不独立创造异常和建议规则。先把产品库存、关键词、竞品和广告决策页面做清楚，再把这些页面产生的高优先级异常和待处理建议汇总到总览。

因此当前只确认“总览负责聚合和排序”，具体异常类型、优先级和建议标准后续再定。

### 4.3 核心数据复制 / 简要周报

总览页提供一个简要周报按钮：

- 自动生成一份简短的经营周报和基础分析；
- 用户可以直接复制；
- 第一版先做出模板，再和客户共创迭代；
- 当前不提前固定全部字段、篇幅和结论标准。

## 5. 产品与库存页：内容和排布

### 5.1 页面定位与分工

页面用于快速找产品、看状态和做判断，不是把所有产品数据平铺成一张大报表。

- 总览页回答“整体哪里值得关注”；
- 产品与库存页回答“具体哪个子 ASIN 出了什么问题、为什么、接下来需要关注什么”；
- 总览只接结论和入口，本页保留支撑判断的产品明细。

### 5.2 判断对象与规则来源

- 子 ASIN 是最小判断单元；
- 父体只用于归属、聚合和快速定位；
- 主列表一行对应一个子 ASIN；
- 销量预测、库存风险、补货判断和仓储费风险都落到子 ASIN；
- 产品定位、阶段和当前目标来自产品跟踪表；
- 不同定位、阶段和目标调用不同判断规则，不能共用一套标准。

目前只确认“产品定位和阶段驱动差异化规则”，具体分类、字段和阈值仍待客户确认。

### 5.3 页面从上到下的排布

#### 第一层：固定快速查询和筛选

页面顶部固定保留：

- ASIN / 产品名称；
- 产品定位；
- 库存风险；
- 销售状态；
- 时间范围。

这层用于快速缩小范围，不做复杂的通用筛选器。

#### 第二层：子 ASIN 主列表

主列表一行一个子 ASIN，默认按“更需要处理、风险更高”排序，而不是简单按名称或销量排序。

每行只放结论级信息：

- 产品 / 子 ASIN 基本识别信息；
- 销售表现结论；
- 库存覆盖和库存风险结论；
- 临近 BD 对预测的影响；
- 当前综合结论；
- 进入详情的入口。

主列表不平铺全部销量、库存、补货和库龄字段。运营需要时再打开详情。

#### 第三层：单个子 ASIN 详情

单品详情按一条连续判断链展示：

1. **销售表现**：当前销量结果、趋势和比较周期；
2. **未来 90 天销量预测**：日常销量与 BD 计划统一进入同一预测；
3. **库存消耗与覆盖**：预测销量如何消耗现有及未来库存；
4. **缺货和冗余判断**：预计覆盖时间、缺货日期、过量或积压风险；
5. **补货节点**：在采购 / 运输交期和安全库存规则具备后，给出建议补货时间和数量；
6. **库龄和仓储费风险**：显示当前库龄及未来进入收费节点的库存风险。

详情的目标是解释主列表结论，不是重新做一张全字段报表。

#### 第四层：嵌入式 Agent 查询

Agent 嵌入产品查询流程，不单独做一个聊天页面。运营可以：

- 对当前选中的子 ASIN 提问；
- 对当前筛选结果提问；
- 追问销售、预测、库存、补货或仓储费结论；
- 从回答直接跳到支撑该结论的详情位置。

### 5.4 统一销量预测逻辑

- 页面统一提供未来 90 天预计销量和库存消耗；
- BD 不单独做一个功能；
- 后台登记的 BD 计划日期作为销量预测输入；
- 其他核心输入包括稳定的历史销量、产品定位、阶段和当前目标；
- 日常销量预测和 BD 预测不能形成两套相互冲突的结果；
- BD 取消或改期后，预测需要随计划变化。

目前只确认预测框架和 90 天范围，预测模型、历史窗口、BD 影响方式和更新频率仍待确认。

### 5.5 库存—补货—仓储费链路

库存输入包括：

- 当前可售库存；
- 在途库存；
- 已计划但尚未收货的库存；
- 预留库存；
- 不可售库存；
- 不同库龄的库存。

在数据和规则具备后，页面输出：

- 预计库存覆盖时间；
- 预计冗余库存；
- 预计缺货日期；
- 建议补货时间和数量；
- 即将进入高库龄 / 收费节点的库存；
- 仓储费金额或风险等级。

补货依赖采购 / 运输交期和安全库存规则；仓储费依赖库龄口径、收费节点和费率，不能自行假设。

### 5.6 本页向下游提供什么

本页向关键词和广告决策提供产品状态与约束，例如产品当前目标、销量趋势、库存是否能承接机会、是否存在缺货或积压风险。本页不直接修改广告。

## 6. 关键词分析页：内容和排布

### 6.1 页面定位与数据边界

关键词页同时承担两件事：

- 给运营提供快速、集中的关键词信息查询；
- 在后台沉淀结构化证据，供竞品页和广告决策页继续使用。

一个固定品线共用一套市场关键词库。底层只有一套数据，通过不同查询对象形成市场视图和产品视图，不为每个产品建立互相割裂的词库。

关键词页不直接给出出价、预算、增删词或广告执行命令。

### 6.2 页面从上到下的排布

#### 第一层：动态关键词日报

页面顶部是动态生成的“关键词日报”，不是固定结论卡片。日报结构稳定，每天根据当前数据选择具体关键词、关键词组和产品，固定回答五个问题：

1. 品牌 / 品类关键词流量获取的整体结果，以及相对指定比较周期的变化；
2. 主要增长和下滑的关键词或关键词组，只有在帮助理解时才关联具体产品；
3. 核心关键词覆盖、自然位置和广告位置的重要变化，包括新增覆盖和丢失覆盖；
4. 新出现的异常和机会信号，例如核心词位置下滑，或需求增长但覆盖不足；
5. 当天影响最大的一小组关键词，附带证据，并支持下钻到单词深研或产品视图。

每份日报必须显示：

- 数据范围；
- 对比周期；
- 数据刷新时间；
- “流量获取”的测量定义和来源。

日报可以汇总品牌 / 品类表现，但涉及具体产品“应该怎么做”时，仍需绑定该产品当前目标。

#### 第二层：统一搜索入口

搜索框同时接受：

- 关键词；
- 产品名称；
- 子 ASIN。

系统根据查询对象进入相应视图：搜索关键词进入市场词 / 单词研究，搜索产品或 ASIN 进入产品视图。

#### 第三层 A：市场关键词默认视图

用户进入页面时默认看到市场关键词列表，一行对应一个市场关键词，先展示这个词的共享市场事实，例如：

- 搜索量；
- 需求趋势；
- 竞争情况；
- 近期主要变化；
- 是否属于当天值得关注的关键词；
- 进入单词深研的入口。

这里展示的是市场事实，不直接判断某个产品是否应该投这个词。实际可用字段取决于数据源能力。

#### 第三层 B：产品 / 子 ASIN 查询视图

用户选择具体子 ASIN 后，查看该产品在共享关键词库中的：

- 当前覆盖情况；
- 自然位置和广告位置；
- 覆盖与位置变化；
- 核心词的新增或丢失覆盖；
- 值得继续深看的关键词；
- 与产品目标、库存承接有关的限制提示。

这个视图回答“该产品在市场关键词版图中处于什么位置”，不是另建产品专属词库。

#### 第四层：单个关键词深研

单词深研分两步：

1. 先看关键词自身的市场事实，包括需求、趋势、竞争和主要变化；
2. 再绑定具体子 ASIN 和当前产品目标，形成业务判断。

完整业务判断上下文是：

> 关键词 × 子 ASIN × 当前产品目标

产品目标和阶段来自产品跟踪表。同一个词对不同子 ASIN、不同阶段可能得到不同结论，不能笼统定义为对整个品牌都好或都不好。

### 6.3 判断信号和表达方式

业务判断可以综合：

- 需求机会；
- 产品与关键词的匹配程度；
- 产品覆盖或位置缺口；
- 库存及补货是否能够承接；
- 需要由竞品页继续验证的竞争信号。

关键词页只给证据级结论，例如“需求上涨、产品匹配、当前位置偏弱”或“存在机会，但当前库存不能承接”，不直接转成广告动作。

### 6.4 后台证据记录与下游交接

证据记录不一定单独做成可见模块，但后台至少需要保留：

- 关键词市场事实；
- 产品与关键词关系；
- 与产品目标的匹配情况；
- 库存 / 补货约束；
- 数据时间戳和来源；
- 当前证据结论。

竞品页利用这些证据选择需要继续查看的关键词和竞品；广告决策页再结合竞品验证形成最终建议。

### 6.5 第三方工具边界

可以参考第三方插件在市场关键词、产品关键词和单词深研方面的信息架构，但不代表插件里的所有字段都能接入。实际字段、历史范围、更新频率和来源仍需验证。

## 7. 竞品分析页：内容和排布

### 7.1 页面首要问题

竞品页不是通用的竞品资料查询页，而是回答：

> 当前哪些竞品造成最大的市场威胁？威胁体现在哪里？有哪些可核验的证据？

页面定位是“威胁识别和证据分析工作区”，不是独立输出广告动作的页面。

### 7.2 页面整体路径

> 动态 AI 竞品日报 → 可核验证据和数据 → 运营自助查询与深挖

页面既不能只给一段无法核验的 AI 结论，也不能一打开就把所有竞品字段平铺给用户。

### 7.3 页面从上到下的排布

#### 第一层：动态 AI 竞品日报

页面顶部是动态生成的竞品日报。结构可以固定，但每天具体写哪些竞品和威胁，必须根据当前信号选择，不能预设固定卡片。

日报需要说明：

- 当天或当前周期最重要的威胁；
- 哪些竞品构成威胁；
- 竞品出现了什么可观察的市场表现；
- 压力体现在价格、排名 / 销量、流量、关键词入口，还是多种因素组合；
- 支撑结论的数据入口；
- 数据时间范围、刷新时间和来源。

日报结论必须能点击或下钻到证据，不能只输出无法核验的描述。

#### 第二层：威胁优先的竞品主列表

主列表优先展示当前或近期影响更大的竞品，而不是按竞品名称简单排序。

列表承担两个任务：

- 让运营先看到“谁最值得关注”；
- 提供进入单个竞品证据详情的入口。

威胁排序的具体算法尚未确认，后续需要结合客户判断方式和真实可用数据共同确定。

#### 第三层：自助查询和筛选

运营可以按以下条件浏览或搜索：

- 竞品 / ASIN；
- 时间范围；
- 子类目；
- 变化类型。

可查询的数据维度包括：

- 价格和促销；
- 销量及量级；
- 子类目排名；
- 流量；
- 主要关键词变化；
- 竞品流量结构。

这些是信息框架，不代表字段已经全部具备。

#### 第四层：单个竞品详情与共同时间线

进入竞品详情后，把市场结果和证据信号对齐到同一条时间线：

1. **市场结果侧**：销量、量级、类目 / 子类目排名；
2. **价格与转化侧**：价格、Coupon、促销和其他可观察信号；
3. **流量与位置侧**：主要关键词入口、广告加码信号、自然位置变化和流量结构变化；
4. **关键词级证据**：继续下钻查看具体关键词发生了什么。

价格 / 转化侧与流量 / 位置侧通常可能同时变化，也可能只有一侧变化。两类信号需要一起分析，但不能设成互斥解释。

#### 第五层：证据结论和下游交接

竞品页输出的是有证据支持的竞品信号，例如某一时期价格、销量、排名或关键词入口发生变化，以及该变化是否值得广告决策继续关注。

广告决策页再结合产品状态、库存约束和关键词证据形成最终建议。竞品页不直接给出价、预算或具体执行动作。

### 7.4 因果边界

页面可以描述多个指标同步变化，但不能只凭相关性断言其中一个造成另一个。未经验证的因果关系只能作为分析假设，并且必须展示时间范围和来源。

### 7.5 第三方数据边界

第三方插件或接口可以提供外部竞品数据，工作台负责把数据组织成统一、可追溯、可下钻的证据。价格、销量、排名、流量、关键词和流量结构的实际字段、粒度、历史范围和更新频率仍需客户及数据源验证。

## 8. 广告分析与决策页：两个子页面并行

广告部分不再按“先完成数据展示、以后再做 AI 分析”的串行方式推进，而是两个子页面并行开发，但第一版完成深度不同：

1. **广告分类与数据查看子页面**：第一版做得相对完整，重点解决广告组标签、筛选和分类数据展示；
2. **子 ASIN 广告分析子页面**：第一版先完成广告架构拆解和基础诊断，不要求一次形成完整的广告策略 Agent。

### 8.1 子页面一：广告分类与数据查看

这个子页面主要是广告数据工作台，AI 不是核心能力。页面分为两个模块。

#### 模块一：广告组多维标签

- 以广告组为主要整理对象；
- 从关联子 ASIN、广告后台已有属性、投放对象、投放目的和运营自定义分类等维度建立标签；
- 广告后台已有属性不重复要求运营人工维护；
- 投放目的可以由 AI 根据现有信息提出标签建议，但必须由运营确认；
- 需要区分运营已确认、AI 建议待确认和暂时无法识别的标签状态；
- 标签需要保留生效时间和历史变化，避免用当前目的错误解释过去表现；
- 广告组同时关联多个子 ASIN 或混合多个目的时，需要明确标记，不能强行归入单一产品或单一目的。

具体标签体系和分类名称尚未确认，当前材料中的抢位、稳定流量、长尾测试、品牌防守等只作为讨论示例。

#### 模块二：按标签筛选和分类查看数据

- 支持按子 ASIN 查找其关联广告组；
- 支持按投放目的查看承担同类任务的广告组；
- 支持组合广告类型、投放对象、时间范围等其他标签继续筛选；
- 先展示同类广告组的汇总表现，再下钻到具体广告组和投放对象；
- 第一版以数据展示和运营人工判断为主；
- 只有在客户明确配置指标、比较周期和阈值后，才提供简单异常提示或调整建议，AI 不自行假设阈值。

### 8.2 子页面二：子 ASIN 广告分析

这个子页面是广告部分 AI 能力最集中的位置，以子 ASIN 为入口，对单个产品的现有广告进行纵向拆解。

第一版先完成：

1. 汇总子 ASIN 关联的 SP、SB、SD、Campaign、广告组和投放对象；
2. 形成可核验的现有广告架构；
3. 区分运营已确认的广告目的与 AI 推测的目的；
4. 识别目的不清、多个目的混合、结构重复或明显缺失等诊断点；
5. 在明确阈值、相对自身历史变化或同类广告组比较有依据时，解释数据异常；
6. 判断现有表现是否支撑已经确认的广告目的，并给出初步检查方向或调整方向；
7. 每条诊断展示支撑证据、不确定项和仍缺少的数据。

完整能力方向仍然是：

> 产品市场位置与定位 → 产品推广目标 → 应有广告策略 → 现有广告架构和目的 → 目标支撑情况 → 广告优化方案

但第一版不要求把整条链路全部完善，也不提前承诺精确的竞价、预算调整幅度或完整的新广告搭建方案。

### 8.3 两个子页面如何互相积累

- 子页面一沉淀广告组与子 ASIN 的关系、目的标签、确认状态和分类数据；
- 子页面二使用这些标签理解单个子 ASIN 的广告架构；
- 子页面二识别出的广告目的，经运营确认后可以回到子页面一成为正式标签；
- 后续继续结合阈值、历史广告表现、运营实际调整和 3 / 7 天结果，逐步提高第二子页面的诊断和策略能力。

### 8.4 仍然有效的执行与复盘边界

- 广告判断最终落到子 ASIN；
- 不能只用统一 ACOS 判断所有广告好坏；
- AI 给建议，运营接受、拒绝或修改；
- 第一版不直接修改广告；
- 同时记录 AI 建议和运营实际执行值；
- 第一版只复盘广告动作；
- 先观察 3 天，必要时补充 7 天；
- 没有 API 时通过人工录入或导入记录实际动作。

## 12. 历史材料与最新结论的冲突处理

出现冲突时，以原始记录和时间更晚的明确确认结论为准：

- **父体与子体**：早期资料有父体 / 产品笼统说法，最新结论是子 ASIN 为最小判断单元；
- **BD**：早期设想独立 BD 模块，最新结论是 BD 作为 90 天销量预测输入；
- **关键词动作**：早期有直接筛词和动作建议倾向，最新结论是动态关键词日报和证据层，不直接给广告动作；
- **竞品因果**：早期容易把价格变化直接解释成销量 / 排名原因，最新结论是不凭相关性断言因果；
- **范围**：早期多角色、多类目和通用平台设想，被当前一个品线、一个运营的边界覆盖；
- **执行方式**：早期自动执行 / 一键执行设想，被“AI 建议、人工执行”覆盖；
- **广告 AI 能力范围**：早期方案把现有广告诊断、完整优化建议、新广告方案和历史策略参考并列为第一版功能；最新结论是两个广告子页面并行开发，第一子页面重点做标签、筛选和数据展示，第二子页面第一版先做子 ASIN 广告架构拆解和基础诊断，再随数据积累逐步完善完整策略能力；
- **ACOS / TACOS**：访谈中术语有混用，不能直接落成统一阈值，需正式确认口径并按产品目标差异化；
- **利润口径**：访谈表述有过纠正，必须以客户正式公式为准；
- **日与月**：总览可以每天打开，但头部类目市场份额主要按月判断，不能混为日指标。
