# 产品销售库存 Demo 实现方案

更新时间：2026-08-29
适用范围：异常总览、库存全览、单一子 ASIN 盘点（方案 4.2 / 5.1 / 7.2 / 8.2）
数据底座：`../02-数据构建/v0.2.2`（5 父 ASIN、342 子 ASIN、统一基准日 2026-08-03）
配套文档：数据缺口见 [05-数据缺口登记.md](05-数据缺口登记.md)，本文只讲怎么做。

## 1. 策略：壳子先行，缺口按需补

先把三页的壳子和判断链跑通，**不预先补数据**。哪个功能摆弄不出来，再回头补那一处最小必要数据。

这样做的理由不是省事，是三条：

1. **只有一项缺口真的挡住页面。** 促销/活动完全没有（G1）。仓储费和成本币种（G2、G3）挡住的是"金额能不能当判断依据"，不挡住页面结构。其余六项是精度折扣。
2. **缺口大部分就是方案要求演示的状态。** 需求文档 4.4 节列了 13 种全局状态，实测 **12 种现在就有真实样本**（见 3.3）。把它们做成一等公民，缺口自动变成内容。
3. **先固化派生数据会让 demo 摆弄不了。** 覆盖天数、风险等级、阈值如果预先算成 JSON，改一个阈值就要重跑构建。这些必须运行时算。

## 2. 架构

### 2.1 计算放在哪

按"贵不贵、会不会随参数变"切，而不是按"数据层 vs 展示层"切：

| | 内容 | 放哪 |
| --- | --- | --- |
| 已完成，落盘 | 产品身份与属性、月度与滚动窗口销量、当前库存 15 列、批次库龄、在途事件、单位经济性、父体逐日销量与库存 | `v0.2.2`（22 张表） |
| 运行时算 | 需求预测、逐日库存投影、覆盖天数、缺口与超量、断货日、仓储费分摊、五类风险与严重度、承接能力、范围汇总 | 服务端，每次请求重算 |
| 按需再补 | 见第 5 节触发表 | 新版本数据包 |

运行时算的全部对象是 342 个子体，本地毫秒级，没有预烤的必要。

### 2.2 技术选型

- 服务端：Python 标准库 `http.server` + `sqlite3` **只读**打开 `v0.2.2/bamboocool_product_sales_inventory_v0.2.2.sqlite`（22 张表已建好，含 11,935 条批次），零第三方依赖；
- 用 SQLite 而不是读 JSON：数据包 33MB，本机内存紧，SQLite 按需查询内存占用极小；
- 前端：静态 HTML + CSS + 原生 JS，无构建步骤；
- 端口 **18810**（已确认空闲，避开旧原型的 18700），显式绑定 `127.0.0.1`；
- 启动脚本用 double-fork + `setsid` 防进程组回收（旧原型 `start.py` 的做法可直接搬）；
- 目录：`../../03-前端Demo/`，内含 `server.py` / `start.py` / `lib/` / `web/`。

**安全说明**：服务只绑回环、无鉴权，仅供本机演示。若要给外部看，走 SSH 隧道，不要改绑定地址。

### 2.3 视觉

工程仪表盘语言：深色分层背景、等宽数字右对齐、发丝线分区不做卡片、圆角 ≤3px、无装饰阴影、颜色只承担语义。旧原型 `web/app.css` 可作起点。

三色来源标注（真实 / 派生 / 补造）常显，页面顶部固定一条数据基准与性质声明。

## 3. P1：盘点页壳子

先做单品盘点页，因为另两页读的是它的结果。

### 3.1 七个板块的数据来源

| 板块 | 现在能填什么 | 缺口与降级 |
| --- | --- | --- |
| 产品与盘点结果 | 身份、父体、款号、组合、配色、尺码、负责人、店铺、货物状态、生命周期，341–342/342 真实 | 1 个子体无属性行 → 显示"属性缺失" |
| 销量与需求 | 3/7/14/30/60/90 天真实累计与日均、2026-06 月度、父体日线（579/580/579/579/84 天） | 无子体日线（G4）→ 日线标"父体合计"，叠子体日均参考线 |
| 库存盘点 | 15 个数量列全真实（可售/待调仓/预留/入库中/在途/海外仓/本地/待交付/采购计划） | — |
| 在途与批次 | 194 条真实出货事件，真实 ETA 54 条 | 款号粒度（G6）→ 标明原始粒度，未分摊前不进正式余额 |
| 库存承接 | 运行时算：覆盖天数、断货日、安全线突破日、30/90 天缺口、超量、承接等级 | 16 个子体 30 天日均为 0 → "不可计算"，不写极大值 |
| 库龄 | 11,935 条批次、各档分布、181+ 14,081 件、3 天内跨线 1,286 件/34 子体、7 天内 3,069 件/36 子体 | 收货日是均匀切片假设（G5）→ 标 `estimated`，并写明 FIFO 与 LIFO 下 181+ 差 2.65 倍 |
| 仓储费 | 运行时按数量×体积×库龄档分摊 | 体积 330/342、成本 180/342、币种未确认（G2、G3）→ 金额标"仅示意"，12 个子体显示"不可计算" |
| 盘点记录 | 父体可售线 580 天真实，可做 13 期 | 两个父体的可用/在途只 34 天（G7）→ 该指标标"历史仅覆盖 5 周" |

### 3.2 参数面板（demo 可摆弄的核心）

界面右上角给一组可改参数，改完立刻重算，并显示当前值命中多少对象：

- 安全库存天数（客户真实值 14 / 60 可作默认）
- 目标覆盖天数、最大覆盖天数
- 五类风险各自的阈值
- 批次消耗方式 FIFO / LIFO
- 预测窗口与历史权重
- 活动增量系数

每个参数旁标 `is_demo_default` 与规则版本。**阈值必须显示命中数**——可用率中位数 0.33、覆盖天数中位数 45 天，照搬"可用率 <50% 即异常"会一次点亮 217/341 个对象，那是在描述常态。

### 3.3 13 种状态，12 种有真实样本

方案 4.4 要求的全局状态，现在的样本来源：

| 状态 | 真实样本 |
| --- | --- |
| 正常无明显风险 | 有 |
| 当前筛选无结果 | 前端状态 |
| 新品/历史不足，置信度低 | B0GQXK2Q58 仅 84 天日历史 |
| 无活动计划 | 180 个子体（10 个款号）一条 BD 记录都没有 |
| 在途存在但 ETA 未知 | 194 条里真实 ETA 仅 54 条 |
| 总库存有量但可售异常 | 62 个子体可售为 0，217 个可用率 <50% |
| 产品定位/阶段缺失 | 1 个子体无属性行 |
| 阈值使用 Demo 默认 | 全部五类风险阈值 |
| 数据源过期 | B0GQXK2Q58 日数据止于 2026-07-28，早于基准日 |
| 仓储费缺失只能估算 | 12 个缺体积、162 个缺成本 |
| 预测/盘点不可计算 | 16 个子体 30 天日均为 0 |
| 部分派生部分补造 | 批次库龄全部 `estimated` |
| **活动已取消或刚修改** | **无，需构造（唯一一个）** |

这 12 种不是"数据不好"，是这套系统该有的表达能力。壳子阶段就要把它们做成显式状态，不能等到最后补。

### 3.4 P1 验收

- 342 个子体每一个都能打开盘点页，七个板块都有内容或明确的不可计算说明；
- 抽 10 个子体，覆盖天数、断货日、缺口、3/7 天跨龄量能从明细手工复算一致；
- 改任一参数后，页面数字立刻变化，且依据区显示新的规则版本与命中数；
- 上表 12 种状态各能找到至少一个演示对象；
- 任何一个数字都能说清是真实、派生还是补造。

## 4. P2：两个总览页

从盘点结果聚合，不另造一套口径。

- **异常总览**：五类风险各一个标准化看板 + 风险产品区。真实材料：覆盖 <7 天 74 个、<14 天 95 个、<30 天 131 个；覆盖 >90 天 86 个、>180 天 27 个（最大 659 天）；可用率 <50% 217 个、<30% 161 个；181+ 14,081 件、高占比 >50% 有 42 个；仓储费为分摊值。
- **库存全览**：筛选主轴用款号(15) / 父体(5) / 组合(26) / 配色(55) / 尺码(8) / 负责人(3) / 店铺(4) / 货物状态(3) / 生命周期(2)，全部真实。品类只有一个值「男士长平角」，保留但显示单值。
- 父体折叠与款号折叠**并列提供**：父 ASIN 与款号是交叉关系（17 条边，2 个款号被两个父体共享），按层级相加会重复计数。
- 覆盖天数、可用率、费用率、风险分值**不做简单平均**，用范围内总分子除总分母，并同时给中位数。

验收：同一子体在三页的风险、库存、建议量完全一致；筛选后所有指标重算；从详情返回保留筛选、排序、展开与滚动位置。

## 5. P3：什么时候回来补数据

不按清单补，按"演示时摆弄不出来"补。触发条件与最小补法：

| 想演示 | 现在为什么不行 | 最小补法 | 代价 |
| --- | --- | --- | --- |
| BD 拉高需求造成缺口（S03） | G1 无未来活动 | 造 **1 个**未来 BD 事件挂在有真实锚的 5 个款号上 | 小 |
| 活动取消后积压（S07） | G1 无活动版本 | 给上面那个事件加一个 `cancelled` 版本 | 小 |
| 库存货值排序 / 费占毛利 | G3 币种未确认 | 向客户问一句话 | 零开发 |
| 仓储费金额可当判断依据 | G2 只有负责人×月总额 | 向客户要 ASIN 级仓储费账单 | 零开发 |
| 某个子体的历史日线 | G4 无子体逐日 | 用父体日形状按子体 7 个真实窗口值约束拆分 | 约 20 万行，中 |
| 在途进正式可用余额 | G6 款号粒度 | 按子体库存权重分摊，先跑量级校验 | 中 |
| 13 期完整周度历史 | G7 两个父体仅 34 天 | 无法补，只能标注覆盖范围 | 不可补 |
| 12 个子体的仓储费 | G8 缺单件体积 | 向客户要 TH23AM-153 箱规 | 零开发 |

注意最后一列：真正需要写代码补的只有两项（G4 拆分、G6 分摊），四项是向客户问一句话，一项不可补。这就是"先做壳子"成立的原因。

## 7. 仍待客户确认（不阻塞 P1、P2）

1. 单位成本币种（影响货值、费销比、费毛利比三个结论）；
2. ASIN 级仓储费账单；
3. 风险阈值、合理覆盖周期、库龄分段、仓储费压力分母的正式标准；
4. 带日期与折扣幅度的 BD/Deal 记录；
5. 负责人姓名是否原样展示（数据里是真实姓名，数据层保留真实关联即可支持别名）；
6. TH23AM-153 的箱规与单件体积。
