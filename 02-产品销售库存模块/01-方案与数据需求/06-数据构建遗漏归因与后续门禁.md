# 数据构建遗漏归因与后续模块强制门禁

更新时间：2026-08-29  
适用范围：Bamboocool Demo 各业务模块的数据规划、数据源审计、数据构建和验收  
归因边界：客户数据源只以用户指定的 `数据源/AI广告对接数据-总20260803` 为准；其他目录不用于判断本次源数据是否齐全

## 1. 结论

这次数据包不足以支撑可玩 Demo，主要不是因为需求没写清楚，也不是因为所有缺失都藏在原表里没有被发现。

根因是：

1. 需求阶段已经定义了完整的数据契约和验收条件；
2. 指定数据源内确实缺少子 ASIN 连续日销量、可用的 Deal 事件明细和未来 Deal 排期；
3. 数据构建方案也已经规定“缺失部分补齐”“缺失未来活动时场景补充”；
4. 但实际构建被收窄成“来源事实层”，把补齐、预测、投影、风险和活动场景整体推迟；
5. 质量门禁只检查已生成数据是否自洽，没有检查页面能力依赖的数据是否齐备；
6. 因此出现“所有检查通过，但核心页面无法运行”的假绿状态。

责任分布判断：

| 环节 | 判断 | 责任程度 |
| --- | --- | --- |
| 正式产品方案 | 子 ASIN 粒度、活动影响、未来逐日需求均已说明 | 非主因 |
| Demo 数据需求 | 日销量、活动、预测、投影、风险、场景和验收均已字段化 | 非主因 |
| 指定数据源 | 部分关键输入确实缺失或粒度不足 | 客观缺口，但不是不补齐的理由 |
| 数据源索引 | 能回答“有哪些表和字段”，不能充分回答业务粒度、指标语义和能力覆盖 | 次要方法缺陷 |
| 数据构建执行 | 把必须补齐的上游输入留到后续，交付层级发生目标漂移 | 主要根因 |
| 质量与验收 | 未设置需求覆盖、场景覆盖和页面查询门禁 | 主要系统性根因 |

## 2. 证据链

### 2.1 需求在构建前已经写清楚

`01-产品销售库存模块-Demo数据需求.md` 在数据构建前已经明确：

- 最小分析单元是子 ASIN；
- `fact_sales_daily` 粒度为日期 × 子 ASIN × 站点；
- `fact_promotion_event` 必须包含活动类型、开始/结束时间、状态、折扣、活动增量和版本；
- 历史销售至少连续 180 天，未来预测连续 90 天；
- 活动需覆盖历史 6 个月和未来 90 天；
- 必须具备计划、批准、活动中、取消、完成及至少一个版本变更；
- S03 要演示未来 BD 导致缺口；
- S07 要演示活动取消后形成积压；
- S20 要演示调整活动增量后，预测和库存结果联动变化；
- “销售真实段、未来预测段、活动事件和库存投影使用一致日期轴”属于 Demo 不能省略项。

所以，子体日销量和未来 Deal 不是构建后临时增加的新要求。

### 2.2 构建方案也已经规定缺失时补齐

`03-产品销售库存Demo数据构建方案.md` 已明确：

- 真实数据优先；
- 可计算的数据由规则派生；
- 原始资料没有、粒度不足或时间不足时补齐；
- `fact_sales_daily` 在子体粒度缺失时进行约束拆分；
- `fact_promotion_event` 缺少审批、排期或未来活动时补齐；
- 数据处理流程应先生成缺失矩阵，再对缺失部分执行补齐；
- 20 个场景中没有覆盖的故事必须增加最小必要记录。

因此，方法定义与实际执行发生了偏离。

### 2.3 实际构建主动排除了核心能力层

首版构建器的文件说明直接写明：预测、投影、风险和场景补充不进入 v0.1.0。

v0.1.0 的 `missing_field_matrix` 对 342 个子 ASIN 全部标记：

- `needs_child_daily_supplement = true`；
- `needs_inventory_history_supplement = true`；
- `needs_lot_date_supplement = true`；
- `needs_forecast_derivation = true`；
- `needs_projection_derivation = true`；
- `needs_risk_derivation = true`。

也就是说，系统知道所有对象都缺这些数据，却仍然将数据包判为 `all_checks_passed = true`。

v0.2.0 继续把以下内容列为“来源事实层之外”：

- 子 ASIN 逐日销量；
- 需求预测；
- 库存投影；
- 盘点结果；
- 五类风险。

v0.2.2 的 manifest 仍把子体日销量、预测、投影、盘点和风险列为 `next_layer`。

### 2.4 实际表结构与需求数据契约没有闭合

需求规定的关键对象与 v0.2.2 实际情况如下：

| 需求对象 | v0.2.2 状态 | 影响 |
| --- | --- | --- |
| `fact_sales_daily`：日期 × 子 ASIN | 缺失；只有父体日销量、子体月销量和窗口值 | 子体历史曲线、异常日、活动/非活动拆分无法直接运行 |
| `fact_promotion_event` | 缺失 | Deal 标记、活动版本、取消状态、活动增量无输入 |
| `bridge_promotion_product` | 缺失 | 活动无法稳定关联到子 ASIN |
| `fact_demand_forecast_daily` | 缺失 | 基线/含活动预测切换不可运行 |
| `fact_inventory_projection_daily` | 缺失 | 共同日期轴、缺货日和安全线突破无法由数据包直接提供 |
| `fact_inventory_assessment` | 缺失 | 三页没有共同的子 ASIN 盘点结果 |
| `fact_inventory_risk` | 缺失 | 五类风险、多风险和风险生命周期不可直接运行 |
| `fact_storage_fee` | 缺失 | 仓储费风险只能临时估算，不能形成完整费用事实 |
| `dim_inventory_rule_set` / `bridge_product_rule` | 缺失 | 参数、规则版本和产品适用关系没有数据契约 |
| `fact_demo_scenario` | 缺失 | 无法证明关键演示故事可重复触发 |
| `fact_source_run` / `fact_result_lineage` | 只有文档式血缘，没有完整结果级表 | 页面结论无法系统追溯到输入和规则 |

现有 v0.2.2 更准确的名称应是“产品销售库存来源事实与部分派生底座”，不是“可直接接页面的完整 Demo 数据包”。

## 3. 为什么会出现这种偏差

### 3.1 把“数据源覆盖率”误当成“页面能力覆盖率”

数据源索引主要回答：

- 有哪些文件、Sheet 和字段；
- 字段的非空率、日期范围和示例；
- 哪些表结构重复；
- 哪些字段可能是关联键。

它没有完整回答：

- 一行的真实业务粒度；
- ASIN 是单个子体、父体还是子体清单；
- “销量”是总销量、广告归因销量、父体合计还是窗口累计；
- 该字段能支撑哪一个页面交互；
- 缺失字段是可派生、必须补造还是必须向客户补问。

所以“全部字段已扫描”不能推出“全部页面数据已准备”。

### 3.2 没有维护需求到数据产物的双向追踪

需求文档虽然列出了功能、数据表、字段和验收项，但构建器没有读取一份可执行的需求清单，也没有生成以下关系：

```text
页面功能
→ 页面输出
→ 计算公式
→ 必需输入
→ 目标粒度与时间范围
→ 来源/派生/补齐方案
→ 实际数据表
→ 自动验收
```

结果是需求文档和构建脚本成为两套平行材料。文档写得完整，并不能约束脚本必须产出这些表。

### 3.3 缺失矩阵被当成说明材料，而不是构建任务队列

正确逻辑应是：

```text
发现必需字段缺失
→ 标记缺口类型
→ 生成补齐任务
→ 执行补齐
→ 校验补齐后的守恒和场景
→ 才允许发布
```

实际逻辑是：

```text
发现必需字段缺失
→ 写入 missing_field_matrix / known_limitations
→ 其他现有表检查通过
→ 发布数据包
```

这使“知道缺什么”替代了“把缺失数据构建出来”。

### 3.4 质量门禁验证了内部正确性，没有验证用途适配性

现有门禁主要检查：

- 父/子体数量；
- 主键唯一；
- 已有库存、库龄、标识覆盖率；
- 父体日销量非空；
- JSON 与 SQLite 行数一致；
- 库龄前滚后的内部守恒。

这些检查能说明“已经生成的表没有明显机械错误”，但不能说明“Demo 所需数据已经生成”。

缺失的门禁包括：

- 必需表是否存在；
- 必需字段和正确粒度是否存在；
- 每个页面交互是否有查询结果；
- 每个场景是否有可触发样本；
- 上游缺口是否导致下游计算链断裂；
- 是否存在历史和未来的完整日期轴。

因此出现了质量检查全绿但 Demo 不可玩的结果。

### 3.5 将阶段性交付层级与最终用途混淆

“来源事实层”本身可以作为一个合法中间产物，但必须满足两个条件：

1. 文件名、manifest 和交付说明明确写为中间层；
2. 不得以它回答“是否可以开始接页面”。

本次虽在 README 中写了边界，但后续讨论和实现计划仍把它作为页面底座，导致中间层被当成最终 Demo 数据包。

### 3.6 局部修复没有重新执行全量需求回归

v0.2.0、v0.2.1、v0.2.2 分别修复了父体日销量选源、单位体积和库龄基准日等问题，但每次都沿用上一版本的交付边界。

局部问题修好后，没有重新回答：

- 九项能力现在有几项能运行；
- 三个页面有多少交互能运行；
- 20 个演示场景覆盖了多少；
- 必需数据表还缺哪些。

这属于补丁式迭代，而不是按完整产品契约回归。

### 3.7 未经确认把“完整可玩”降级成“壳子先行”

后续实现方案提出“壳子先行、缺口按需补”，并把子体日销量定义为精度问题。这与原数据需求中的“Demo 不能省略”和用户要求的“先构建足以支撑功能的数据”不一致。

页面可以为真实系统显示缺失状态，但 Demo 的核心成功路径不能全部依赖缺失状态。是否接受这种降级应由用户决定，不能由构建过程自行改变。

## 4. 根因树

```text
表象：数据包有很多真实字段，但不足以做可玩 Demo
├─ 指定源数据客观缺口
│  ├─ 无选定子体连续日销量
│  ├─ 无完整 Deal 事件事实
│  └─ 无未来 Deal 排期
├─ 构建策略错误（主因）
│  ├─ 必补缺口被整体推迟到 next layer
│  ├─ 没有把缺失矩阵转换成补齐任务
│  ├─ 没有完成预测、投影、盘点和风险依赖闭包
│  └─ 中间来源层被当成页面数据包
├─ 质量体系错误（主因）
│  ├─ 只检查已有表
│  ├─ 不检查必需表和目标粒度
│  ├─ 不检查页面查询
│  └─ 不检查演示场景
└─ 过程治理错误
   ├─ 文档与代码无可执行追踪
   ├─ 局部修复无全量回归
   └─ 范围降级未经用户确认
```

## 5. 下一模块必须采用的工作方法

### 5.1 第一张表：能力—数据契约矩阵

在检查数据源之前，先对产品方案逐项拆解。每个页面能力必须形成一行，至少包含：

| 字段 | 含义 |
| --- | --- |
| `capability_id` | 稳定能力编号 |
| `page` / `interaction` | 页面和具体交互 |
| `decision_or_output` | 用户最终看到或操作的结果 |
| `metric_definition` | 指标定义和计算关系 |
| `required_inputs` | 直接输入与依赖结果 |
| `required_grain` | 目标业务粒度 |
| `history_horizon` / `future_horizon` | 历史和未来范围 |
| `required_states` | 正常、缺失、取消、失败等状态 |
| `required_scenarios` | 必须可触发的演示故事 |
| `acceptance_query` | 可自动执行的验收查询 |

没有这张矩阵，不进入数据源映射。

### 5.2 第二张表：源—目标字段映射矩阵

每个必需输入必须逐项标记：

| 状态 | 使用条件 |
| --- | --- |
| `direct` | 指定源中存在、粒度和口径完全匹配 |
| `derived` | 可由现有字段按确定规则计算 |
| `supplemented` | 源中缺失或粒度不足，需要受真实锚约束地构造 |
| `scenario_added` | 为演示状态或未来事件专门构造 |
| `blocked` | 既不能构造也不能合理派生，需要客户补充或删除能力 |

映射必须记录：源文件、Sheet、字段、实际粒度、指标语义、日期范围、覆盖率、冲突来源、转换规则和目标表字段。

不能只看表头。必须用真实行验证：

- ID 是单值还是列表；
- 日期是一日、月份还是报表区间；
- 指标是总量、归因量还是滚动窗口；
- 一行是否在目标主键下唯一；
- 目标对象集合的实际覆盖率。

### 5.3 第三张表：缺口处置清单

每个 `supplemented`、`scenario_added` 或 `blocked` 项必须拥有：

- 影响的能力和页面；
- 构造方法；
- 真实锚点；
- 守恒关系；
- 允许的假设；
- provenance 标记；
- 质量测试；
- 负责人和完成状态。

缺口不能只写在 `known_limitations` 中。只要它影响 P0/P1 能力，就必须成为当前版本任务；若要延期，必须取得用户确认。

### 5.4 先做依赖闭包，再开始批量生成

把页面结果画成有向依赖图，并从最终结果反向检查输入是否闭合。

例如产品库存模块：

```text
风险结果
← 盘点结果
← 库存投影
← 每日正式需求 + 供应事件 + 当前可售
← 每日基线需求 + 活动增量
← 子体历史日销量 + 活动事件
```

如果子体历史日销量和活动事件为空，预测、投影、盘点和风险都不能被视为可完成。不能因为下游表还没有开始生成，就把上游缺失降为“只影响图表精度”。

### 5.5 严格分开四层交付物

| 层级 | 内容 | 是否可称可玩 Demo 数据包 |
| --- | --- | --- |
| L0 源索引 | 文件、Sheet、字段和基础画像 | 否 |
| L1 标准化来源事实 | 客户原值、去重、统一标识和粒度说明 | 否 |
| L2 补齐与场景事实 | 缺失粒度、未来事件、异常状态、场景数据 | 否，除非所有页面只读事实 |
| L3 服务数据层 | 预测、投影、盘点、风险、聚合、血缘和页面索引 | 是 |

每个版本 manifest 必须声明 `delivery_layer`。L0–L2 检查通过，只能说明该层合格，不能说明 Demo 已就绪。

### 5.6 建立四类强制门禁

#### A. 契约门禁

- P0/P1 必需表全部存在；
- 必需字段齐全；
- 主键与粒度符合数据契约；
- 每个能力都映射到具体表和字段；
- 不允许用父体、款号或报表区间替代子体日粒度而不报错。

#### B. 数据门禁

- 主键唯一、外键完整；
- 目标对象覆盖率达到约定值；
- 日期连续性和历史/未来范围满足契约；
- 跨表守恒成立；
- 直接值、派生值、补齐值和场景值来源明确；
- 缺失对象有显式不可计算状态。

#### C. 能力门禁

为每个页面功能运行验收查询。例如：

- 任一子 ASIN 能返回历史销售、基线预测、含活动预测和库存余额；
- 活动日的正式预测与基线存在可解释差额；
- 活动取消后新版本不再产生未来增量；
- 修改活动增量后，缺货日或覆盖结果按规则联动；
- 五类风险均能从明细复算；
- 三页读取同一 `assessment_id` 和规则版本。

#### D. 场景门禁

场景清单必须机器可读，每个场景包含：对象、输入事件、期望输出和断言。P0/P1 场景未覆盖时，构建失败。

以 Deal 为例至少要有：

- 无活动计划；
- 历史已完成活动；
- 未来 planned/approved 活动；
- active 活动；
- cancelled 活动；
- 修改后产生新版本并 supersede 旧版本；
- 活动导致库存结论改变；
- 活动取消导致积压结论改变。

### 5.7 发布条件

只有同时满足以下条件，才能把数据包交给前端并称为“可玩 Demo 数据包”：

1. P0/P1 能力契约覆盖率 100%；
2. Critical 数据缺口为 0；
3. 必需场景覆盖率 100%；
4. 所有契约、数据、能力和场景门禁通过；
5. manifest 明确为 L3 服务数据层；
6. 任一范围降级均有用户确认记录；
7. 独立验收者只根据产品方案和数据包即可复核，不依赖构建者口头解释。

## 6. 下一模块的标准执行顺序

1. 读取正式产品方案、能力清单和访谈事实；
2. 输出能力—数据契约矩阵；
3. 输出完整依赖图和 P0/P1 场景清单；
4. 扫描用户指定的数据源范围；
5. 对每个目标字段做真实行、粒度、口径和覆盖率验证；
6. 输出源—目标映射矩阵；
7. 将所有缺口分类为 derived / supplemented / scenario_added / blocked；
8. 先确认补齐策略和守恒条件，再编写生成器；
9. 依次生成 L1、L2、L3，不跨层宣称完成；
10. 执行契约、数据、能力、场景四类门禁；
11. 由独立验收者进行需求回归；
12. 通过后才交给前端。

## 7. 本次复盘的直接结论

本次问题应归因为：

> 指定数据源存在真实缺口，但需求和构建方案已经要求对这些缺口进行补齐；实际构建却停在来源事实层，且质量门禁没有验证需求覆盖和页面可玩性，最终把“中间数据层正确”错误地等同于“Demo 数据已经完成”。

后续不能再用“字段扫描完整”“现有表检查通过”或“已记录缺口”作为数据构建完成的依据。完成标准必须回到页面能力和可复现演示场景。
