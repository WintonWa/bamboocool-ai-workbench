# 产品销售库存 Demo 数据构建方案

更新时间：2026-08-29  
适用范围：Bamboocool AI 运营工作台第一阶段 Demo——产品、销售与库存模块  
输入依据：产品方案、产品库存三页架构、能力清单、访谈纪要、客户全量数据源索引

## 1. 建设原则

本 Demo 按正式产品方案重新建设。页面范围、对象关系、导航层级、交互路径和能力边界，以产品方案、产品库存三页架构和能力清单为准。

数据采用“真实数据优先、派生计算其次、缺失部分补造”的策略：

1. 客户表中已经存在且质量可用的数据，清洗、映射后直接继承；
2. 可以由现有数据计算得到的指标，不补造原值，统一由规则派生；
3. 只有原始资料确实没有、粒度不足或时间范围不足的字段才补齐；
4. 为了让 Demo 覆盖必要的异常故事，可以增加少量场景数据，但必须与真实数据分开标记；
5. 页面只读取标准化后的数据层，不直接读取格式复杂、公式密集、口径不一的客户工作簿。

结合关键表的实际关联结果，首版不建议机械采用“8 个父 ASIN、约 72 个子 ASIN”。客户真实父体的变体规模差异很大，部分父体本身就有 50–130 多个子 ASIN。更合适的候选范围是 5 个真实父 ASIN、约 342 个真实子 ASIN：其中 4 个成熟父体合计约 250 个子体，另加入 1 个历史较短的新父体约 92 个子体。这个规模既能展示真实的变体复杂度和生命周期差异，也仍然适合本地 Demo 分页、筛选和钻取。

最终入选对象仍需检查产品线和业务故事是否匹配；规模应由真实父子关系决定，不能为了凑整数拆断父体。

## 2. 为什么不能直接把 Excel 原样接入页面

使用客户现成数据是正确方向，但“继承数据”不等于“原表直接读取”。客户资料存在以下客观情况：

- 同一 ASIN、库存或销量指标分布在不同文件与 Sheet 中；
- 部分工作簿有多层表头、合并单元格和大量公式；
- 同名字段可能存在不同时间粒度、币种、统计窗口和业务口径；
- 两份库存工作簿内容完全重复，直接累加会造成重复计算；
- 日销量在父 ASIN 粒度较完整，部分子 ASIN 只有月累计或周期数据；
- 当前库存信息较丰富，但历史库存快照和未来逐日库存并不完整；
- 库龄多为区间桶，缺少逐批次收货日期；
- 仓储费、运输费和利润数据以团队/月度汇总为主，不能直接归到每个子 ASIN；
- 缺少统一的规则版本、预测版本、风险生命周期和结果血缘。

因此需要做一次标准化 ETL：保留可用原值，解决重复、关联、粒度和口径问题，再补齐缺失部分。这样既能最大程度利用客户真实数据，也能保证 Demo 三个页面的数据互相一致。

## 3. 对现成数据的实测判断

对产品月报、FBA 库存、补货建议和父 ASIN 日表现做了实体级交叉核查，结果如下：

| 核查项 | 结果 | 判断 |
| --- | ---: | --- |
| 月报产品表现 | 1,154 个子 ASIN、70 个父 ASIN | 产品主数据规模足够，不需要虚构商品体系 |
| 产品 ASIN 与 FBA 库存关联 | 1,136 / 1,154，覆盖 98.4% | 当前库存可以大面积直接继承 |
| 产品 ASIN 与补货建议关联 | 883 / 1,154，覆盖 76.5% | 全量存在缺口，但可从高覆盖父体中选 Demo 范围 |
| 补货表关键标识完整度 | ASIN 100%、FNSKU 99.8%、SKU 98.3% | 子 ASIN 级标识桥接可靠 |
| 补货表当前库存与销量窗口 | FBA、可售、预留、在途、总库存及 3/7/14/30/90 天销量均为 100% 非空 | 库存盘点的基础事实较强 |
| 补货建议日期完整度 | 预计断货时间 79.5%、建议采购日 73.0% | 可继承现有结果，但不能假设所有产品都有建议 |
| 父 ASIN 日表现 | 21 个父 ASIN 有日数据；成熟候选有 579–593 天历史 | 父体趋势和季节性可以直接继承 |
| 子 ASIN 日表现 | 主要是月度值或 3/7/14/30/90 天窗口值 | 不能冒充真实日明细，需要受真实汇总约束地补齐 |

首版可优先考虑四组成熟父体，其子体数量约为 96、66、51、37，补货数据覆盖分别达到 100%、100%、100%、97%，且父体日历史约 579–593 天；再加入一组约 92 个子体、约 85 天历史、补货覆盖 100% 的较新父体，用于展示新品和短历史场景。这里记录的是匿名结构候选，正式选取时还要核查其产品线和场景差异。

由此可以得出：

- 产品主数据、当前库存、销量窗口和大部分补货数据应直接继承；
- 父 ASIN 日趋势应直接继承；
- 子 ASIN 日序列只能依据真实父体日总量、子体月销量和各销量窗口进行约束拆分，并标记为补齐；
- 未来预测、库存投影、盘点结论和风险状态本质上是系统计算结果，应由规则派生；
- 只有真实数据没有覆盖的必要演示故事才增加场景记录。

## 4. 数据来源标记

所有进入 Demo 的字段或记录必须携带来源类型，建议使用以下四种：

| `provenance_type` | 含义 | 示例 |
| --- | --- | --- |
| `customer_actual` | 从客户表中直接继承，只做格式和枚举标准化 | ASIN、SKU、FNSKU、实际库存、实际历史销量 |
| `derived` | 使用真实或补齐数据按明确规则计算 | 可售库存、覆盖天数、预计断货日、风险等级 |
| `supplemented` | 客户资料缺失，按可解释方法补齐 | 缺失的子 ASIN 日销量、批次收货日、标准 ETA |
| `scenario_added` | 为确保 Demo 覆盖必要故事而增加 | 一条延迟到货、一个临界库龄批次、一次未来活动 |

同时记录：

- `source_file`、`source_sheet`、`source_row_key`；
- `source_as_of_date` 和数据更新时间；
- `transform_rule` 或补齐方法；
- `confidence_level`；
- `dataset_version`、`rule_version` 和 `calculation_run_id`。

这样在详情页中可以区分“客户原始事实”“系统计算结果”和“Demo 补齐场景”，也方便以后替换为真实接口。

## 6. 九项能力的数据继承策略

| 能力 | 现有支撑度 | 优先继承的数据 | 需要补充或派生的部分 |
| --- | --- | --- | --- |
| 销售、产品、库存统一关联 | 强 | 父/子 ASIN、SKU、FNSKU、店铺、负责人、产品生命周期 | 去重、实体归一、历史映射和统一产品主键 |
| 分类分级规则 | 缺失 | 零散运营经验字段和现有公式可作规则输入 | 建立统一规则集、适用范围、优先级和版本 |
| 活动校准的销量预测 | 部分 | 父 ASIN 日表现、子 ASIN 月度/周期销量、广告及动作日期 | 补齐缺失的子 ASIN 日粒度；派生基准与活动校准预测 |
| 当前与未来可用库存 | 部分偏强 | FBA、AWD、海外仓、国内仓、在途、预留、接收中 | 标准化库存状态；补齐 ETA；派生未来逐日可用量 |
| 覆盖天数、缺口和建议量 | 部分 | 3/7/14/30 天销量、断货时间、补货建议字段 | 统一按正式规则重新计算并生成版本 |
| 库龄、成本和仓储费压力 | 部分 | 库龄桶、库存成本、月度仓储费、运输费用 | 缺少批次日期时合理反推；将汇总费用按规则分配 |
| 五类库存风险识别 | 部分 | 冗余库存、断货、周转、库龄线索 | 统一派生风险、严重度、证据、建议和生命周期 |
| 产品范围聚合盘点 | 强 | 组别、负责人、父/子 ASIN、生命周期、销售目标 | 从子 ASIN 结果动态聚合，不能手写父级汇总 |
| 版本、快照与血缘 | 缺失 | 文件路径、Sheet、文件日期和业务日期 | 建立计算批次、周度盘点版本、规则版本和结果血缘 |

结论：客户源数据是 Demo 的主要数据底座，而不是只用于观察字段和分布。补造主要集中在缺失粒度、未来事件、规则版本和场景覆盖上。

## 7. 核心数据表的处理方式

| 数据表 | 数据性质 | 主要来源 | 处理方式 |
| --- | --- | --- | --- |
| `dim_product_parent` | 真实继承 | 月报父 ASIN、产品跟进、款式目标 | 合并去重，保留实际父体、产品线、负责人和生命周期 |
| `dim_product_child` | 真实继承 | 产品表现 ASIN、库存与补货表 | 保留实际子体、变体、状态、售价等可用字段 |
| `bridge_product_identifier` | 真实继承 | ASIN、SKU、FNSKU、MSKU 字段 | 统一多标识映射，处理一对多和历史变更 |
| `fact_sales_daily` | 真实为主、缺失补齐 | 父 ASIN 日表现、流量表、子 ASIN 月度销量 | 优先保留实际日数据；粒度缺失时按月度总量和已知权重拆分，并标记 `supplemented` |
| `fact_promotion_event` | 真实为主、场景补充 | 动作调整、广告活动、周/月目标 | 保留可识别活动；缺少审批、排期或未来活动时补齐 |
| `fact_inventory_snapshot` | 真实继承 | FBA、AWD、海外仓、国内仓、在途和预留库存 | 选定数据截止日，去重后建立统一位置与状态枚举 |
| `fact_inventory_lot` | 真实为主、缺失补齐 | 库龄桶、库存成本、库存明细 | 有批次数据直接继承；只有库龄桶时按桶内规则反推批次日期 |
| `fact_supply_event` | 真实为主、缺失补齐 | 出货表、补货建议、在途明细 | 继承采购/出货/到货记录；标准化节点和 ETA |
| `fact_storage_fee` | 真实汇总、规则分配 | 月度仓储费、库存成本 | 保留真实汇总金额；按数量、体积、库龄等规则分配至子 ASIN |
| `dim_inventory_rule_set` | 配置数据 | 产品方案、运营经验、客户表公式 | 建立默认、产品线、生命周期三级规则及版本 |
| `bridge_product_rule` | 配置数据 | 产品层级和规则适用范围 | 按优先级绑定规则至父/子 ASIN |
| `fact_demand_forecast_daily` | 派生结果 | 标准化历史销量、活动和季节性 | 生成基准/活动两种预测、P50/P90 和置信度 |
| `fact_inventory_projection_daily` | 派生结果 | 当前库存、供应事件、销量预测 | 逐日计算未来 90 天可用库存、缺口和断货日期 |
| `fact_inventory_assessment` | 派生结果 | 库存投影和规则集 | 每个子 ASIN、每个盘点版本生成统一结论和建议量 |
| `fact_inventory_risk` | 派生结果 | 盘点、库龄、库存和供应事件 | 生成五类风险、严重度、证据、动作和状态变化 |
| `fact_source_run` / `fact_result_lineage` | 治理记录 | 全部数据层 | 记录原始文件、转换过程、补齐规则和结果依赖 |

## 8. 数据选取范围

首版不必把所有客户数据全部塞入页面。建议从真实数据中选一个既完整又有差异的展示范围：

| 对象 | 建议规模 | 选取方式 |
| --- | ---: | --- |
| 站点 | 1 | 美国站 |
| 核心产品线 | 1 | 选择客户数据中覆盖最完整的一条产品线 |
| 父 ASIN | 5 | 4 个成熟父体加 1 个较新父体，最终按完整度和场景差异确认 |
| 子 ASIN | 约 342 | 保留入选父体下的实际子 ASIN，不任意截断父子关系 |
| 父体销售历史 | 成熟父体约 579–593 天，新父体约 85 天 | 直接继承实际日数据，不强行把所有对象补成相同长度 |
| 子体销售历史 | 月度与 3/7/14/30/90 天窗口为真实值 | 页面需要日趋势时，在真实汇总约束下补齐日序列 |
| 预测和库存投影 | 90 天 | 系统派生 |
| 周度盘点版本 | 13 | 有历史快照则继承，无历史快照部分回放生成 |

负责人名称是否原样展示，可在 Demo 面向范围明确后决定；数据层保留真实关联，同时支持展示别名，不影响业务关系。

## 9. 演示场景的形成方式

不应先凭空制造全部故事。建议先在客户真实数据中识别现成场景，再补齐缺失场景：

1. 从断货时间、库存覆盖、冗余库存、库龄桶、在途 ETA 等字段中寻找真实异常；
2. 将真实异常映射为缺货、断货、冗余、滞销和临界库龄五类标准风险；
3. 检查真实数据能否覆盖产品方案要求的 20 个演示场景；
4. 已覆盖的场景直接使用真实记录；
5. 未覆盖的场景只增加最小必要记录，并标记为 `scenario_added`；
6. 场景补充不能篡改其他真实汇总，应通过独立批次或调整项保持守恒。

优先寻找并展示以下高价值场景：

- 高销量产品即将断货；
- 在途数量足够但 ETA 晚于预计断货日；
- 扣除预留和不可售后出现库存缺口；
- 低动销且库存高形成冗余；
- 批次将在 3/7 天内跨过 180 天库龄阈值；
- 同父体不同子体走势明显分化；
- 风险在不同周度版本中新增、升级或解除；
- 未来活动使原本安全的库存变得不足。

## 10. 数据处理与补齐流程

建议建立可重复执行的数据管道：

1. 冻结客户原始文件快照，只读保存；
2. 解析全部相关 Sheet，保留文件、Sheet 和原始行定位；
3. 去除完全重复文件，展开多层表头，区分公式与缓存结果；
4. 统一 ASIN、SKU、FNSKU、店铺、站点、日期、币种和库存状态；
5. 建立字段口径优先级，解决同一指标多来源冲突；
6. 计算每个父/子 ASIN 的字段完整度并选择 Demo 产品范围；
7. 将真实销售、库存、在途、库龄和费用写入标准表；
8. 生成字段缺失矩阵，只对缺失部分执行补齐；
9. 运行预测、库存投影、盘点和风险规则，生成派生结果；
10. 检查 20 个场景的覆盖率，只补充尚未覆盖的必要故事；
11. 写入来源、转换、补齐、规则和计算血缘；
12. 执行完整性、守恒、一致性和可玩性校验。

### 10.1 多来源冲突建议优先级

同一字段出现多个来源时不能简单取最后一个值。首版建议按以下原则裁决：

- 产品标识：库存/补货明细与产品表现表交叉验证；
- 日销售：带明确日期和 ASIN 粒度的业务报告优先；
- 当前库存：以选定截止日最新的库存明细为准；
- 在途和 ETA：出货表的实际节点优先于补货建议中的计划节点；
- 库龄和成本：库存明细优先，月度汇总用于总额校验；
- 公式结果：保留展示值，同时按正式规则重算并记录差异；
- 无法自动判断的冲突进入 `data_conflict_log`，不静默覆盖。

## 11. 关键计算与守恒约束

- `available_now = fba_sellable + awd_available + overseas_available - reserved - unsellable`
- `projected_available(d) = available_now + cumulative_arrivals(d) - cumulative_demand(d)`
- `coverage_days = available_now / max(recent_daily_demand, epsilon)`
- `gap_qty = max(0, target_stock - projected_available(target_date))`
- 父 ASIN 和产品线指标必须由入选子 ASIN 聚合；
- 真实月销量被拆分为日销量时，补齐后的日销量之和必须等于真实月总量；
- 仓储费分配到子 ASIN 后必须与客户真实汇总金额一致；
- 库存批次剩余量之和必须与对应库存位置总量一致；
- 供应事件只有到达或可承诺日期进入窗口后才能增加未来可用量；
- 同一版本的总览、列表和详情必须引用同一份盘点结果；
- 所有补齐值必须可追溯，不能覆盖对应的客户真实原值。

## 12. 数据包结构建议

建议采用“ETL/补齐脚本 + 标准化数据 + 页面数据集 + manifest”：

```text
bamboocool-ai-workbench-demo/
├── scripts/
│   ├── import-customer-data.mjs
│   ├── normalize-product-inventory.mjs
│   ├── supplement-missing-data.mjs
│   └── build-inventory-assessment.mjs
├── data/
│   ├── normalized/
│   │   ├── products.json
│   │   ├── sales.json
│   │   ├── inventory.json
│   │   ├── lots.json
│   │   └── supply-events.json
│   └── serving/inventory/
│       ├── dataset-manifest.json
│       ├── forecasts.json
│       ├── assessments.json
│       ├── risks.json
│       └── lineage.json
└── app/
    └── 按产品方案实现的页面与路由
```

`dataset-manifest.json` 至少包含：数据截止日、来源文件版本、记录数、真实/派生/补齐比例、规则版本、盘点版本和质量检查结果。

## 13. 质量门槛

- 每个页面字段都能说明是客户真实值、派生值还是补齐值；
- 客户可用字段不被补造值覆盖；
- 入选父/子 ASIN 的产品标识关系完整且无重复主键；
- 所有子 ASIN 具备页面所需的历史销售、当前库存和未来投影；
- 三页对同一子 ASIN、同一版本的风险、库存和建议量完全一致；
- 五类风险均有可筛选样本，优先来自真实数据；
- 真实汇总值与标准化明细的误差处于可解释范围；
- 重复文件不会被重复累计；
- 冲突字段和补齐字段均有日志；
- Demo 中所有新增场景有明确标记，不冒充客户原始事实。

## 14. 实施顺序

1. 从客户真实数据中建立产品、销量、库存、在途和库龄标准表；
2. 计算字段完整度，确定首版真实父/子 ASIN 范围；
3. 输出缺失字段矩阵和多来源冲突清单；
4. 确认补齐规则、预测规则和库存风险规则；
5. 只对缺失字段和缺失场景进行补充；
6. 生成预测、库存投影、盘点结果、风险及血缘；
7. 建立新的 Demo 前端工程，并按正式三页架构接入数据；
8. 完成跨页面一致性、场景覆盖和可玩性验收。
