## 1. 为什么要这个模块

客户运营组长吴孙昇 00:48:01 给的是战略建议，不是产品意见：

> 「我们能集中一个点，比如说产品与库存……然后帮助到我们运营去更精准的预投跟下单，
> 这件事就已经成功了 80% 了。」

理由是老板画像（01:04:08）：

> 「他绝对理解这一点，但是你如果说跟他讲广告，他就他就没啥感觉，因为他是干供应链出身的。」

而这条链在项目里**几乎不存在**：233KB 主方案出现「预投」1 次，工作台全部代码 0 次。
客户点名说成功 80% 的那件事，demo 里没有。这个模块补的就是它。

### 1.1 预投是什么（吴组长原话拼出来的定义）

> 「预投是……我们预先的把这个面料给他发下去。意思就是说我下个月可能需要 100 吨或者 50 吨
> 这样子，然后让他们去准备」（00:43:45）

**预投 = 提前给工厂下面料准备量。单位是销售单位（盒/袋），不是吨。**
生产端拿到盒数后自己拆条数与配色（00:59:36）。面料量由盒数 × 单包条数换算。

### 1.2 时间链条（00:56:21 ~ 01:03:07）

```
 预投          备面料约 1 个月        下单        生产 10~25 天   物流 15~20 天      开卖
  │──────────────────────────────────▶│──────────────────────────────▶│─────────────▶│
 M 月初                             M+1 月初                                        M+2 月
                        ← 合计约两个半月（吴组长：「按两个半月比较平均一点」）→
```

基准日 **2026-08-03** ⇒ 现在做的是 **2026 年 10 月销售月**的预投，下单月是 **2026 年 09 月**。

### 1.3 考核（01:01:44）

> 「你每个月的预投数字跟你的下单数字，要差不多在 70% 以上，
> 就是说你投 100 万，你得用掉 70 万」

**达成率 = 总下单数 ÷ 预投总数 ≥ 70%。** 投多了的部分变成面料库存，是纯资金占用
（「备到面料这事，其实已经变成钱了」01:01:25）。

### 1.4 三个人为判断点 —— Agent 该接的正是这三处（01:05:57）

> 「所以这里面全是人为判断，所以这里面在我看来有三个人为判断，
> 如果能把这三个人为判断交给 AI 来做的话，会好很多」

| # | 判断点 | 现在人怎么做 | 错在哪 |
| --- | --- | --- | --- |
| 1 | **预投数量偏差** | 3/7/15/30 天加权平均，再凭经验对市场/去年同期做主观调整 | 「跟人的经验有一定关系，跟你市场的判断还有一定关系」（00:57:48）——每个运营偏差不一样 |
| 2 | **下单数字偏差** | 同一套加权平均 | 「他只考虑到过去的情况……明明下个月是会安排一些 BD 或者 LD，而他没有把这些事考虑进去」（01:05:31） |
| 3 | **尺码与配色拆分偏差** | 人工拆 M/L/XL | 「尺码之间的销量也是动态波动的」（01:05:57） |

## 2. 第一步：页面需要什么

### 2.0 组织页面的那条标准（v0.2 修正）

**v0.1 错在这里，记下来免得重犯。**

v0.1 是这么组织页面的：把吴组长会上提到的每一件事各建一个板块——他说了三个人为
判断点，就建「三个判断点」板块；说了两个半月链条，就建「时间链条」板块；说了
70% 考核，就建考核页；说了 30 万盒≈200 吨，就建换算。

这是**需求覆盖清单**的组织方式，不是页面设计。结果是页面结构等于会议要点结构，
看起来像会议记录套了个表格外壳。用户第一句反馈就是「我感觉你是把会议内容复制上去了，
而不是专门做了一个页面」——判断准确。它还带出两个连带症状：

- 界面上出现 12 处「客户原话：……」。运营不需要看他自己领导说过的话。
- 界面上出现 10 处对实现与 Demo 局限的解释（「所以两个数不一样，两个都给」）。
  那是设计者在辩护，契约 §11 第一条明令禁止这类表述上屏。
- 详情页七个板块里三块核心列是空的、一块对全部 57 个配色组一模一样。
  **空位被会议原话撑起来了**，所以看起来有内容。

### 2.0b v0.3 修正：预投不是新事，是库存预估的一个新出口

v0.2 仍然错在一处：它**自己复刻了一套预估**（运营现在那套 3/7/15/30 天加权平均），
拿它当建议值的来源和对拍基线。用户 2026-09-04 的判断：

> 「它的这个问题其实它跟我们的库存盘点是一样的，因为它的核心都是去预估一个 ASIN
> 在未来一定时间的一个销量……这个基础的 AI 的预估销量已经是有的，我们直接把这个
> 预投给它加到这个逻辑里面就行了……你搞得有点太复杂了。」
>
> 「吴组长他也说了，他们现在的这个预估方式是比较草率的，只考虑了 3 天销量、
> 7 天销量、14 天销量这种平均。那我觉得既然用上 AI 了，就不需要这么草率的
> 拉个公式了……我们直接用我们的预估销量模型做就行了呀。」

**所以 v0.3 删掉了自建预估这一整块**，包括四个窗口权重参数。建议值改成：

```
预投建议 = 目标销售月的逐子体预估 p50 按配色组聚合 × (1 + 安全余量)
```

预估直接读需求预测 Agent 的产出（跑过的子体用它，没跑过回落数据包脚手架，
每组标出是哪一种）。参照列换成一个纯事实：**近 30 天实销** —— 吴组长举例时
用的就是它（「最近 30 天卖了 1000 件」→ 投 110%），不是复刻公式。

### 2.0c 连带结论：预投不需要自己的 Agent

吴组长点名的三个人为判断点，在有了**逐子体** 90 天预估之后已经全部有归属：

| 他说的判断点 | 实际归谁 |
| --- | --- |
| 预投数量偏差（对市场/去年同期的主观调整） | 需求预测 Agent 已在判（缺货扭曲/活动/生命周期） |
| 下单数字偏差（没考虑未来 BD/LD） | 需求预测 Agent 已吃 `plan_child_promotion_daily` |
| 尺码与配色拆分偏差 | **不需要判断** —— 预估本来就是逐子体做的，子体就是尺码，占比是求和的自然产物 |

所以 `preinvest-judgment` Agent 与 `agent_result.py` 已整块删除。
预投模块自己的东西只剩四样确定性的：**时间口径 / 聚合层级 / 单位链 / 那份可交的表**。

### 2.0d 核心视图：图上圈一段

> 「你只是需要把那个库存预估那给预投做一个专属的前端就行。比如说我们不是柱状图吗？
> 你把柱状图的某一段专门标出来，我们现在预投就是这部分的一个量就行了呀，比较简单。」

依据页的主体因此是一张逐日柱状图：左边深色 120 天历史实销、右边浅色 90 天预估，
**销售月那一段染成强调色并加背景带**，那一段求和就是预估销量。两条参考线：
基准日（历史/预估分界）、这批最早到货日（落在销售月中间 → 说明上半月卖的还是现有库存）。

### 2.0e 时间口径：M+2（已拍定）

8 月做的预投对应 **10 月** 的销量。依据是源表 —— 逐月预投列与月报预投下单表全是 M+2。

推导过 M+3（前置期 75 天 → 10-17 到货 → 服务下一个整月 11 月），但实测
**需求预估只有 90 天（到 2026-11-01），11 月只覆盖 1/30 天，数字不可用**
（预估合计 2,110 盒 vs 应有 6 万+）。要走 M+3 需要预估先延长到 119 天。
口径差异由用户在会上向客户解释。参数 `pre.target_month_offset` 默认 2，可切。

### 2.0f v0.2 的标准仍然成立：按运营要做的那一个动作组织

预投这件事真实的动作序列是：每月某天，运营要交一份预投表给生产端
（款号×组合×盒数）。他现在的做法是打开 Excel，看 3/7/15/30 天加权，凭经验调，
填数字，交上去，一个月后下单被考核。

**这一页要替代的就是那个填数动作。** 一切板块按它是否服务这个动作来取舍。

### 2.1 三页与各自那个动作

| 页面 | id | 用户 | 要做的那个动作 | 产物 |
| --- | --- | --- | --- | --- |
| **预投考核** | `pre-audit` | 组长 / 老板 | 看上一轮准不准，决定这轮要不要收紧 | 判断（无交付物） |
| **预投计划** | `pre-plan` | 运营 | **填这一轮的预投表并交出去** | `.xlsx` 交生产端 |
| **配色组依据** | `pre-group` | 运营 | 决定某一行的建议值接受还是改掉 | 那一行的最终值 |

默认落地页仍是 `pre-audit`：汇报对象是供应链出身的老板，先看「现在有多不准」，
再看这轮打算怎么投。

### 2.2 预投计划页的板块（每一块都服务「填表并交出去」）

| 板块 | 服务那个动作的哪一步 |
| --- | --- |
| 页头 + 截止日 | 这轮什么时候必须定稿 |
| 摘要（当前合计 / 折吨 / 有几行要看） | 这份表现在是什么样 |
| **需要你看的 N 行** | 先看该看的，带「为什么要你看」 |
| **按建议走的 M 行**（默认折叠） | 剩下的不占注意力 |
| 每行的「我要投」输入框 | 就地改，改完当场看到折吨与合计的变化 |
| 底部「导出预投表」 | 交出去 |

**57 行不平铺。** 平铺等于把分类工作推回给人。按四条确定性判据分两堆，
判据阈值在参数面板里可调（属于工作台算术，不进 Agent）：

| 判据 | 含义 | 实测命中（57 组） |
| --- | --- | --- |
| `diff` | AI 建议与现行口径差异超过 `pre.review_diff_rate` | 0（Agent 未接通） |
| `missed` | 上一轮达成率低于 `pre.achieve_rate_min` | 7 |
| `promo` | 下月活动覆盖尺码比例 ≥ `pre.review_promo_coverage` | 18 |
| `ramp` | 生命周期是成长期，历史加权不可靠 | 9 |
| `nohist` | 找不到上一轮记录，建议值没有历史校验 | 0（都有记录） |

结果 29 行需复核 / 28 行按建议走，需复核那些行占建议总量 58%。

⚠️ `promo` 第一版写成「有 BD/LD 就复核」，命中 47/57 = 86% —— **命中 86% 的判据
等于没有分层**。实测活动覆盖尺码比例中位数只有 17%（6 个尺码里 1 个做 3 天 LD），
所以加了覆盖门槛。低于门槛的行仍显示活动标记，只是不进复核。
（这与「门禁要打在真有那个特征的对象上」是同一条纪律。）

### 2.3 每行必须有一个可交的数

`suggested_units` = AI 建议（有就用）否则现行 Excel 口径，
并且 `suggested_from` 必须上屏标明来源。

**这不是静默回落。** v0.1 把 AI 列留空、不给打底值，结果是 Agent 未接通时
这一页没有产物，运营还得回 Excel 填——页面价值为零。标明来源的打底值让他能改、
能交，而 AI 那一列独立存在时对拍照旧成立。

配套的一条：AI 一个都没判时，「现行口径」列不出现——它与「系统建议」是同一个数，
同一个数占两列会看起来像 bug（也违反契约 §11「两个数相等不要分两句报」）。

### 2.4 配色组依据页的板块

只回答「这个建议值我该接受还是改掉」，所以只有四块：

| 板块 | 作用 |
| --- | --- |
| 决策条：系统建议 → 我要投 → 折面料 | 就地改，实时换算 |
| 建议值怎么来的（四个窗口日均摊开） | 只给结果它就是黑盒，摊开才能判断改不改 |
| **三样反驳证据** | 见下 |
| 尺码拆分 | 生产端按它拆条，是交付物的一部分 |

三样证据是用来**反驳建议值**的——建议值是算出来的，这三样是事实：

1. **去年同期** —— 现行口径完全不看这个数，人工调整那一步补的就是它
2. **上一轮** —— 这个组自己的历史准不准，最硬的一条
3. **下月活动** —— 已排好但现行口径算不进去的增量

三样都不支持改动时，就按建议走。

**AI 理由块只在真有 AI 判断时才渲染整块**，未接通时不出现——不放空卡。
同理尺码建议列、瀑布图都遵循这条：

> **没有内容的板块整块不渲染，不用说明文字把它撑起来。**
> 页面因此会变短，但短的是实话。

### 2.5 从这一页移走的东西（v0.1 有、v0.2 没有）

| 移走的 | 为什么 |
| --- | --- |
| 时间链条甘特 | `chain_dates` 不接 group_id，对全部 57 个配色组一模一样，放单对象详情页是装饰。现在只剩计划页页头一行「本轮须在 X 前定稿」 |
| 预投构成瀑布图 | 它画的是三段 AI 判断各调了多少。未接通时三段全空；接通后同样信息在依据页用三张理由卡讲得更清楚。代码已删，不留死代码 |
| 「三个判断点」独立板块 | 那是 AI 怎么想的，不是运营要看的七个板块之一。融进 AI 理由块 |
| 逐月预投走势（详情页那份） | 与「这一行该投多少」无关。整组趋势留在考核页 |
| 全部 12 处「客户原话」 | 运营不需要看自己领导说过的话。它们属于方案文档与汇报稿 |
| 全部对 Demo 局限的解释 | 契约 §11 明令禁止 |

### 2.6 运营改的值存在哪

存浏览器 localStorage（键 `preinvest.overrides.v1`），**不写库**——
契约 §6.1 要求模块对所有数据源只读，写库全在 Agent 侧。

导出时随 POST body 带给后端合并（57 行改动放不进 query string）。
界面上如实标成「存在这台浏览器本地，换机器不会带过去」。
最终交付物是那个 `.xlsx`：「系统建议」与「我最终投」分两列不并，另有一列记录
人工调整了多少盒——并了拿文件的人分不清哪个数是人定的。

### 2.7 明确不做的

- 不做面料吨位到具体面料品号的拆解（客户没给面料 BOM）
- 不做「预投→采购单」的执行动作（契约 §9：AI 建议不得渲染成已执行动作）
- 不做逐月预投历史的金额汇总（源表预投数在尺码行上重复，会重复计数）

## 3. 第二步：整条逻辑与 Agent 设计

### 3.1 分界尺子（契约 §0 / 08-Agent 需求与数据契约要则）

> **这条数据在真实业务里、Agent 跑之前，存在吗？**
> 存在 → 输入。不存在、要判出来 → 产出，且页面展示的必须是这一份。

### 3.2 计算链（八步，工作台算 6 步，Agent 判 1 步，人审 1 步）

```
① 建配色组               产品包 dim_product_child 按 style_no×combination 聚 → 57 组
   ↓                     工作台 · 确定性
② 聚 10 月预测销量        需求预测 Agent 的子体级 p10/p50/p90 → 按组按月求和
   ↓                     工作台 · 确定性（不重做预测，消费已有那份）
③ 复刻现行 Excel 口径     3/7/15/30 天加权日均 × 目标月天数 × (1+安全余量)
   ↓                     工作台 · 确定性 ← 这是对拍基线，必须可复现
──────────────────────────────────────────────────────────────────────
④ 预投判断 Agent          三段判断，见 §3.3
   ↓                     Agent · LLM 真产出
──────────────────────────────────────────────────────────────────────
⑤ 单位换算               盒 → 条（×单包条数）→ 吨（×666.7 g/盒）
   ↓                     工作台 · 确定性
⑥ 达成率预判与考核        预判下单÷预投；历史轮次算真实达成率与闲置
   ↓                     工作台 · 确定性
⑦ 资金占用估算            闲置盒数 × 单盒成本 × 面料成本占比（占比待客户确认）
   ↓                     工作台 · 确定性，结果标「待确认」
⑧ 人工审批               运营看「建议量 + 原因 + 预期结果」，认可才落为本轮预投
                         页面只呈现，不代替人按下去
```

第 ⑧ 步的形态与 09-03 会上定的广告形态一致（AI 出动作+原因+预期结果 → 人审批），
不是这个模块自己发明的一套。

### 3.3 Agent 设计：一个 Agent，三段判断

**为什么是一个而不是三个。** 三个判断点共享同一份上下文（同一配色组的历史、去年同期、
未来活动、尺码轨迹），且第 2、3 段依赖第 1 段的结果。拆成三个 Agent 会引入依赖顺序，
还会出现三次推理互相矛盾（预投量按旺季判、下单量按淡季判）。
对比 8-31 会上客户要求「关键词拆两个 Agent」——那是因为对象不同（词 vs ASIN）；
这里三段的对象是同一个配色组。

```
id      : preinvest-judgment
label   : 预投判断
owner   : preinvest
对象    : 一个配色组（款号×组合）
触发    : 每月定时（预投窗口开启时）/ 运营手动 / 重点对象
```

**Agent 判（LLM 不可替代的三段）**

| 段 | 判断内容 | 为什么代码做不了 |
| --- | --- | --- |
| 一 | 预测销量能不能直接当预投基数；要不要按去年同期与市场走向调整、调多少、为什么 | 吴组长说这就是「人的主观」那部分，没有公式 |
| 二 | 未来已排的 BD/LD 会把这一轮下单推到什么水平 | 活动增量幅度要看品类、位置、往期同类活动表现 |
| 三 | 这一轮尺码占比该怎么拆（不是照抄历史占比） | M/L/XL 动态波动，要判断波动是趋势还是噪声 |

**工作台算（确定性，留在工作台阈值才能即时生效）**

聚合月度预测 / 现行 Excel 口径复刻 / 盒→条→吨换算 / 达成率与达标判定 /
闲置量与资金占用 / 尺码历史占比基线 / 时间链条六个日期 / 与现行口径的差额

**Agent 必填输入（真实业务里 Agent 跑之前就存在的）**

- 该组各子体近 730 天逐日销量（含去年同期同月）
- 该组各子体未来 90 天 p10/p50/p90（需求预测 Agent 的产出，是上游事实）
- 未来已排活动计划（BD/LD/Coupon 排期与折扣）
- 该组历史各轮预投数、下单数、达成率
- 该组尺码历史销量占比轨迹
- 该组身份：单包条数、子体清单、生命周期阶段

**禁止入参**（否则就是把答案递给它照读）

- 现行 Excel 口径算出的预投建议量 ← 这是要跟它对拍的另一方，喂进去它会向它收敛
- 源表 `预投预计` / `建议发货（2个月）` / `建议备货（4个月）` 三列 ← 口径不明
  （实测整数占比 2%，不是盒数），客户没确认过它算什么
- 任何本模块算出的达成率预判、闲置量、资金占用 ← 那是 Agent 判完之后的下游

**Agent 产出**

- 本轮预投建议盒数
- 三段判断各自的调整幅度与**中文依据**（每段一句，说得出维度+幅度+当前状态）
- 尺码占比建议（一组比例，和为 1）
- 本轮下单量预判（用于算达成率预判）
- 本次判断的确定程度与理由

**回落规则**（Agent 没跑过 / 库不存在 / 缺字段时页面怎么显示）

按契约要则：库不存在 → 整块标「未接入」；台账无该对象 → 「本期未判」；
字段 NULL → 显示「—」不填默认值；枚举落词表外 → 「待确认」。
**绝不静默回落到现行 Excel 口径然后假装是 AI 口径**——那会让页面上的对拍差额变成 0
却看不出原因。当前 Agent 侧 18812 未启动，所以这一版页面**默认就是「未接入」态**，
现行口径与预测聚合照常显示，AI 那一列显式空着。

## 4. 第三步：可视化

### 4.1 计划页与依据页不用图表

它们要回答的是「该投多少」和「这个数该不该改」。答案是**一个可改的数字加几条
并列的事实** —— 那些用数字块和表格比用图准确。v0.1 在这两页放了瀑布图和甘特图，
一个在 Agent 未接通时三段全空，一个对全部 57 个配色组一模一样，两个都已删除。

计划页的视觉重心是那一列输入框：数字右对齐 + 等宽，与上下的数字列对齐；
聚焦时只换边框不换尺寸（换尺寸会让整行跳）；改过的行给一条左边线而不改字色
（改字色会和语义色打架）。

依据页的视觉重心是顶部决策条：`系统建议 → 我要投 → 折面料` 三栏横排，
中间那栏是输入框且用强调色，一眼看出哪个数是人定的。
现行口径的四个窗口摊成一个公式行（`45.0 ×25% + 40.6 ×25% + … = 加权日均 40.3`），
只给结果它就是个不可核对的黑盒。

三样证据用三张等宽卡横排，卡顶一条色边表达状态（未达考核线=红、有活动=橙、
无数据=虚线），不靠颜色单独承载信息，卡内都有文字。

### 4.2 考核页两张图（保留）

**达成率分布直方图** —— 横轴达成率分桶，纵轴配色组数，考核线单独作为一条桶边界
画成竖线，线左侧警示色。桶边界必须让考核线落在边界上：跨线的桶会让「达标几个」
和图上看到的对不上。这张图的作用是一眼看出偏差形态——实测 62 组在 90% 以上、
17 组低于 30%，中间很少，说明不是普遍多投而是少数整批投错。

**分批下单节奏** —— 一条虚线是预投量，一条阶梯是四个下单日的累计下单，
两线之间的缺口用 areaStyle 填成一块可见的面积。把「投了但没用掉」画成面积，
而不是一个要自己减的数。

### 4.3 两条踩过的工程坑

**ECharts 不在 index.html 里。** 外壳不预加载它，库存模块是按需注入 script 标签的。
第一版这里写成 `if (!window.echarts) return null;` —— 结果图区一片空白且控制台
没有任何报错，是最难查的那种。现在改成按需加载，失败时在页面上渲染可见提示。

**只用 tokens.css 里真实存在的变量。** 第一版 CSS 用了 85 处发明的变量名
（`--ink-dim` / `--line` / `--sev-high` / `--fs-h1`…），未定义的 `var()` 让整条
声明失效，页面看着「还行」但边框、语义色、字号档位一条都没生效。
真实的是 `--fg3` / `--glass-line` / `--alert` `--warn` `--good` `--calm` /
`--fs-page` `--fs-title` `--fs-value` `--fs-body` `--fs-meta` `--fs-axis`。

**换算系数不在前端写死。** 折吨要在输入框里实时换算，但 `fabric_g_per_box` 是可调
参数，随载荷带到前端用——写死就是第二个真相来源，参数改了页面不变且没有症状。
