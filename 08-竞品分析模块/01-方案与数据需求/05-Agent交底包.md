## 1. 这个模块干什么

**判断对象：竞品产品族（父 ASIN）。** 子 ASIN、报价、关键词是底层观察对象，只在详情展开。

模块性质是**证据层**：输出「竞品发生了什么、可能影响哪里、证据是否充分」，
不输出预算、出价、广告开关、执行动作。

### 1.1 三条工作流，两条是 Agent 的

| 工作流 | 谁做 | 用 LLM | 入口 | `trigger` 取值 |
| --- | --- | :---: | --- | --- |
| 每日定时采集 | 自动化任务 | 否 | 每天固定时间去各来源取数、落表 | — |
| **周期性分析** | **Agent** | 是 | 采集完成后按周期跑；重点竞品（快捷位那 8 个）每周期必跑 | `scheduled` / `priority` |
| **点击触发分析** | **Agent** | 是 | 运营在页面上对某个族点「重新分析」 | `manual` |
| 呈现 | 工作台前端 | 否 | 打开即读最新一次，秒开 | — |

采集是自动化，不是 Agent 的事。**Agent 的两条工作流差别只在入口和 `trigger` 取值，判断步骤完全相同**，见 1.3。

页面本身**从不同步等 Agent**：三个路由都是只读 GET，读的是已沉淀的最新一次结果。点击触发是异步的，见 1.2。

### 1.2 触发契约（页面 ↔ Agent 的接缝）

**工作台模块不能写库**——契约 6.1 强制 `file:…?mode=ro` 只读打开。所以分工是：
**页面只负责发起请求、轮询状态、结果到了重取载荷；写库全在 Agent 侧。**

**页面点击时发出的请求**（`request_key` 用于幂等，同族同窗口重复点击应复用在跑的任务而不是排两个）：

```json
{
  "trigger": "manual",
  "family_asin": "B0FNQYP7DW",
  "window_from": "2026-02-05",
  "window_to": "2026-08-03",
  "data_as_of": "2026-08-03",
  "requested_by": "ops-wangnan",
  "request_key": "B0FNQYP7DW-2026-08-03-manual-1756600000",
  "thresholds": {
    "price_drop_pct": 5.0,
    "gap_shift_pct": 10.0,
    "rank_shift_pct": 15.0,
    "kw_rank_shift": 3,
    "min_duration_days": 7,
    "family_coverage_pct": 30.0,
    "stale_days": 14
  }
}
```

`thresholds` 就是页面参数面板上那七个当前值（默认值如上，可调范围见第 3 节）。**运营调完阈值再点重跑，Agent 必须用请求里带的值，不能用自己写死的**——否则页面筛选口径与 Agent 判断口径各说各话。周期性工作流没有页面上下文，用默认值。

**Agent 立即返回**，不等分析完成：

```json
{ "task_id": "T-B0FNQYP7DW-1756600000", "state": "queued" }
```

**状态机与页面行为**（轮询策略见下方 1.2.1）：

| `state` | 附带 | 页面显示 |
| --- | --- | --- |
| `queued` | — | 按钮变「排队中」并禁用，旧结果继续可读 |
| `running` | — | 「分析中」，**不遮挡现有内容** |
| `done` | `run_id` | 提示「已更新」，重取 `rival` 载荷，整页换成新 run |
| `skipped` | `reason` | 「无新观察数据，沿用 X 日的分析」，旧结果保留 |
| `failed` | `reason` | 「本次重跑失败 · <原因>」，旧结果保留，不涂红告警 |

#### 1.2.1 轮询策略：终态驱动，页面不设失败上限

**页面轮到终态（`done` / `skipped` / `failed`）才停，不因为「等太久」自己判失败。**
超时归任务服务管——它有权把卡住的运行判 `failed` 并给 `reason`；页面只负责如实反映。
页面自己设死上限会造成最糟的一种错：Agent 还在正常工作，页面已经告诉运营失败了。

| 阶段 | 轮询间隔 | 页面显示 |
| --- | --- | --- |
| 0 – 30 秒 | 2 秒 | 「排队中」/「分析中」 |
| 30 秒 – 3 分钟 | 5 秒 | 「分析中（已 1 分 20 秒）」——**显示已耗时，让人知道它在动** |
| 3 分钟以后 | 10 秒 | 「仍在分析（已 3 分 40 秒）」，**不改状态、不报失败** |
| 连续 5 次请求失败 | 停止 | 「暂时读不到分析状态」，**不宣称分析失败**，给「重新查询」按钮 |

**实测依据**（2026-08-31，八步顺序调用，`deepseek/deepseek-v4-flash`）：

| 环节 | 实测 |
| --- | --- |
| 入队 → `running` | 约 0.8 秒 |
| 完整八步 completed | **65.3s / 103.5s / 106.3s** |
| `skipped`（不调模型） | 亚秒级 |

原来写的「上限 2 分钟」按这个量级**已经贴着天花板**：106 秒的那次只剩 14 秒余量。
下一版改成分阶段取数后，五个受控取数工具会各加一次模型往返，
按单步 8–13 秒推算总时长会到 **105–170 秒**，固定 2 分钟上限会误杀掉相当一部分正常运行。
所以不设上限，改成上表的退避 + 显示已耗时。

**两种 `failed` 要分开显示**，因为运营该做的事不同：

| `reason` | 含义 | 页面该说 |
| --- | --- | --- |
| 「本地任务服务已重启，请重新发起分析」 | 别人的运行或跑批把这次挤掉了（实测：新进程启动会无条件把在飞任务判失败） | 「这次分析被另一次运行打断」+ 一键重新发起 |
| 其余 | 真失败 | 「本次重跑失败 · <原因>」+ 一键重新发起 |

**重跑是追加，不是覆盖。** 同族同日多跑会新增一行 `run`，靠 `created_at` 分先后（门禁 G8），页面按 `run_date DESC, created_at DESC` 取最新。被替代的那次仍在库里，新 run 的 `diff.prev_run_id` 应指向它。

**身份与时序由写入端盖章，不在 Agent 的输出面。** Agent 提交一批行，写入端补齐
`run_id`、`created_at`、`report_id`、`report.item_seq`、`handoff_id`、`ref_run_id`、
`frozen_run_id`、`prev_run_id`，以及从请求原样回填的 `family_asin` / `run_date` /
`data_as_of` / `window_from` / `window_to` / `trigger`。
判据是「需不需要跨 run 的全局视野」——单对象重跑的 Agent 拿不到全局排位，所以报告在
整份报告里排第几、id 里的序号，都只能由写入端定。完整清单与理由见
`04-Agent输出点盘点.md` 0.1。

### 1.3 一次运行的八步（两条 Agent 工作流共用）

**一次运行 = 一个竞品父 ASIN。** J1–J6 是这一次运行内部的六个判断环节，**不是六个 Agent**。

**输入**（只读观察层 + ATTACH 产品包）：父 ASIN + 观察窗；身份三层（族的在售子体数 vs 自报变体数、子体的装盒数与 `pack_resolved` 与主销标记、报价层的 BuyBox 与卖家）；四条序列（价格、市场表现、关键词位置、流量结构）；与自有的候选竞争关系 147 条；数据健康区间；自有件单价；上一次的 run。

| 步 | 判断点 | 判什么 | 关键判据与禁止项 | 写入 |
| --: | --- | --- | --- | --- |
| 0 | — | 组装观察窗与输入 | — | — |
| 1 | J3 上半 | **数据能不能用** | 断更、来源冲突、过期（超 `stale_days`）→ 定档 `sufficient` / `partial` / `insufficient`。判成 `insufficient` 就**在这里短路**：写 `attention_level=none`、**零条依据条目**、不进报告，只写证据不足原因与待补数据，结束 | `run` |
| 2 | J3 下半 | **变化性质分类** | 短期跳变 / 持续变化 / 断更造成的假变化。断更 14 天后回来的「排名大涨」是观察缺口不是市场变化，必须剔除，不进库。持续性看 `min_duration_days` | `change` 的日期、幅度、`current_state` |
| 3 | J2 | **能否代表整族** | 覆盖比例（`family_coverage_pct`）只是参考：71 个变体里 3 个降价与 3 个**主销**变体降价含义完全不同 | `change.represents_family` + `coverage_note` |
| 4 | J1 | **竞争关系是否成立** | 同类目同价格带不等于竞争，看材质、定位、包装数、人群。价差**一律按件单价**（竞品多 6 件装、自有 3/4/7 件装），`pack_resolved=0` 的对象排除在价差结论外 | 决定 `impact` 的自有一侧范围 |
| 5 | J4 | **同期关系是否成立** | 同期证据 / 先后关系 / 独立变化 / 证据不足。看每条轨的起止、幅度、覆盖与可信度组合。**只能表述为「同期变化」「可能相关」**，`causal_ready` 默认 0 | `concurrency` |
| 6 | J5 | **关注程度与影响范围** | 分级 + 至少 2 条可解释依据 + 允许运营手工调整。**禁止综合威胁分数**，禁止数字权重（`weight_note` 写「持续性最强」这类定性说明） | `run.attention_level` / `attention_summary` + `attention_reason` + `impact` |
| 7 | J6 | **报告选题与表达** | 「最值得关注」而不是「阈值命中项全列」。只写关注 `high`/`medium` 且证据充分、且至少一条 `represents_family=1` 的族。`headline` 就是那条变化本身，不写模板句 | `report` |
| 8 | — | 收尾装配 | 把变化铺成四轨时间线区段（含事件前后可比窗口）、写假设与待观察、与上一次 run 比出 `transition`、挑出该交给关键词页/广告页的证据 | `timeline` / `open_item` / `diff` / `evidence_handoff` |

一次运行的产出量级约 **8–15 行**，跨 10 张表。两个真实样例的实际行数见第 6 节。

## 2. 页面结构（两页）

### 2.1 竞品威胁总览 `/competitor` · 页面 id `cmp-overview`

主区只有一个焦点：**威胁比较表**。侧栏是可折叠抽屉（外壳提供把手）。

| 位置 | 板块 | 回答什么 | 数据来源 |
| --- | --- | --- | --- |
| 侧栏 | 本周期最值得关注 | 一条洞察，不重复比较表的结论 | `analysis_report` 第 1 条 |
| 侧栏 | 变化类型计数带 | 四类各几个族；点数字筛主表 | `analysis_change.domain` 去重族数 |
| 侧栏 | 快捷位（8 个常看竞品） | 常看的族 + 件单价 + 关注等级 | `dim_competitor_family.in_quick_slot` + 各族最新 run |
| 侧栏 | 数据状态与更新 | 四类观察更新到哪天 + 缺失/过期/待确认计数 | `fact_competitor_*_daily` 的 MAX(date) + `fact_competitor_data_status` |
| 侧栏 | 口径与未确认项（抽屉） | 范围、脊椎、竞争关系数、未确认口径 7 条 | `competitor_manifest` + `bridge_competitor_child` |
| 主区 | **威胁比较表** 8 列 | 先看谁 | 见下 |

比较表 8 列，一行一个竞品产品族：

| 列 | 内容 | 来源 |
| --- | --- | --- |
| 竞品身份 | 品牌 + 父 ASIN（左侧 3px 语义色条按关注等级） | `dim_competitor_family` |
| 当前威胁 / 变化 | 关注等级词 + 最重要那条变化的短标签 + 「较上次 加重/减弱」 | `run.attention_level` + `change[0].label` + `diff.transition` |
| 市场结果 | 40 点排名趋势线 + 当前名次 + 月量级 | `market_daily` 降采样 + `change(domain=market)` |
| 价格与促销 | 40 点件单价趋势线 + 当前件单价 + 整包价带 + 自有倍数（贵/便宜） | `price_daily` 降采样 + ATTACH 产品包算自有件单价 |
| 流量与关键词 | 关键词位置变化 + 流量结构变化 | `change(domain=keyword/traffic)` |
| 发生时间 | 首条变化起始日 + 当前状态 | `change[0].date_from/current_state` |
| 证据 | 数据性质词 + 状态词 + 「为什么」浮层 | `change.value_origin` 映射 + `run.evidence_level/evidence_reason` |
| 操作 | 「时间线」按钮进详情 | — |

排序：关注等级 → 状态正常优先 → 件单价。可切「最近变化 / 自有价差倍数 / 小类排名」（参数 `cmp.sort_by`）。**不生成综合威胁分数。**

### 2.2 单一竞品分析 `/competitor/cmp-rival/<父ASIN>` · 页面 id `cmp-rival`

| 板块 | 回答什么 | 数据来源 |
| --- | --- | --- |
| 判断带 | 为什么现在要看它 | hero = `run.attention_level`（28px）+ `attention_summary`；件单价中位、自有件单价倍数、在售子体/自报变体、数据性质+状态+本次分析日期与 trigger；下挂 `attention_reason` 依据列表；固定一行「同期变化不等于因果」 |
| **共同时间线**（第二焦点，ECharts） | 同期关系直接可读 | 三格共用一根横轴：① 件单价折线 + 活动期阴影带 + 自有件单价虚线参考线；② 小类排名折线（第 1 名在顶）+ 月新增评论柱；③ 四条泳道（价格活动 / 关键词位置 / 市场表现 / 数据状态）。dataZoom 缩放，悬停四轨游标同步并读出当天日期，点区段出事件前后可比窗口 |
| 市场表现与价格活动 | 当期决策数字 | `market_daily` / `price_daily` 末值 + 起点 + 活动天数；「产品族与报价关系」走抽屉（子体表 + 报价卖家 + 与自有竞争关系） |
| 关键词入口证据 | 该竞品当期落在前三的重点词 | `fact_competitor_keyword_rank` + `dim_competitor_keyword`；自然位画成位置条（起点 → 当前）；下挂流量结构一行 |
| 事实、模拟、假设与因果未知（四段） | 四者分开不混为一谈 | ① 可观察事实 = `change` 里 `value_origin ∈ direct/derived`；② 模拟数据得出的变化 = `value_origin = constructed`；③ 分析假设与待观察 = `open_item`；④ 不能确认的因果 = `concurrency` 里 `causal_ready = 0` |
| 分析记录与证据交付 | 存档、与上一版比较、交给下游 | `run.run_id` + `diff` + `data_status` + `evidence_handoff` |

**「重新分析」按钮在判断带右上**，点它按 1.2 发起点击触发工作流。**页面侧当前未实现**，
Agent 侧的运行端点与状态端点定下来后我这边接（见第 7 节）。

**三个降级分支**（Agent 漏写会掉进来）：

| 情形 | 页面行为 |
| --- | --- |
| 观察层有该族、判断层无 run | 三个事实看板照常显示，结论区写「尚未纳入分析」 |
| 有 run 但 `evidence_level = insufficient` | 不给关注等级、不进计数带、不进报告；只显示证据不足原因与待补数据 |
| 该族不在抓取名单（无历史） | 只给当期快照事实，不给任何变化结论 |

**新鲜度不告警**：客观显示「分析于 X 日 · 周跑」，不涂红、不排异常。

## 3. 框架功能（外壳 vs 模块的分工）

工作台 `09-工作台`，端口 18820，零依赖 Python（stdlib `http.server` + 只读 SQLite），前端原生 ES module。

**外壳提供**（模块不许重建）：全局导航、页签、快速筛选栏、参数面板、AI 交互窗口、右侧抽屉、单例浮层、URL 即状态（history / 筛选快照 / 滚动恢复）、`tokens.css` 设计令牌、数据性质与状态两套固定词表。

**模块提供**：

```text
09-工作台/modules/competitor/module.py   自描述入口（外壳唯一读的文件）
09-工作台/modules/competitor/data.py     只读数据层
09-工作台/modules/competitor/compute.py  两页载荷装配
09-工作台/modules/competitor/rules.py    cmp.* 参数声明
09-工作台/web/modules/competitor.js      前端 ES module
09-工作台/web/modules/competitor.css     作用域样式
09-工作台/web/modules/competitor/timeline.js  共同时间线图表
```

**三个路由**（前缀 `cmp`，参数键都带 `cmp.`）：

| 路由 | 返回 |
| --- | --- |
| `GET /api/competitor/meta` | 范围、观察窗、四类观察新鲜度、快捷位 8 个、竞争关系数、重点词数、数据状态计数、7 条未确认口径 |
| `GET /api/competitor/rivals` | 总览全部：洞察带 + 计数带 + 比较表（含每行 40 点趋势） |
| `GET /api/competitor/rival/<父ASIN>` | 详情全部：判断带 + 四轨 + 产品族报价 + 市场 / 价格逐日 + 关键词 + 流量 + 四段证据 + 记录交接 |

**九个可调参数**（`cmp.` 前缀，外壳统一解析并夹紧）：`price_drop_pct`、`gap_shift_pct`、`rank_shift_pct`、`kw_rank_shift`、`min_duration_days`、`family_coverage_pct`、`stale_days`、`sort_by`、`quick_only`。

前七个是「什么幅度才算一条值得上屏的变化」，**全部属于待客户确认项**。默认值与可调范围：

| 参数 | 默认 | 范围 | 步长 | 含义 |
| --- | --: | --- | --: | --- |
| `price_drop_pct` | 5.0 | 1–30 | 0.5 | 件单价相对前一段基线下降超过这个百分比才算一条价格变化 |
| `gap_shift_pct` | 10.0 | 2–50 | 1 | 自有与竞品件单价倍数变动超过这个百分比才上屏 |
| `rank_shift_pct` | 15.0 | 5–60 | 1 | 小类排名相对窗口起点变动超过这个百分比才算市场表现变化 |
| `kw_rank_shift` | 3 | 1–20 | 1 | 自然位变动超过这个名次才算一条关键词位置变化 |
| `min_duration_days` | 7 | 1–60 | 1 | 变化至少持续这么多天才上屏，滤掉单日跳变 |
| `family_coverage_pct` | 30.0 | 5–100 | 5 | 发生变化的子体占在售子体的比例达到这个值，才考虑上卷为整族事件 |
| `stale_days` | 14 | 3–90 | 1 | 某类观察比基准日旧过这么多天，标为过期并降低结论强度 |

**这七个值随点击触发的请求传给 Agent**（见 1.2 的 `thresholds`），Agent 必须用请求里的值判断，不能写死。周期性工作流没有页面上下文，用上表默认值。后两个（`sort_by`、`quick_only`）只管页面排序与筛选，不传给 Agent。

**四个筛选项**（外壳渲染，模块声明）：竞品或父 ASIN 搜索、子类目、变化类型、证据状态。

## 7. 还需要你那边定的三件事

1. **点击触发的轮询走哪条路。** 两个选项：① 你那边给一个状态端点（1.2 定的五态）；
